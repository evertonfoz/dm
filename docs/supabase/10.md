# Estados de Rede, Erro e Carregamento na Feature Tutor

## Objetivo do material

Neste material, você aprenderá a tratar corretamente os estados de carregamento, erro, lista vazia, paginação e operações CRUD na feature Tutor de uma aplicação Flutter que utiliza Supabase como fonte remota de dados. O foco é melhorar a experiência do usuário durante operações que dependem de rede, evitando telas que parecem travadas, mensagens confusas ou comportamentos inesperados. 

Ao final, a feature Tutor deverá ser capaz de:

1. indicar quando os dados estão sendo carregados;
2. diferenciar erro de lista vazia;
3. manter a lista visível quando apenas a paginação falhar;
4. bloquear ações duplicadas durante cadastro, edição e remoção;
5. exibir mensagens claras para o usuário;
6. registrar erros técnicos apenas durante o desenvolvimento;
7. organizar os estados da `TutorController` de forma previsível e reutilizável.

---

# 1. Contextualização: por que os estados de rede são importantes

Quando uma aplicação usa uma base local, como SQLite, as operações costumam responder rapidamente. A consulta, o cadastro, a edição e a remoção acontecem no próprio dispositivo. Por isso, muitas vezes o usuário quase não percebe tempo de espera.

Com Supabase, o cenário muda. A aplicação passa a depender de uma comunicação remota. Isso significa que qualquer operação pode ser afetada por:

* instabilidade de internet;
* demora na resposta do servidor;
* falha de autenticação;
* indisponibilidade temporária;
* permissões incorretas;
* erros na tabela remota;
* perda de conexão durante uma operação.

Por esse motivo, não basta implementar o CRUD. A interface precisa informar ao usuário o que está acontecendo. Uma tela sem feedback pode parecer travada. Uma lista vazia sem explicação pode ser confundida com erro. Uma mensagem técnica pode assustar ou confundir. Um botão de salvar sem bloqueio pode gerar cadastros repetidos.

A controller passa a ter papel central porque ela representa os estados da feature. A interface observa esses estados e reage visualmente a cada situação.

---

# 2. Conceitos fundamentais

## Estado de carregamento inicial

O carregamento inicial acontece quando a tela de tutores é aberta e a aplicação ainda não possui dados carregados na lista.

Esse estado deve ser representado por uma variável como:

```dart
bool _isLoading = false;
```

Quando `_isLoading` for `true` e a lista estiver vazia, a interface deve mostrar um indicador centralizado, como `CircularProgressIndicator`.

Esse estado responde à pergunta:

> “A tela está buscando os primeiros dados?”

Ele não deve ser confundido com paginação.

---

## Estado de paginação

A paginação acontece quando a tela já possui dados, mas precisa buscar mais registros ao chegar ao final da lista.

Esse estado deve ser separado do carregamento inicial:

```dart
bool _isPaginating = false;
```

A separação é importante porque o usuário não deve perder a lista inteira apenas porque a aplicação está carregando mais itens.

O carregamento inicial ocupa a tela toda. A paginação aparece normalmente no final da lista.

---

## Estado de erro

O estado de erro indica que uma operação falhou. A controller pode armazenar uma mensagem amigável para a interface exibir:

```dart
String? _errorMessage;
```

Quando `_errorMessage` for diferente de `null`, significa que existe um erro a ser mostrado ou tratado.

A mensagem deve ser compreensível para o usuário. Em vez de mostrar detalhes como `PostgresException`, `JWT expired` ou `permission denied for table tutors`, a aplicação deve exibir algo como:

```text
Não foi possível carregar os tutores. Verifique sua conexão e tente novamente.
```

O erro técnico pode ser útil para o desenvolvedor, mas não deve ser exibido diretamente ao usuário final.

---

## Estado de lista vazia

Lista vazia não é erro.

Esse é um dos pontos mais importantes deste material. Uma lista vazia significa que a busca funcionou, mas não encontrou registros cadastrados.

Por exemplo:

```text
Nenhum tutor cadastrado.
```

Esse estado só deve aparecer quando:

* o carregamento terminou;
* não existe erro;
* a lista de tutores está vazia.

Se houver erro, a mensagem deve ser de erro. Se ainda estiver carregando, deve aparecer loading. Se a busca funcionou e não trouxe dados, deve aparecer estado vazio.

---

## Estados de escrita: cadastro, edição e remoção

Operações de escrita são ações que modificam os dados. Na feature Tutor, elas incluem:

* cadastrar tutor;
* editar tutor;
* remover tutor.

Cada operação deve ter seu próprio estado:

```dart
bool _isInserting = false;
bool _isUpdating = false;
bool _isDeleting = false;
```

Separar esses estados evita comportamentos incorretos. Por exemplo, a aplicação pode estar removendo um tutor enquanto não está cadastrando outro. Usar um único `isLoading` para tudo torna a interface menos precisa e mais difícil de manter.

---

# 3. Estados necessários na `TutorController`

A `TutorController` deve manter estados separados para cada tipo de operação. Uma estrutura inicial adequada é:

```dart
bool _isLoading = false;
bool _isPaginating = false;
bool _isInserting = false;
bool _isUpdating = false;
bool _isDeleting = false;

String? _errorMessage;
```

Cada variável possui uma função específica:

`_isLoading` indica o carregamento inicial da listagem. Ele deve ser usado quando a tela ainda não possui dados e está buscando os primeiros registros.

`_isPaginating` indica que a próxima página de dados está sendo carregada. Ele deve aparecer no final da lista, sem apagar os registros já carregados.

`_isInserting` indica que um novo tutor está sendo cadastrado. Ele deve ser usado para bloquear o botão de salvar durante o cadastro.

`_isUpdating` indica que um tutor existente está sendo atualizado. Ele também deve bloquear o botão de salvar durante a edição.

`_isDeleting` indica que uma remoção está em andamento. Ele ajuda a evitar múltiplos pedidos de exclusão para o mesmo registro.

`_errorMessage` guarda uma mensagem de erro amigável. Ela deve ser limpa antes de novas tentativas e atualizada quando uma operação falhar.

---

# 4. Getters para expor os estados à interface

Os atributos da controller devem permanecer privados. A interface não deve acessar `_isLoading`, `_errorMessage` ou qualquer outro campo privado diretamente.

Em Dart, o prefixo `_` indica que o atributo é privado ao arquivo. Para permitir que a interface consulte os estados, a controller deve expor getters públicos.

```dart
bool get isLoading => _isLoading;
bool get isPaginating => _isPaginating;
bool get isInserting => _isInserting;
bool get isUpdating => _isUpdating;
bool get isDeleting => _isDeleting;

String? get errorMessage => _errorMessage;
bool get hasError => _errorMessage != null;
bool get isSaving => _isInserting || _isUpdating;
```

O getter `isSaving` é especialmente útil para formulários, porque cadastro e edição normalmente usam o mesmo botão de salvar. Em vez de a tela verificar separadamente `isInserting` e `isUpdating`, ela consulta apenas:

```dart
_controller.isSaving
```

Isso deixa a interface mais limpa e reduz repetição de lógica.

---

# 5. Limpando mensagens de erro

Erros antigos não devem permanecer na tela depois que o usuário inicia uma nova tentativa. Para isso, a controller deve ter um método de limpeza:

```dart
void clearError() {
  _errorMessage = null;
  notifyListeners();
}
```

Esse método faz duas coisas:

1. remove a mensagem de erro anterior;
2. chama `notifyListeners()` para avisar a interface que o estado mudou.

Sem essa limpeza, o usuário poderia corrigir uma situação, tentar novamente e ainda ver uma mensagem antiga, mesmo que a próxima operação esteja em andamento ou tenha dado certo.

---

# 6. Carregamento inicial da lista de tutores

O método de carregamento inicial deve:

1. impedir chamadas duplicadas;
2. ativar `_isLoading`;
3. limpar erros anteriores;
4. buscar os dados no repositório;
5. atualizar lista, offset e controle de paginação;
6. tratar erro com mensagem amigável;
7. desativar `_isLoading` no final;
8. notificar a interface.

Exemplo completo:

```dart
Future<void> loadTutors() async {
  if (_isLoading) return;

  _isLoading = true;
  _errorMessage = null;
  notifyListeners();

  try {
    final result = await _repository.getAllTutors(
      limit: _limit,
      offset: 0,
    );

    _tutors
      ..clear()
      ..addAll(result);

    _offset = result.length;
    _hasMoreData = result.length == _limit;
  } catch (error) {
    debugPrint('Erro ao carregar tutores: $error');

    _errorMessage =
        'Não foi possível carregar os tutores. '
        'Verifique sua conexão e tente novamente.';
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

A condição `if (_isLoading) return;` evita que o carregamento inicial seja executado várias vezes ao mesmo tempo.

O bloco `try` contém a operação remota. Se a busca funcionar, a lista local da controller é atualizada.

O bloco `catch` captura falhas. A mensagem técnica é registrada com `debugPrint`, mas o usuário recebe uma mensagem clara.

O bloco `finally` sempre é executado, com sucesso ou erro. Ele garante que `_isLoading` volte para `false`. Sem isso, a tela poderia ficar presa em estado de carregamento.

Para usar `debugPrint`, importe:

```dart
import 'package:flutter/foundation.dart';
```

# 7. Exibindo estados na `TutorListPage`

A interface deve reagir aos estados da controller. O ponto principal é respeitar a prioridade dos estados.

A ordem recomendada é:

1. carregamento inicial;
2. erro sem dados;
3. lista vazia;
4. lista com dados;
5. paginação ou erro de paginação no final da lista.

---

## Carregamento inicial

Quando a tela ainda não possui tutores e está carregando os primeiros dados, exiba um indicador centralizado:

```dart
if (_controller.isLoading && _controller.tutors.isEmpty) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}
```

Esse código deve ser usado apenas para o carregamento inicial. Ele não deve ser usado durante paginação, porque a paginação não deve substituir a lista inteira.

---

## Erro no carregamento inicial

Se houver erro e a lista estiver vazia, mostre uma mensagem com botão de tentar novamente:

```dart
if (_controller.hasError && _controller.tutors.isEmpty) {
  return Center(
    child: Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        Text(
          _controller.errorMessage!,
          textAlign: TextAlign.center,
        ),
        const SizedBox(height: 16),
        ElevatedButton(
          onPressed: _controller.loadTutors,
          child: const Text('Tentar novamente'),
        ),
      ],
    ),
  );
}
```

Esse comportamento evita que o usuário veja uma tela vazia sem saber o que aconteceu.

O botão “Tentar novamente” é importante porque oferece uma ação concreta. Em falhas de rede, a próxima tentativa pode funcionar.

---

## Lista vazia

Se o carregamento terminou, não existe erro e a lista está vazia, a tela deve informar que não há tutores cadastrados:

```dart
if (!_controller.isLoading &&
    !_controller.hasError &&
    _controller.tutors.isEmpty) {
  return const Center(
    child: Text('Nenhum tutor cadastrado.'),
  );
}
```

Essa mensagem é diferente de erro. Ela informa que a operação foi concluída com sucesso, mas não retornou registros.

---

# 8. Diferença entre carregamento, erro e lista vazia

Esses três estados costumam ser confundidos, mas representam situações diferentes.

Carregamento significa que a aplicação ainda está esperando uma resposta. O usuário deve ver um indicador visual.

Erro significa que a aplicação tentou buscar os dados, mas a operação falhou. O usuário deve ver uma mensagem clara e uma opção de tentar novamente.

Lista vazia significa que a busca funcionou, mas não existem registros cadastrados. O usuário deve ver uma mensagem simples, como “Nenhum tutor cadastrado.”

A diferença prática é:

```text
Carregamento: "Aguarde, estou buscando os dados."
Erro: "Não consegui buscar os dados."
Lista vazia: "Busquei os dados, mas não encontrei registros."
```

Nunca use o mesmo comportamento visual para todos esses casos. Isso prejudica a experiência do usuário e dificulta a compreensão do estado real da aplicação.

---

# 9. Tratando erro durante paginação

A paginação precisa de um cuidado especial. Se a próxima página falhar, a lista que já foi carregada não deve desaparecer.

O comportamento correto é:

* manter os tutores já carregados visíveis;
* mostrar uma mensagem de erro no final da lista;
* oferecer um botão para tentar carregar mais;
* não reiniciar a tela inteira;
* não apagar o contexto do usuário.

Exemplo de item no final do `ListView.builder`:

```dart
if (_controller.hasError && _controller.tutors.isNotEmpty) {
  return Padding(
    padding: const EdgeInsets.all(16),
    child: Column(
      children: [
        Text(
          _controller.errorMessage!,
          textAlign: TextAlign.center,
        ),
        const SizedBox(height: 8),
        OutlinedButton(
          onPressed: _controller.loadNextPage,
          child: const Text('Tentar carregar mais'),
        ),
      ],
    ),
  );
}
```

Esse trecho só deve ser exibido quando já existem tutores na lista. Se a lista está vazia e houve erro, trata-se de erro no carregamento inicial, não de erro de paginação.

A ideia principal é preservar o que já deu certo. Se os primeiros registros foram carregados, eles devem continuar visíveis.

# 10. Cadastro de tutor com estado de inserção

O cadastro deve usar `_isInserting`. O método pode retornar `bool` para informar ao formulário se a operação foi concluída com sucesso.

```dart
Future<bool> insertTutor(Tutor tutor) async {
  if (_isInserting) return false;

  _isInserting = true;
  _errorMessage = null;
  notifyListeners();

  try {
    await _repository.insertTutor(tutor);
    return true;
  } catch (error) {
    debugPrint('Erro ao cadastrar tutor: $error');

    _errorMessage =
        'Não foi possível cadastrar o tutor. Tente novamente.';
    return false;
  } finally {
    _isInserting = false;
    notifyListeners();
  }
}
```

O retorno `true` indica que o formulário pode fechar, voltar para a listagem ou exibir uma mensagem de sucesso.

O retorno `false` indica que a operação falhou. Nesse caso, o formulário deve permanecer aberto e exibir a mensagem da controller.

O bloqueio inicial evita chamadas repetidas se o usuário tocar várias vezes no botão de salvar.

---

# 11. Edição de tutor com estado de atualização

A edição deve usar `_isUpdating`. A estrutura é semelhante ao cadastro, mas a mensagem de erro deve representar atualização.

```dart
Future<bool> updateTutor(Tutor tutor) async {
  if (_isUpdating) return false;

  _isUpdating = true;
  _errorMessage = null;
  notifyListeners();

  try {
    await _repository.updateTutor(tutor);
    return true;
  } catch (error) {
    debugPrint('Erro ao atualizar tutor: $error');

    _errorMessage =
        'Não foi possível atualizar o tutor. Tente novamente.';
    return false;
  } finally {
    _isUpdating = false;
    notifyListeners();
  }
}
```

A separação entre `_isInserting` e `_isUpdating` permite que a controller represente exatamente qual operação está em andamento.

Mesmo que a tela use o getter `isSaving`, internamente a controller continua sabendo se a ação é cadastro ou edição.

---

# 12. Remoção de tutor com estado de exclusão

A remoção deve usar `_isDeleting`. Após remover o tutor, a listagem deve ser atualizada para refletir o estado atual do banco remoto.

```dart
Future<bool> deleteTutor(int id) async {
  if (_isDeleting) {
    return false;
  }

  _isDeleting = true;
  _errorMessage = null;
  notifyListeners();

  try {
    await _repository.deleteTutor(id);

    await refresh();

    return true;
  } catch (error) {
    debugPrint('Erro ao remover tutor: $error');

    _errorMessage =
        'Não foi possível remover o tutor. Tente novamente.';
    return false;
  } finally {
    _isDeleting = false;
    notifyListeners();
  }
}
```

O `refresh()` após a remoção é importante porque garante que a lista exibida na tela corresponda aos dados atuais do Supabase.

Sem o refresh, o tutor removido poderia continuar aparecendo temporariamente na interface, causando a impressão de que a exclusão falhou.

# 13. Bloqueando o botão de salvar

Durante cadastro ou edição, o botão de salvar deve ser desabilitado. Isso evita envios duplicados.

```dart
ElevatedButton(
  onPressed: _controller.isSaving ? null : _saveTutor,
  child: _controller.isSaving
      ? const SizedBox(
          width: 20,
          height: 20,
          child: CircularProgressIndicator(
            strokeWidth: 2,
          ),
        )
      : const Text('Salvar'),
)
```

Quando `_controller.isSaving` é `true`, o botão fica sem ação (`onPressed: null`) e mostra um loading pequeno.

Esse comportamento informa ao usuário que a ação foi recebida e está sendo processada.

Sem esse bloqueio, o usuário poderia tocar várias vezes no botão e criar requisições repetidas.

---

# 14. Exibindo erro no formulário

Quando cadastro ou edição falham, a mensagem deve aparecer em uma região visível do formulário, preferencialmente antes do botão de salvar.

```dart
if (_controller.hasError)
  Padding(
    padding: const EdgeInsets.only(bottom: 16),
    child: Text(
      _controller.errorMessage!,
      style: const TextStyle(
        color: Colors.red,
      ),
    ),
  )
```

Essa mensagem deve explicar o problema de forma simples. O usuário não precisa saber o nome da exceção técnica. Ele precisa entender que a ação não foi concluída e que pode tentar novamente.

# 15. Usando `SnackBar` para ações pontuais

Algumas ações ficam melhores com feedback temporário. A remoção é um bom exemplo.

Depois que o usuário remove um tutor, a aplicação pode mostrar uma `SnackBar` informando sucesso ou falha.

```dart
final success = await _controller.deleteTutor(tutor.tutorId!);

if (!context.mounted) {
  return;
}

ScaffoldMessenger.of(context).showSnackBar(
  SnackBar(
    content: Text(
      success
          ? 'Tutor removido com sucesso.'
          : _controller.errorMessage ?? 'Erro ao remover tutor.',
    ),
  ),
);
```

O uso de `context.mounted` é importante porque existe um `await` antes da exibição da `SnackBar`. Durante esse tempo, o widget pode ter sido removido da árvore. Se isso acontecer e o código tentar usar o `context`, pode ocorrer erro.

A validação com `context.mounted` evita esse problema.

---

# 16. Evitando mensagens técnicas para o usuário

Mensagens técnicas podem expor detalhes internos da infraestrutura e não ajudam o usuário a resolver o problema.

Evite exibir mensagens como:

```text
PostgresException
JWT expired
permission denied for table tutors
relation public.tutors does not exist
```

Essas mensagens podem ser úteis para o desenvolvedor, mas são inadequadas para o usuário final.

Prefira mensagens como:

```text
Não foi possível carregar os tutores. Verifique sua conexão e tente novamente.
```

```text
Não foi possível salvar o tutor. Verifique os dados e tente novamente.
```

```text
Não foi possível remover o tutor. Tente novamente.
```

A mensagem ideal deve responder a três pontos:

1. o que não foi possível fazer;
2. se existe alguma ação possível para o usuário;
3. sem expor detalhes técnicos desnecessários.

# 17. Registrando erro técnico durante o desenvolvimento

Durante o desenvolvimento, o erro técnico pode ser registrado no console com `debugPrint`.

```dart
} catch (error) {
  debugPrint('Erro ao carregar tutores: $error');

  _errorMessage =
      'Não foi possível carregar os tutores. '
      'Verifique sua conexão e tente novamente.';
}
```

Esse padrão separa dois públicos:

* o desenvolvedor vê detalhes técnicos no console;
* o usuário vê uma mensagem clara na interface.

Essa separação melhora a manutenção sem prejudicar a experiência do usuário.

# 18. Organizando mensagens de erro com constantes

Espalhar mensagens de erro pela controller dificulta manutenção. Se a mesma mensagem precisar ser alterada, será necessário procurar vários pontos do código.

Uma alternativa melhor é centralizar as mensagens em constantes privadas:

```dart
static const String _loadErrorMessage =
    'Não foi possível carregar os tutores. '
    'Verifique sua conexão e tente novamente.';

static const String _insertErrorMessage =
    'Não foi possível cadastrar o tutor. Tente novamente.';

static const String _updateErrorMessage =
    'Não foi possível atualizar o tutor. Tente novamente.';

static const String _deleteErrorMessage =
    'Não foi possível remover o tutor. Tente novamente.';
```

Depois, no bloco `catch`, basta usar a constante:

```dart
_errorMessage = _loadErrorMessage;
```

Exemplo aplicado:

```dart
Future<void> loadTutors() async {
  if (_isLoading) return;

  _isLoading = true;
  _errorMessage = null;
  notifyListeners();

  try {
    final result = await _repository.getAllTutors(
      limit: _limit,
      offset: 0,
    );

    _tutors
      ..clear()
      ..addAll(result);

    _offset = result.length;
    _hasMoreData = result.length == _limit;
  } catch (error) {
    debugPrint('Erro ao carregar tutores: $error');
    _errorMessage = _loadErrorMessage;
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

A centralização garante consistência no tom das mensagens e facilita revisões futuras.

# 19. Aplicação prática resolvida: implementando feedback completo na feature Tutor

## Cenário

A tela de tutores utiliza Supabase para listar, cadastrar, editar e remover registros. Como as operações dependem da rede, a interface precisa mostrar feedback adequado durante cada etapa.

## Objetivo

Implementar estados separados na `TutorController` e fazer a interface reagir corretamente a carregamento inicial, erro, lista vazia, paginação, cadastro, edição e remoção.

---

## Solução comentada

A controller deve conter estados separados:

```dart
bool _isLoading = false;
bool _isPaginating = false;
bool _isInserting = false;
bool _isUpdating = false;
bool _isDeleting = false;

String? _errorMessage;
```

Ela também deve expor getters:

```dart
bool get isLoading => _isLoading;
bool get isPaginating => _isPaginating;
bool get isInserting => _isInserting;
bool get isUpdating => _isUpdating;
bool get isDeleting => _isDeleting;

String? get errorMessage => _errorMessage;
bool get hasError => _errorMessage != null;
bool get isSaving => _isInserting || _isUpdating;
```

O carregamento inicial deve ativar `_isLoading`, limpar erros antigos e atualizar a lista:

```dart
Future<void> loadTutors() async {
  if (_isLoading) return;

  _isLoading = true;
  _errorMessage = null;
  notifyListeners();

  try {
    final result = await _repository.getAllTutors(
      limit: _limit,
      offset: 0,
    );

    _tutors
      ..clear()
      ..addAll(result);

    _offset = result.length;
    _hasMoreData = result.length == _limit;
  } catch (error) {
    debugPrint('Erro ao carregar tutores: $error');
    _errorMessage = _loadErrorMessage;
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

A interface deve distinguir carregamento, erro e lista vazia:

```dart
if (_controller.isLoading && _controller.tutors.isEmpty) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}

if (_controller.hasError && _controller.tutors.isEmpty) {
  return Center(
    child: Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        Text(
          _controller.errorMessage!,
          textAlign: TextAlign.center,
        ),
        const SizedBox(height: 16),
        ElevatedButton(
          onPressed: _controller.loadTutors,
          child: const Text('Tentar novamente'),
        ),
      ],
    ),
  );
}

if (!_controller.isLoading &&
    !_controller.hasError &&
    _controller.tutors.isEmpty) {
  return const Center(
    child: Text('Nenhum tutor cadastrado.'),
  );
}
```

O formulário deve bloquear o botão de salvar durante cadastro ou edição:

```dart
ElevatedButton(
  onPressed: _controller.isSaving ? null : _saveTutor,
  child: _controller.isSaving
      ? const SizedBox(
          width: 20,
          height: 20,
          child: CircularProgressIndicator(strokeWidth: 2),
        )
      : const Text('Salvar'),
)
```

A remoção deve atualizar a listagem após concluir:

```dart
Future<bool> deleteTutor(int id) async {
  if (_isDeleting) return false;

  _isDeleting = true;
  _errorMessage = null;
  notifyListeners();

  try {
    await _repository.deleteTutor(id);
    await refresh();
    return true;
  } catch (error) {
    debugPrint('Erro ao remover tutor: $error');
    _errorMessage = _deleteErrorMessage;
    return false;
  } finally {
    _isDeleting = false;
    notifyListeners();
  }
}
```

## Resultado esperado

Depois da implementação:

* ao abrir a tela, o usuário vê loading enquanto os dados são buscados;
* se a busca falhar, aparece uma mensagem clara com botão de tentar novamente;
* se não houver tutores, aparece a mensagem “Nenhum tutor cadastrado.”;
* durante paginação, a lista permanece visível;
* se a próxima página falhar, o erro aparece no final da lista;
* durante cadastro ou edição, o botão salvar fica desabilitado;
* durante remoção, a aplicação evita ações duplicadas;
* após remover um tutor, a listagem é recarregada;
* mensagens técnicas ficam no console, não na interface.

## Como validar

Para validar a implementação, abra a tela de tutores com internet funcionando. A lista deve carregar normalmente. Em seguida, teste com a tabela vazia. A tela deve mostrar estado vazio, não erro.

Depois, simule falha de conexão. No carregamento inicial, a tela deve exibir uma mensagem de erro com botão para tentar novamente. Se a falha ocorrer durante paginação, os tutores já carregados devem permanecer visíveis.

No formulário, toque rapidamente várias vezes em “Salvar”. A aplicação deve impedir envios duplicados, mantendo o botão desabilitado durante a operação.

Na remoção, exclua um tutor e observe se a listagem é atualizada. O tutor removido não deve continuar aparecendo após o refresh.

## Possíveis erros na implementação

Um erro comum é usar `_isLoading` para todas as operações. Isso torna a tela confusa, porque cadastro, edição, remoção, carregamento inicial e paginação passam a parecer a mesma coisa.

Outro erro é limpar a lista quando a paginação falha. Isso prejudica a experiência porque o usuário perde os registros que já estavam disponíveis.

Também é comum esquecer o `finally`. Quando isso acontece, um loading pode ficar ativo para sempre após uma exceção.

Outro problema frequente é exibir mensagens técnicas diretamente ao usuário. Isso deve ser evitado porque expõe detalhes internos e não orienta a ação do usuário.

# 20. Erros comuns e dúvidas frequentes

## Usar apenas um `isLoading` para tudo

Esse erro acontece quando a controller possui uma única variável para representar qualquer operação em andamento.

O problema é que a interface perde precisão. Ela não sabe se está carregando a lista, paginando, salvando ou removendo.

A solução é usar estados separados:

```dart
_isLoading
_isPaginating
_isInserting
_isUpdating
_isDeleting
```

---

## Apagar a lista quando a paginação falha

Quando a próxima página falha, a lista já carregada deve continuar na tela.

Apagar tudo faz o usuário perder contexto. A falha ocorreu apenas na tentativa de carregar mais dados, não nos dados já carregados.

O correto é mostrar o erro no final da lista e oferecer uma nova tentativa.

---

## Mostrar erro técnico ao usuário

Mensagens como `permission denied for table tutors` ou `JWT expired` não devem ser exibidas diretamente.

O usuário deve receber mensagens orientadas à ação, como:

```text
Não foi possível carregar os tutores. Verifique sua conexão e tente novamente.
```

O erro técnico pode ser registrado com `debugPrint`.

---

## Não bloquear o botão de salvar

Se o botão permanece ativo durante cadastro ou edição, o usuário pode tocar várias vezes e gerar requisições duplicadas.

A solução é desabilitar o botão enquanto `isSaving` for `true`.

---

## Esquecer de limpar erro antigo

Se `_errorMessage` não for limpo antes de uma nova tentativa, a interface pode continuar exibindo uma mensagem antiga.

Antes de iniciar uma operação, use:

```dart
_errorMessage = null;
```

Depois, chame:

```dart
notifyListeners();
```

---

## Usar `BuildContext` depois de `await` sem verificar `context.mounted`

Após um `await`, o widget pode não estar mais montado. Antes de exibir uma `SnackBar`, navegar ou usar o contexto, verifique:

```dart
if (!context.mounted) {
  return;
}
```

Isso evita erros relacionados ao ciclo de vida da interface.

# 21. Checklist explicado de validação

## Verifique se o carregamento inicial mostra feedback visual

O que verificar: ao abrir a tela de tutores, a interface deve exibir um indicador de carregamento enquanto busca os primeiros dados.

Por que importa: sem esse feedback, o usuário pode achar que a tela travou.

Como validar: abra a tela com uma conexão lenta ou simule atraso no repositório. O `CircularProgressIndicator` deve aparecer enquanto a lista está vazia e `_isLoading` está ativo.

O que acontece se faltar: a tela pode parecer parada, gerando dúvida sobre o funcionamento da aplicação.

---

## Verifique se erro e lista vazia são tratados separadamente

O que verificar: uma falha de rede deve mostrar mensagem de erro. Uma busca bem-sucedida sem registros deve mostrar “Nenhum tutor cadastrado.”

Por que importa: erro e ausência de dados são situações diferentes.

Como validar: teste uma falha de conexão e depois teste uma tabela vazia no Supabase.

O que acontece se faltar: o usuário pode interpretar uma falha como ausência de registros ou achar que uma lista vazia é problema técnico.

---

## Verifique se a paginação não apaga os dados já carregados

O que verificar: quando a próxima página falhar, os tutores já exibidos devem continuar na tela.

Por que importa: a falha da próxima página não invalida os dados anteriores.

Como validar: carregue a primeira página com sucesso e force erro ao buscar a próxima. A lista deve permanecer visível, com mensagem de erro no final.

O que acontece se faltar: o usuário perde contexto e pode acreditar que todos os dados desapareceram.

---

## Verifique se cadastro e edição bloqueiam o botão de salvar

O que verificar: durante cadastro ou edição, o botão “Salvar” deve ficar desabilitado e mostrar loading.

Por que importa: isso evita operações duplicadas.

Como validar: toque rapidamente várias vezes no botão de salvar. Apenas uma requisição deve ser enviada.

O que acontece se faltar: a aplicação pode cadastrar registros duplicados ou executar atualizações repetidas.

---

## Verifique se a remoção atualiza a listagem

O que verificar: após remover um tutor, a lista deve refletir o estado atual do banco remoto.

Por que importa: o usuário precisa confiar que a ação foi aplicada.

Como validar: remova um tutor e observe se ele deixa de aparecer após o `refresh()`.

O que acontece se faltar: o tutor pode continuar aparecendo, dando a impressão de que a remoção falhou.

---

## Verifique se as mensagens para o usuário são amigáveis

O que verificar: a interface não deve mostrar nomes de exceções, erros de banco ou mensagens internas do Supabase.

Por que importa: mensagens técnicas confundem o usuário e expõem detalhes internos.

Como validar: force erros e observe o texto exibido na tela.

O que acontece se faltar: a experiência fica menos profissional e menos compreensível.

---

## Verifique se erros técnicos são registrados apenas no console

O que verificar: o código deve usar `debugPrint` para registrar detalhes úteis ao desenvolvedor.

Por que importa: o desenvolvedor precisa investigar problemas sem expor detalhes ao usuário.

Como validar: force uma falha e confira o console durante o desenvolvimento.

O que acontece se faltar: a depuração fica mais difícil ou a interface passa a exibir informações inadequadas.

---

## Verifique se `notifyListeners()` é chamado nos momentos corretos

O que verificar: sempre que um estado relevante mudar, a controller deve notificar a interface.

Por que importa: sem notificação, a tela pode não atualizar.

Como validar: observe se loading, mensagens e botões mudam no momento certo.

O que acontece se faltar: a controller pode estar com o estado correto internamente, mas a interface continuará mostrando informações antigas.

---

# 22. Síntese final

A feature Tutor precisa representar corretamente os estados de operações remotas. Com Supabase, o tempo de resposta e as falhas de rede fazem parte da experiência real do usuário.

A controller deve manter estados separados para carregamento inicial, paginação, cadastro, edição, remoção e erro.

A interface deve reagir a esses estados de forma clara:

* loading centralizado no carregamento inicial;
* erro com botão de tentar novamente quando a lista está vazia;
* estado vazio quando a busca funciona, mas não retorna registros;
* mensagem de erro no final da lista quando a paginação falha;
* botão de salvar bloqueado durante cadastro ou edição;
* feedback pontual com `SnackBar` em ações como remoção.

A principal ideia é que cada estado da aplicação precisa ter um feedback visual compatível com o que está acontecendo.

---

# Conclusão

Em aplicações com dados remotos, fazer o CRUD funcionar é apenas parte da solução. A aplicação também precisa comunicar espera, erro, sucesso, ausência de dados e operações em andamento.

Quando a `TutorController` expõe estados bem separados e a interface reage corretamente a eles, a experiência se torna mais clara, previsível e segura.

Com esses ajustes, a feature Tutor passa a lidar melhor com a realidade de uma aplicação conectada ao Supabase: operações podem demorar, falhar, retornar vazio ou exigir nova tentativa. O papel da interface é transformar esses estados técnicos em feedback compreensível para o usuário.
