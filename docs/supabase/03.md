# Criando o Projeto e a Tabela de Tutores no Supabase

## Objetivo do material

Neste material, você aprenderá a preparar a estrutura inicial no Supabase para armazenar os dados da feature de Tutor do projeto Pet Care. O foco é criar um projeto remoto no Supabase, acessar o SQL Editor, executar um comando DDL para criar a tabela `tutors`, testar a tabela com dados de exemplo e compreender a lógica de exclusão lógica usando o campo `deleted_at`.

Ao final, a base remota estará pronta para receber dados de tutores cadastrados posteriormente em um aplicativo Flutter. A conexão entre Flutter e Supabase será tratada em uma etapa futura. Este material se concentra apenas na preparação do banco de dados remoto. 

---

## 1. Contextualização: por que criar a estrutura no Supabase antes de conectar o Flutter

Em uma aplicação real, os dados usados pelo aplicativo geralmente não ficam apenas no dispositivo do usuário. Eles precisam ser armazenados em uma base remota para que possam ser consultados, atualizados, protegidos e compartilhados entre diferentes acessos.

No projeto Pet Care, a feature Tutor precisa armazenar informações de pessoas responsáveis pelos pets. Antes de o Flutter enviar ou buscar esses dados, é necessário criar no Supabase uma tabela capaz de guardar essas informações de forma organizada.

O Supabase será usado como backend remoto, oferecendo um banco PostgreSQL gerenciado. Isso significa que a aplicação poderá usar uma base de dados relacional sem que seja necessário instalar e manter manualmente um servidor PostgreSQL.

Neste material, a tabela criada será chamada `tutors`. Ela armazenará dados como nome, e-mail, telefone e datas de controle do registro.

---

## 2. O que será criado no Supabase

A estrutura principal criada será uma tabela chamada `tutors`, dentro do schema `public` do banco PostgreSQL do Supabase.

A tabela terá os seguintes campos:

```sql
tutor_id
nome
email
telefone
created_at
updated_at
deleted_at
```

Esses campos representam os dados essenciais de um tutor e os metadados necessários para controlar criação, atualização e exclusão lógica.

A tabela será criada com o seguinte comando:

```sql
create table if not exists public.tutors (
  tutor_id bigint generated by default as identity primary key,
  nome text not null,
  email text not null,
  telefone text not null,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone not null default now(),
  deleted_at timestamp with time zone
);
```

Esse comando cria a tabela apenas se ela ainda não existir. Isso evita erro caso o comando seja executado mais de uma vez no mesmo projeto.

---

## 3. Diferença entre os nomes dos campos no Flutter e no banco de dados

No Flutter, usando Dart, é comum nomear atributos com a convenção `camelCase`. Nessa convenção, a primeira palavra começa com letra minúscula e as próximas palavras começam com letra maiúscula, como em `createdAt`.

No PostgreSQL, é comum usar a convenção `snake_case`, em que as palavras são separadas por underline, como em `created_at`.

Por isso, os campos podem aparecer de formas diferentes no código Flutter e no banco de dados.

No Flutter, os atributos podem ser representados assim:

```dart
nome
email
telefone
createdAt
updatedAt
deletedAt
```

No Supabase, as colunas correspondentes serão:

```sql
tutor_id
nome
email
telefone
created_at
updated_at
deleted_at
```

Essa diferença não é um erro. Ela apenas reflete convenções diferentes em ambientes diferentes. Posteriormente, o model `Tutor` poderá ter métodos de conversão para transformar dados recebidos do banco em objetos Dart e transformar objetos Dart em mapas enviados ao Supabase.

Por exemplo, o campo `created_at` vindo do banco poderá ser convertido para `createdAt` no Dart. Da mesma forma, `deletedAt` no Flutter poderá ser enviado como `deleted_at` para o banco.

## 4. Conceitos fundamentais

### 4.1 Supabase

O Supabase é uma plataforma que oferece recursos para aplicações, incluindo banco de dados PostgreSQL, autenticação, armazenamento de arquivos e configurações de acesso. Neste material, o recurso principal usado será o banco de dados.

Cada projeto criado no Supabase representa um ambiente independente da aplicação. Dentro dele ficam os recursos como tabelas, configurações, chaves de acesso e mecanismos de segurança.

### 4.2 PostgreSQL

PostgreSQL é o banco de dados relacional usado pelo Supabase. Um banco relacional organiza os dados em tabelas. Cada tabela possui colunas, que definem os tipos de dados, e linhas, que representam os registros armazenados.

No caso deste material, cada linha da tabela `tutors` representará um tutor.

### 4.3 Tabela

Uma tabela é uma estrutura usada para armazenar registros do mesmo tipo. A tabela `tutors` armazenará registros de tutores.

Cada tutor terá um identificador único, nome, e-mail, telefone e campos de controle temporal.

### 4.4 Coluna

Uma coluna define uma informação específica que será armazenada em cada registro. Por exemplo, a coluna `email` armazena o e-mail do tutor.

Cada coluna possui um tipo de dado e pode ter restrições, como ser obrigatória ou permitir valor vazio.

### 4.5 Chave primária

A chave primária identifica de forma única cada registro de uma tabela. Na tabela `tutors`, a chave primária será `tutor_id`.

Isso significa que dois tutores diferentes não poderão ter o mesmo `tutor_id`.

### 4.6 DDL

DDL significa Data Definition Language, ou Linguagem de Definição de Dados. São comandos SQL usados para criar ou alterar estruturas do banco, como tabelas e colunas.

O comando `create table` é um exemplo de DDL, pois define a estrutura de uma tabela.

### 4.7 DML

DML significa Data Manipulation Language, ou Linguagem de Manipulação de Dados. São comandos SQL usados para inserir, consultar, atualizar ou remover registros.

Exemplos de comandos DML são:

```sql
insert
select
update
delete
```

Neste material, o comando `create table` será usado para estruturar a tabela, enquanto `insert`, `select`, `update` e `delete` serão usados para testar os dados.

## 5. Criando um projeto no Supabase

Para começar, é necessário acessar o painel do Supabase e criar um novo projeto.

Durante a criação, o Supabase pode solicitar algumas informações importantes.

### Nome do projeto

O nome do projeto deve estar relacionado à aplicação. Para o projeto Pet Care, um nome possível é:

```text
pet-care
```

Esse nome ajuda a identificar o projeto no painel do Supabase, principalmente quando existem vários projetos na mesma conta.

### Organização

A organização indica onde o projeto ficará agrupado dentro da conta do Supabase. Em contas individuais, pode existir apenas uma organização. Em equipes, a organização pode representar um grupo de trabalho.

### Senha do banco

A senha do banco de dados PostgreSQL deve ser segura e guardada com cuidado. Ela não deve ser colocada diretamente no código Flutter.

Colocar senhas sensíveis no código da aplicação é uma prática insegura, pois o código pode ser versionado, compartilhado ou exposto. Em projetos reais, credenciais e chaves precisam ser tratadas com atenção.

### Região do servidor

A região do servidor define onde a infraestrutura do projeto ficará hospedada. O ideal é escolher uma região geográfica próxima dos usuários da aplicação, pois isso pode reduzir latência e melhorar a experiência de uso.

Depois de informar esses dados, é necessário aguardar a configuração inicial do projeto. Quando o projeto estiver pronto, será possível acessar o Dashboard do Supabase.

## 6. Áreas do Supabase usadas neste material

Neste material, duas áreas do Supabase são especialmente importantes: o Table Editor e o SQL Editor.

### Table Editor

O Table Editor permite visualizar e gerenciar tabelas de forma visual. Ele apresenta os registros em formato de grade, semelhante a uma planilha.

Ele é útil para:

```text
visualizar tabelas;
conferir colunas;
verificar registros inseridos;
navegar entre dados;
criar ou editar estruturas de forma visual.
```

Mesmo quando a tabela é criada por SQL, o Table Editor é útil para confirmar se a estrutura foi criada corretamente.

### SQL Editor

O SQL Editor permite executar comandos SQL diretamente no banco de dados do projeto.

Ele será usado neste material porque torna a criação da tabela mais explícita, reproduzível e fácil de registrar. Ao usar SQL, a estrutura da tabela fica documentada em um comando que pode ser salvo, reutilizado e versionado.

Essa escolha é importante porque evita depender apenas de cliques na interface. Um comando SQL pode ser repetido em outro ambiente, revisado por outras pessoas e reaproveitado em materiais futuros.

## 7. Criando a tabela `tutors` pelo SQL Editor

Para criar a tabela, siga o fluxo geral:

1. Acesse o projeto no Supabase.
2. Abra o SQL Editor.
3. Crie uma nova query.
4. Cole o comando SQL de criação da tabela.
5. Execute o comando.
6. Verifique a tabela no Table Editor.

O comando completo é:

```sql
create table if not exists public.tutors (
  tutor_id bigint generated by default as identity primary key,
  nome text not null,
  email text not null,
  telefone text not null,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone not null default now(),
  deleted_at timestamp with time zone
);
```

Esse comando cria a tabela `tutors` no schema `public`.

O uso de `if not exists` faz com que a tabela seja criada somente se ainda não existir. Isso evita que o banco retorne erro se a query for executada novamente.

---

## 8. Entendendo cada parte do comando SQL

### `create table if not exists public.tutors`

Esse trecho informa ao banco que deve ser criada uma tabela chamada `tutors` dentro do schema `public`.

O schema `public` é uma área padrão do PostgreSQL usada para organizar objetos do banco, como tabelas.

A expressão `if not exists` evita recriar uma tabela que já existe.

### `tutor_id bigint generated by default as identity primary key`

Esse campo será o identificador único de cada tutor.

O tipo `bigint` permite armazenar números inteiros grandes. A expressão `generated by default as identity` indica que o banco poderá gerar automaticamente o valor do identificador.

A restrição `primary key` define `tutor_id` como chave primária da tabela. Isso garante que cada registro tenha um identificador único.

Na prática, ao inserir um tutor, não será necessário informar manualmente o `tutor_id`. O banco gerará esse valor.

### `nome text not null`

Esse campo armazena o nome do tutor.

O tipo `text` permite guardar texto sem um limite pequeno pré-definido. A restrição `not null` indica que o campo é obrigatório. Portanto, não será permitido criar um tutor sem nome.

### `email text not null`

Esse campo armazena o e-mail do tutor.

Ele também é obrigatório por causa do `not null`.

Neste momento, o campo `email` ainda não possui restrição de unicidade. Isso facilita testes iniciais, mas em projetos reais pode ser necessário avaliar se o mesmo e-mail deve ou não poder aparecer mais de uma vez.

### `telefone text not null`

Esse campo armazena o telefone do tutor.

Embora telefone pareça número, ele foi definido como `text`. Essa escolha é adequada porque telefones podem conter caracteres como parênteses, hífens, espaços, código de área e zeros à esquerda.

Por exemplo:

```text
(45) 99999-1001
```

Se o telefone fosse tratado como número, informações de formatação poderiam ser perdidas, e zeros à esquerda poderiam ser removidos indevidamente.

### `created_at timestamp with time zone not null default now()`

Esse campo registra a data e hora de criação do registro.

O tipo `timestamp with time zone` armazena data e hora considerando fuso horário. A restrição `not null` obriga que o campo tenha valor.

O trecho `default now()` faz com que o banco preencha automaticamente esse campo com a data e hora atual quando o registro for criado, caso nenhum valor seja enviado.

### `updated_at timestamp with time zone not null default now()`

Esse campo registra a data e hora da última atualização do registro.

Assim como `created_at`, ele recebe automaticamente o valor atual no momento da inserção. Porém, quando o registro for atualizado posteriormente, será necessário atualizar também o campo `updated_at`, por exemplo usando `updated_at = now()` em comandos `update`.

### `deleted_at timestamp with time zone`

Esse campo será usado para exclusão lógica.

Ele pode ficar vazio, pois não possui `not null`. Quando `deleted_at` estiver com valor nulo, o tutor será considerado ativo. Quando `deleted_at` estiver preenchido, o tutor será considerado removido logicamente.

A exclusão lógica não apaga o registro do banco. Ela apenas marca que aquele registro não deve mais aparecer nas consultas principais da aplicação.

## 9. Testando a tabela com dados de exemplo

Depois de criar a tabela, é importante testar se ela aceita registros corretamente.

Para inserir dados de exemplo, execute:

```sql
insert into public.tutors (nome, email, telefone)
values
  ('Marcos Pereira', 'marcos.pereira@email.com', '(45) 99999-1001'),
  ('Beatriz Souza', 'beatriz.souza@email.com', '(45) 99999-1002'),
  ('Carlos Mendes', 'carlos.mendes@email.com', '(45) 99999-1003');
```

Observe que o comando informa apenas `nome`, `email` e `telefone`.

Não é necessário informar `tutor_id`, porque o banco gera esse valor automaticamente.

Também não é necessário informar `created_at` e `updated_at`, pois esses campos possuem `default now()`.

O campo `deleted_at` também não precisa ser informado. Como ele ficará nulo, os tutores inseridos serão considerados ativos.

## 10. Consultando os tutores cadastrados

Para consultar todos os tutores da tabela, execute:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
order by nome;
```

Esse comando busca todos os registros da tabela `tutors` e ordena o resultado pelo nome.

O resultado esperado é que apareçam os três tutores inseridos, com seus respectivos identificadores e datas preenchidas automaticamente.

A coluna `deleted_at` deverá aparecer vazia para os três registros, pois nenhum deles foi removido logicamente ainda.

---

## 11. Consultando apenas tutores ativos

Na aplicação, normalmente não se deseja exibir registros removidos logicamente. Por isso, a consulta mais próxima do comportamento esperado no aplicativo é:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
where deleted_at is null
order by nome;
```

A condição:

```sql
where deleted_at is null
```

significa: traga apenas os registros cujo campo `deleted_at` esteja vazio.

Essa é a regra central da exclusão lógica neste material. Um tutor ativo é aquele que ainda não possui data de exclusão.

---

## 12. Testando a exclusão lógica

Para simular a remoção lógica de um tutor, execute:

```sql
update public.tutors
set
  deleted_at = now(),
  updated_at = now()
where email = 'carlos.mendes@email.com';
```

Esse comando não apaga o registro de Carlos Mendes. Ele apenas preenche o campo `deleted_at` com a data e hora atual.

Também atualiza o campo `updated_at`, indicando que o registro sofreu uma alteração.

Depois de executar esse comando, rode novamente a consulta de tutores ativos:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
where deleted_at is null
order by nome;
```

O tutor Carlos Mendes não deverá aparecer no resultado, porque agora possui `deleted_at` preenchido.

Porém, se você executar a consulta sem filtro:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
order by nome;
```

o registro continuará existindo na tabela.

Essa diferença mostra o funcionamento da exclusão lógica: o dado é preservado, mas deixa de aparecer nas consultas que filtram apenas registros ativos.

## 13. Diferença entre exclusão física e exclusão lógica

### Exclusão física

A exclusão física remove o registro da tabela.

Um exemplo seria:

```sql
delete from public.tutors
where email = 'carlos.mendes@email.com';
```

Nesse caso, o registro deixaria de existir no banco.

### Exclusão lógica

A exclusão lógica preserva o registro, mas marca que ele foi removido.

Neste material, isso é feito preenchendo o campo `deleted_at`:

```sql
update public.tutors
set
  deleted_at = now(),
  updated_at = now()
where email = 'carlos.mendes@email.com';
```

A exclusão lógica é útil porque preserva histórico, reduz o risco de perda acidental de dados e permite recuperar informações removidas por engano.

No contexto de aprendizado, ela também ajuda a compreender como aplicações reais podem esconder registros sem apagá-los imediatamente do banco.

---

## 14. Limpando dados de teste

Depois de testar a tabela, pode ser necessário remover os dados de exemplo.

Para apagar todos os registros, mantendo a estrutura da tabela, use:

```sql
delete from public.tutors;
```

Esse comando remove todas as linhas da tabela `tutors`, mas não apaga a tabela.

Use esse comando apenas quando tiver certeza de que os registros são dados de teste. Em um projeto real, apagar todos os dados de uma tabela pode causar perda importante de informações.

A diferença é esta:

```text
delete from public.tutors;
```

remove os registros.

```text
drop table public.tutors;
```

apagaria a tabela inteira, incluindo sua estrutura.

Neste material, o comando usado para limpeza é apenas `delete`, pois a intenção é manter a tabela criada.

## 15. Aplicação prática resolvida: criar, testar e validar a tabela de tutores

### Cenário

Você está preparando o banco remoto do projeto Pet Care. A aplicação terá uma feature de Tutor, mas o Flutter ainda não será conectado ao Supabase neste momento.

A tarefa é criar a tabela `tutors`, inserir registros de teste, consultar os dados e validar a exclusão lógica.

### Objetivo

Criar uma tabela funcional no Supabase para armazenar tutores e confirmar que os principais comportamentos esperados funcionam:

```text
inserção de tutores;
consulta de todos os tutores;
consulta apenas de tutores ativos;
marcação de tutor como removido logicamente;
limpeza dos dados de teste.
```

### Solução passo a passo

Primeiro, crie a tabela:

```sql
create table if not exists public.tutors (
  tutor_id bigint generated by default as identity primary key,
  nome text not null,
  email text not null,
  telefone text not null,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone not null default now(),
  deleted_at timestamp with time zone
);
```

Esse comando prepara a estrutura da tabela. O banco será responsável por gerar o `tutor_id` e preencher as datas de criação e atualização inicial.

Em seguida, insira dados de teste:

```sql
insert into public.tutors (nome, email, telefone)
values
  ('Marcos Pereira', 'marcos.pereira@email.com', '(45) 99999-1001'),
  ('Beatriz Souza', 'beatriz.souza@email.com', '(45) 99999-1002'),
  ('Carlos Mendes', 'carlos.mendes@email.com', '(45) 99999-1003');
```

Esse comando cria três registros ativos. Como `deleted_at` não foi informado, ele fica vazio.

Agora, consulte todos os registros:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
order by nome;
```

O resultado esperado é a listagem dos três tutores.

Depois, consulte apenas tutores ativos:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
where deleted_at is null
order by nome;
```

Nesse momento, os três tutores ainda devem aparecer, pois nenhum foi removido logicamente.

Agora, marque um tutor como removido:

```sql
update public.tutors
set
  deleted_at = now(),
  updated_at = now()
where email = 'carlos.mendes@email.com';
```

Esse comando altera apenas o registro com o e-mail informado. O tutor não é apagado, mas passa a ter uma data em `deleted_at`.

Execute novamente a consulta de tutores ativos:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
where deleted_at is null
order by nome;
```

O resultado esperado agora é que apenas Marcos Pereira e Beatriz Souza apareçam.

Para confirmar que Carlos Mendes continua no banco, execute:

```sql
select
  tutor_id,
  nome,
  email,
  telefone,
  created_at,
  updated_at,
  deleted_at
from public.tutors
order by nome;
```

Agora os três registros devem aparecer, mas Carlos Mendes terá `deleted_at` preenchido.

### Como validar

A validação está correta quando:

A tabela `tutors` aparece no Table Editor do Supabase. Isso confirma que o comando DDL foi executado com sucesso.

Os registros inseridos aparecem na consulta geral. Isso confirma que o comando `insert` funcionou.

A consulta com `where deleted_at is null` mostra apenas registros ativos. Isso confirma que a regra de exclusão lógica está funcionando.

O tutor removido logicamente desaparece da consulta de ativos, mas continua aparecendo na consulta geral. Isso confirma que o registro não foi apagado fisicamente.

### Possíveis erros

Um erro comum é tentar inserir um tutor sem preencher `nome`, `email` ou `telefone`. Como esses campos possuem `not null`, o banco recusará a inserção.

Outro erro comum é esquecer o filtro `where deleted_at is null`. Nesse caso, a aplicação pode exibir registros que deveriam estar ocultos.

Também pode ocorrer erro se o comando de criação da tabela for alterado incorretamente, por exemplo removendo a chave primária. Sem chave primária, fica mais difícil identificar cada tutor de forma única.

## 16. Sobre permissões, autenticação e RLS

Neste momento, a tabela está sendo preparada para fins didáticos. O foco é criar a estrutura e validar seu funcionamento básico no SQL Editor.

Em projetos reais, o acesso aos dados precisa ser controlado com autenticação e políticas de segurança. No Supabase, esse controle costuma envolver RLS, ou Row Level Security.

RLS significa segurança em nível de linha. Com ela, é possível definir quais usuários podem ler, inserir, atualizar ou remover determinados registros.

A sequência natural do projeto é:

```text
primeiro, criar a estrutura da tabela;
depois, conectar o Flutter ao Supabase;
em seguida, configurar autenticação e políticas de acesso.
```

Essa ordem ajuda a separar responsabilidades. Antes de lidar com autenticação e segurança, é necessário ter uma estrutura de dados válida.

## 17. Erros comuns e dúvidas frequentes

### Erro 1: confundir `tutor_id` com `tutorId`

`tutor_id` é o nome da coluna no banco de dados. `tutorId` pode ser o nome do atributo no Dart.

Esses dois nomes podem representar a mesma informação, mas pertencem a contextos diferentes. A conversão entre eles deve ser feita no model ou em métodos específicos de mapeamento.

### Erro 2: usar número para telefone

Telefone não deve ser tratado como número em muitos sistemas. Ele pode ter formatação, código de área, espaços, símbolos e zeros à esquerda.

Por isso, o tipo `text` é mais adequado para o campo `telefone`.

### Erro 3: esperar que `updated_at` mude sozinho em toda atualização

O campo `updated_at` tem `default now()`, mas esse valor padrão é aplicado na criação do registro. Em atualizações futuras, é necessário informar explicitamente:

```sql
updated_at = now()
```

Sem isso, o registro pode ser alterado sem que a data de atualização seja modificada.

### Erro 4: esquecer o filtro de tutores ativos

Quando uma aplicação usa exclusão lógica, as consultas principais devem filtrar registros ativos.

A condição correta neste material é:

```sql
where deleted_at is null
```

Sem esse filtro, registros removidos logicamente podem aparecer na aplicação.

### Erro 5: usar `delete` quando a intenção era exclusão lógica

O comando `delete` remove fisicamente o registro. Para exclusão lógica, o correto é usar `update` preenchendo `deleted_at`.

A exclusão lógica preserva o registro. A exclusão física remove o registro.

### Erro 6: colocar senha do banco no código Flutter

A senha do banco não deve ser colocada diretamente no código do aplicativo. Credenciais sensíveis precisam ser protegidas.

Neste material, a senha é usada apenas na configuração do projeto no Supabase, não no código Flutter.

### Erro 7: não verificar a tabela no Table Editor

Depois de executar o SQL, é importante verificar visualmente se a tabela foi criada. O Table Editor ajuda a confirmar se as colunas existem e se os registros foram inseridos corretamente.
