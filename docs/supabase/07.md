# Criando o Repository Remoto de Tutor com Supabase

## Objetivo do material

Neste material, você aprenderá a criar uma implementação remota do contrato `TutorRepository` usando Supabase como fonte de dados. A feature Tutor já possui um `DataSource` remoto responsável por se comunicar diretamente com o Supabase. Agora, o objetivo é criar uma classe de Repository que utilize esse `DataSource` remoto e entregue para a controller a mesma interface esperada pelo domínio da aplicação. 

Ao final, a feature Tutor terá duas implementações concretas do mesmo contrato:

* `SQLiteTutorRepository`, voltada para dados locais em SQLite.
* `SupabaseTutorRepository`, voltada para dados remotos em Supabase.

A controller não precisará conhecer os detalhes de SQLite, Supabase, tabela remota ou chamadas diretas ao banco. Ela continuará dependendo apenas da abstração `TutorRepository`.

---

## Contextualização do problema

Em uma aplicação organizada em camadas, a controller não deve depender diretamente de detalhes de persistência de dados. Isso significa que a controller não deve saber se os tutores estão sendo salvos em SQLite, Supabase, API HTTP, arquivo local ou qualquer outra fonte.

Essa separação é importante porque reduz o acoplamento. Quando uma classe conhece detalhes demais sobre outra camada, qualquer mudança na origem dos dados pode obrigar alterações em várias partes da aplicação. Por exemplo, se a controller chamasse diretamente métodos específicos do Supabase, trocar Supabase por SQLite exigiria mudanças na controller. Isso tornaria a manutenção mais difícil.

O padrão usado aqui resolve esse problema com três papéis principais:

A **controller** coordena o fluxo da tela ou da feature, mas não executa diretamente operações de banco de dados.

O **Repository** implementa o contrato esperado pela controller e decide qual fonte de dados será usada.

O **DataSource** contém os detalhes concretos de acesso à fonte de dados, como Supabase ou SQLite.

Neste material, o foco é a criação do `SupabaseTutorRepository`, que será a ponte entre o contrato `TutorRepository` e o `TutorRemoteDataSource`.

---

# Conceitos fundamentais

## Repository

Um Repository é uma classe responsável por representar uma fonte de acesso aos dados de uma entidade ou recurso da aplicação. Ele oferece métodos de alto nível, como cadastrar, listar, buscar, atualizar e remover registros.

No caso da feature Tutor, o Repository trabalha com objetos do tipo `Tutor`. Ele não deve se preocupar com interface visual, estado de tela ou regras específicas da controller. Sua responsabilidade é fornecer operações de persistência compatíveis com o contrato definido no domínio.

Exemplo de métodos esperados em um Repository de Tutor:

```dart
Future<int> insertTutor(Tutor tutor);

Future<List<Tutor>> getAllTutors({int limit = 20, int offset = 0});

Future<Tutor?> getTutorById(int id);

Future<int> updateTutor(Tutor tutor);

Future<int> deleteTutor(int id);
```

Esses métodos representam operações comuns de CRUD: criação, leitura, atualização e remoção.

---

## Contrato `TutorRepository`

O contrato `TutorRepository` define quais métodos uma implementação de Repository precisa oferecer. Ele funciona como uma promessa: qualquer classe que implemente esse contrato deverá fornecer os métodos exigidos.

Isso permite que a controller dependa da abstração, e não da implementação concreta.

Por exemplo, a controller pode trabalhar com:

```dart
final TutorRepository _repository;
```

Em vez de depender diretamente de:

```dart
final SupabaseTutorRepository _repository;
```

Essa diferença é importante. Quando a controller depende de `TutorRepository`, ela pode receber tanto um `SQLiteTutorRepository` quanto um `SupabaseTutorRepository`, desde que ambos implementem os mesmos métodos.

---

## DataSource remoto

O `TutorRemoteDataSource` é a camada que sabe conversar diretamente com o Supabase. Ele conhece os métodos concretos de acesso remoto, como inserir, buscar, atualizar e excluir dados na tabela remota.

O Repository remoto não precisa repetir a lógica de comunicação com Supabase. Ele apenas delega as chamadas para o `DataSource`.

Essa separação evita duplicação de código e mantém cada classe com uma responsabilidade clara.

---

## Supabase

Neste material, o Supabase é a fonte remota de dados. A aplicação passa a poder manipular registros de tutores em uma base remota, em vez de depender apenas do armazenamento local.

Na prática, isso permite que os dados sejam acessados fora do dispositivo do usuário, desde que a aplicação esteja corretamente configurada e autenticada conforme a estrutura do projeto.

---

# Diferenças conceituais importantes

## Repository local e Repository remoto

A feature Tutor passa a ter duas implementações concretas do mesmo contrato.

O `SQLiteTutorRepository` usa SQLite como fonte local de dados. Ele é útil quando a aplicação precisa armazenar informações no dispositivo, trabalhar offline ou manter uma base local.

O `SupabaseTutorRepository` usa Supabase como fonte remota de dados. Ele é útil quando a aplicação precisa persistir informações em uma base acessível pela nuvem.

Apesar dessa diferença, para a controller os dois repositories parecem iguais, porque ambos implementam `TutorRepository`.

---

## Controller e Repository

A controller não deve saber como o dado é salvo. Ela apenas chama métodos do contrato.

Por exemplo:

```dart
await _repository.getAllTutors();
```

Esse trecho não informa se os dados vêm de SQLite ou Supabase. Isso é proposital. A controller solicita a operação, e a implementação concreta do Repository decide como executá-la.

---

## Repository e DataSource

O Repository não deve conter detalhes complexos de comunicação com o Supabase. Essa responsabilidade pertence ao DataSource remoto.

O Repository funciona como um adaptador entre o contrato da aplicação e os métodos do DataSource.

Por exemplo:

```dart
Future<int> insertTutor(Tutor tutor) {
  return _remoteDataSource.insert(tutor);
}
```

Nesse caso, o método público do contrato é `insertTutor`, enquanto o método do DataSource é `insert`. O Repository conecta essas duas formas de representação.


O primeiro import permite acessar o `TutorRemoteDataSource` e a implementação concreta `SupabaseTutorRemoteDataSource`.

O segundo import permite que o Repository trabalhe com o model `Tutor`.

# Criando a estrutura da classe

A classe deve implementar o contrato `TutorRepository`:

```dart
class SupabaseTutorRepository implements TutorRepository {
  final TutorRemoteDataSource _remoteDataSource;

  SupabaseTutorRepository({TutorRemoteDataSource? remoteDataSource})
      : _remoteDataSource =
            remoteDataSource ?? SupabaseTutorRemoteDataSource();
}
```

A declaração `implements TutorRepository` informa que a classe é obrigada a implementar todos os métodos definidos no contrato.

O atributo `_remoteDataSource` é privado porque começa com `_`. Isso significa que ele só deve ser acessado dentro do próprio arquivo. Essa é uma boa prática, pois impede que outras partes da aplicação manipulem diretamente a dependência interna do Repository.

O construtor recebe um parâmetro opcional chamado `remoteDataSource`. Se uma implementação externa for enviada, ela será usada. Caso contrário, a classe usará automaticamente `SupabaseTutorRemoteDataSource()`.

Essa decisão torna o Repository flexível. Em uso normal, basta criar:

```dart
final repository = SupabaseTutorRepository();
```

Mas em testes, é possível passar um DataSource falso, simulado ou controlado:

```dart
final repository = SupabaseTutorRepository(
  remoteDataSource: fakeTutorRemoteDataSource,
);
```

Isso facilita testes porque evita a necessidade de chamar o Supabase real em todos os cenários.

# Implementando os métodos do contrato

O contrato `TutorRepository` exige a implementação de cinco métodos principais. Cada método do Repository remoto delega a execução para o `TutorRemoteDataSource`.

## Método `insertTutor`

```dart
@override
Future<int> insertTutor(Tutor tutor) {
  return _remoteDataSource.insert(tutor);
}
```

Esse método recebe um objeto `Tutor` e solicita ao DataSource remoto que insira esse registro no Supabase.

O retorno é um `Future<int>`, indicando que a operação é assíncrona e que, ao final, será retornado um número inteiro. Esse inteiro normalmente representa o identificador do registro criado ou algum valor de confirmação definido pela implementação do DataSource.

O `@override` indica que esse método está sobrescrevendo uma exigência do contrato `TutorRepository`.

---

## Método `getAllTutors`

```dart
@override
Future<List<Tutor>> getAllTutors({int limit = 20, int offset = 0}) {
  return _remoteDataSource.getAll(
    limit: limit,
    offset: offset,
  );
}
```

Esse método lista tutores vindos da fonte remota.

O parâmetro `limit` define quantos registros devem ser retornados. O valor padrão é `20`.

O parâmetro `offset` define a partir de qual posição a busca deve começar. O valor padrão é `0`.

Esses dois parâmetros são úteis para paginação. Em vez de carregar todos os registros de uma vez, a aplicação pode buscar pequenos blocos de dados. Isso melhora desempenho e evita consumo desnecessário de recursos.

Exemplo:

```dart
final primeirosTutores = await repository.getAllTutors(
  limit: 20,
  offset: 0,
);

final proximosTutores = await repository.getAllTutors(
  limit: 20,
  offset: 20,
);
```

No primeiro caso, a busca começa no início. No segundo, a busca pula os primeiros 20 registros e retorna o próximo conjunto.

---

## Método `getTutorById`

```dart
@override
Future<Tutor?> getTutorById(int id) {
  return _remoteDataSource.getById(id);
}
```

Esse método busca um tutor específico pelo identificador.

O retorno é `Future<Tutor?>`. O símbolo `?` indica que o resultado pode ser nulo. Isso acontece quando não existe nenhum tutor com o `id` informado.

Esse comportamento é importante porque a aplicação precisa estar preparada para lidar com registros inexistentes.

Exemplo de uso:

```dart
final tutor = await repository.getTutorById(10);

if (tutor == null) {
  debugPrint('Tutor não encontrado.');
} else {
  debugPrint('Tutor encontrado: ${tutor.nome}');
}
```

---

## Método `updateTutor`

```dart
@override
Future<int> updateTutor(Tutor tutor) {
  return _remoteDataSource.update(tutor);
}
```

Esse método atualiza um tutor existente na fonte remota.

O objeto `Tutor` enviado precisa conter as informações necessárias para identificar o registro que será atualizado. Em geral, isso significa que o campo de identificação deve estar preenchido corretamente.

Se o objeto não tiver um identificador válido, o DataSource pode não conseguir localizar o registro no Supabase.

---

## Método `deleteTutor`

```dart
@override
Future<int> deleteTutor(int id) {
  return _remoteDataSource.delete(id);
}
```

Esse método remove um tutor pelo identificador.

Ele recebe apenas o `id`, porque para excluir um registro normalmente não é necessário enviar todos os dados do tutor. Basta indicar qual registro deve ser removido.

Assim como os outros métodos, ele delega a operação para o DataSource remoto.

---

# Arquivo completo

O arquivo `supabase_tutor_repository.dart` completo deve ficar assim:

```dart
import 'package:pet_care/features/tutor/data/datasources/tutor_remote_datasource.dart';
import 'package:pet_care/features/tutor/domain/models/tutor.dart';
import 'package:pet_care/features/tutor/domain/repositories/tutor_repository.dart';

class SupabaseTutorRepository implements TutorRepository {
  final TutorRemoteDataSource _remoteDataSource;

  SupabaseTutorRepository({TutorRemoteDataSource? remoteDataSource})
      : _remoteDataSource =
            remoteDataSource ?? SupabaseTutorRemoteDataSource();

  @override
  Future<int> insertTutor(Tutor tutor) {
    return _remoteDataSource.insert(tutor);
  }

  @override
  Future<List<Tutor>> getAllTutors({int limit = 20, int offset = 0}) {
    return _remoteDataSource.getAll(
      limit: limit,
      offset: offset,
    );
  }

  @override
  Future<Tutor?> getTutorById(int id) {
    return _remoteDataSource.getById(id);
  }

  @override
  Future<int> updateTutor(Tutor tutor) {
    return _remoteDataSource.update(tutor);
  }

  @override
  Future<int> deleteTutor(int id) {
    return _remoteDataSource.delete(id);
  }
}
```

Esse código é simples porque a responsabilidade principal do Repository, neste momento, é cumprir o contrato e encaminhar as operações para a fonte remota.

# Comparação entre as duas implementações

A feature Tutor passa a ter duas classes concretas:

```text
SQLiteTutorRepository
SupabaseTutorRepository
```

As duas implementam:

```text
TutorRepository
```

Isso significa que ambas oferecem os mesmos métodos para a controller:

```text
insertTutor
getAllTutors
getTutorById
updateTutor
deleteTutor
```

A diferença não está na interface pública, mas na origem dos dados.

O `SQLiteTutorRepository` acessa dados locais.

O `SupabaseTutorRepository` acessa dados remotos.

Essa equivalência reduz o impacto da mudança na aplicação. A controller não precisa ser reescrita para trocar a fonte de dados. Basta alterar qual implementação concreta será injetada ou usada como padrão.

# Aplicação prática resolvida: criando e testando o Repository remoto

## Cenário

A feature Tutor já possui um `TutorRemoteDataSource` capaz de conversar com Supabase. Agora, é necessário validar se o novo Repository remoto consegue listar e cadastrar tutores usando essa fonte remota.

## Objetivo

Criar uma instância de `SupabaseTutorRepository`, chamar seus métodos principais e verificar se a comunicação com o Supabase ocorre corretamente.

---

## Teste de listagem

Depois que o Supabase já estiver inicializado na aplicação, crie temporariamente um teste simples:

```dart
final repository = SupabaseTutorRepository();

final tutores = await repository.getAllTutors(
  limit: 5,
  offset: 0,
);

debugPrint('Tutores carregados: ${tutores.length}');
```

Esse teste cria uma instância do Repository remoto e solicita os cinco primeiros tutores cadastrados.

O parâmetro `limit: 5` limita a quantidade de registros retornados.

O parâmetro `offset: 0` indica que a busca começa no primeiro registro disponível.

O `debugPrint` exibe no console a quantidade de tutores carregados. Se a conexão estiver correta e a tabela estiver acessível, o resultado deve mostrar um número igual ou maior que zero.

---

## Teste de cadastro

Também é possível testar a inserção de um tutor:

```dart
final repository = SupabaseTutorRepository();

final tutor = Tutor(
  nome: 'Teste Repository',
  email: 'teste@email.com',
  telefone: '(45) 99999-9090',
  createdAt: DateTime.now(),
  updatedAt: DateTime.now(),
);

final id = await repository.insertTutor(tutor);

debugPrint('Tutor inserido com id: $id');
```

Nesse exemplo, um objeto `Tutor` é criado com dados básicos. Em seguida, o método `insertTutor` é chamado.

O valor retornado é armazenado na variável `id`. Esse valor pode ser usado para confirmar que a inserção ocorreu.

Depois da execução, acesse o painel do Supabase e verifique se o registro foi criado na tabela `tutors`.

---

## Comentário da solução

Esses testes são temporários. Eles servem apenas para validar se o Repository remoto está funcionando antes de conectá-lo oficialmente à controller.

Depois da validação, esse código de teste deve ser removido. Manter testes temporários espalhados pela aplicação pode gerar cadastros duplicados, consultas desnecessárias ou comportamentos inesperados durante o uso normal do app.

---

## Resultado esperado

Ao executar o teste de listagem, a aplicação deve exibir no console a quantidade de tutores carregados.

Ao executar o teste de cadastro, a aplicação deve exibir no console o identificador do tutor inserido.

No Supabase, deve ser possível visualizar o novo registro na tabela `tutors`.

---

## Como validar

A validação deve considerar três pontos.

Primeiro, confirme se não há erro de compilação. Se algum método obrigatório do contrato não foi implementado, o Dart apontará erro na classe `SupabaseTutorRepository`.

Segundo, confirme se a execução não gera erro de inicialização. O Supabase precisa estar inicializado antes de qualquer chamada ao Repository remoto.

Terceiro, confirme se os dados aparecem no painel do Supabase. Essa é a evidência prática de que o DataSource remoto e o Repository estão trabalhando corretamente.

---

# O que o Repository remoto faz e o que ele não faz

## O que ele faz

O `SupabaseTutorRepository` implementa o contrato `TutorRepository`.

Ele usa uma fonte de dados remota para executar operações relacionadas a tutores.

Ele funciona como ponte entre a camada de domínio e o Supabase.

Ele permite que a controller continue chamando os mesmos métodos, sem depender diretamente de detalhes da base remota.

---

## O que ele não faz

O Repository remoto não controla estado de tela.

Ele não contém componentes de interface.

Ele não deve decidir quando mostrar mensagens, loading ou navegação.

Ele também não deve concentrar chamadas complexas ou regras específicas de tela. Esse tipo de responsabilidade deve ficar nas camadas apropriadas da aplicação.

---

# Erros comuns e dúvidas frequentes

## Esquecer o `implements TutorRepository`

Se a classe não declarar `implements TutorRepository`, ela deixa de garantir formalmente que cumpre o contrato esperado pela controller.

O código pode até conter métodos parecidos, mas a aplicação perde a segurança de tipo fornecida pelo contrato.

A forma correta é:

```dart
class SupabaseTutorRepository implements TutorRepository {
}
```

---

## Não implementar todos os métodos obrigatórios

Quando uma classe implementa um contrato, todos os métodos exigidos precisam ser implementados.

Se faltar `deleteTutor`, `updateTutor`, `getTutorById`, `getAllTutors` ou `insertTutor`, o Dart indicará erro.

Esse erro é útil porque impede que uma implementação incompleta seja usada pela controller.

---

## Importar o arquivo errado

Se o import do DataSource remoto estiver incorreto, o Dart não reconhecerá `TutorRemoteDataSource` ou `SupabaseTutorRemoteDataSource`.

O import esperado é:

```dart
import 'package:pet_care/features/tutor/data/datasources/tutor_remote_datasource.dart';
```

Também é necessário importar o model e o contrato:

```dart
import 'package:pet_care/features/tutor/domain/models/tutor.dart';
import 'package:pet_care/features/tutor/domain/repositories/tutor_repository.dart';
```

---

## Chamar o Repository antes da inicialização do Supabase

O Repository remoto depende de uma estrutura remota já configurada. Se a aplicação tentar buscar ou inserir dados antes da inicialização do Supabase, a operação pode falhar.

Por isso, antes de executar testes ou conectar a controller ao Repository remoto, confirme se o Supabase foi inicializado no `main.dart`.

---

## Confundir Repository com DataSource

O DataSource conversa diretamente com a fonte de dados.

O Repository implementa o contrato usado pela aplicação e delega as operações ao DataSource.

Misturar esses papéis deixa o código menos organizado. Se o Repository começar a conter detalhes demais sobre Supabase, ele passa a acumular responsabilidades que deveriam estar no DataSource.

---

## Manter código de teste temporário na aplicação

Os testes de listagem e cadastro são úteis durante a validação, mas devem ser removidos depois.

Se forem mantidos, podem causar inserções repetidas, logs desnecessários ou chamadas remotas inesperadas.

---

Se o arquivo for criado em outra pasta, os imports podem ficar confusos e a arquitetura da feature perde clareza.

## Verifique se a classe implementa `TutorRepository`

A classe deve começar assim:

```dart
class SupabaseTutorRepository implements TutorRepository {
```

Isso importa porque garante que a implementação remota oferece os mesmos métodos esperados pela controller.

Para validar, observe se o Dart não aponta erro de implementação incompleta. Se apontar, algum método obrigatório do contrato ainda está faltando.

## Verifique se o DataSource remoto foi importado corretamente

O arquivo precisa conhecer `TutorRemoteDataSource` e `SupabaseTutorRemoteDataSource`.

Esse item importa porque o Repository remoto não executa diretamente as operações no Supabase. Ele delega essas operações ao DataSource.

Se esse import estiver errado, a classe não compilará.

---

## Verifique se o model `Tutor` foi importado

O Repository recebe e retorna objetos do tipo `Tutor`, por isso precisa importar o model:

```dart
import 'package:pet_care/features/tutor/domain/models/tutor.dart';
```

Sem esse import, o Dart não reconhecerá o tipo usado nos métodos `insertTutor`, `getAllTutors`, `getTutorById` e `updateTutor`.

## Verifique se todos os métodos delegam para o DataSource

Cada método do Repository remoto deve chamar o método correspondente no `_remoteDataSource`.

Por exemplo:

```dart
return _remoteDataSource.insert(tutor);
```

Esse padrão importa porque mantém o Repository simples e evita duplicação de lógica. Se o Repository tentar implementar detalhes da chamada remota diretamente, ele passa a fazer o trabalho do DataSource.

---

## Verifique se `limit` e `offset` foram preservados na listagem

O método `getAllTutors` deve repassar os parâmetros para o DataSource:

```dart

  limit: limit,
  offset: offset,
);
```

Isso importa porque a paginação depende desses valores. Se eles não forem repassados, a controller poderá solicitar uma quantidade específica de registros, mas o DataSource ignorará essa solicitação.

---

## Verifique se o Supabase foi inicializado antes dos testes

Antes de chamar `SupabaseTutorRepository`, o Supabase precisa estar inicializado no `main.dart`.

Esse item importa porque o Repository remoto depende da infraestrutura de conexão com a base remota.

Se a inicialização não ocorrer antes da chamada, os métodos podem falhar mesmo que o Repository esteja implementado corretamente.

---

## Verifique se o registro aparece no painel do Supabase

Depois do teste de cadastro, acesse a tabela `tutors` no Supabase e confirme se o novo registro foi criado.

Essa validação importa porque a ausência de erro no código não garante, sozinha, que a operação persistiu os dados corretamente. A confirmação no painel mostra que a chamada chegou à base remota.

# Síntese final

O `SupabaseTutorRepository` é a implementação remota do contrato `TutorRepository`.

Ele permite que a feature Tutor trabalhe com dados remotos no Supabase sem obrigar a controller a conhecer detalhes da fonte de dados.

A controller continua dependendo da abstração `TutorRepository`.

O Repository remoto recebe ou cria um `TutorRemoteDataSource`.

Cada método do contrato é implementado e delegado para o DataSource remoto.

A feature Tutor passa a ter duas implementações concretas do mesmo contrato: uma local, baseada em SQLite, e uma remota, baseada em Supabase.

Essa estrutura melhora a separação de responsabilidades, facilita testes, reduz acoplamento e prepara a aplicação para trocar a fonte de dados com menor impacto.
