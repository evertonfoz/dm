# O que é o Supabase e por que usá-lo em um projeto Flutter

## Objetivo do material

Neste material, você aprenderá o que é o **Supabase**, por que ele pode ser usado em um projeto Flutter e como ele ajuda a evoluir uma aplicação que antes armazenava dados apenas localmente com **SQLite** para uma aplicação capaz de trabalhar com uma **base remota**.

O foco será a feature de **Tutor** do projeto Pet Care. Essa funcionalidade já possui operações de cadastro, listagem, edição, remoção e busca de tutores. Agora, ela será usada como exemplo para compreender como uma aplicação Flutter pode deixar de depender apenas do banco local do dispositivo e passar a consultar dados em um servidor remoto usando Supabase. 

---

# 1. Contextualização do problema

Até este momento, o projeto Pet Care armazenava os dados localmente usando **SQLite**. Isso significa que as informações ficavam gravadas dentro do próprio dispositivo do usuário. Esse modelo funciona bem quando a aplicação é usada em apenas um aparelho e não precisa compartilhar dados com outros usuários ou dispositivos.

Por exemplo, quando um tutor é cadastrado no celular de uma pessoa, esse dado fica disponível naquele aparelho. Mesmo que o aplicativo seja fechado e aberto novamente, os dados continuam salvos, pois o SQLite garante persistência local.

O problema aparece quando o sistema precisa crescer.

Imagine três cenários:

No primeiro cenário, existe apenas um dispositivo. O usuário cadastra tutores, edita dados e consulta informações sempre no mesmo aparelho. Nesse caso, o SQLite resolve bem o problema, pois não há necessidade de compartilhar os dados.

No segundo cenário, existem vários dispositivos. Um celular cadastra um tutor, mas outro celular também precisa enxergar esse mesmo cadastro. Nesse caso, o SQLite sozinho não resolve, porque cada aparelho possui sua própria base local isolada.

No terceiro cenário, o sistema precisa evoluir para funcionalidades mais amplas, como login de usuários, painel administrativo, integração com APIs externas, permissões de acesso e compartilhamento de dados. Tudo isso exige uma base centralizada, acessível pela internet.

É nesse ponto que surge a necessidade de uma **base remota**.

Uma base remota é um banco de dados que fica em um servidor e pode ser acessado pela internet. Em vez de salvar e consultar dados apenas dentro do celular, o aplicativo Flutter passa a se comunicar com um serviço externo para cadastrar, consultar, alterar e remover informações.

---

# 2. O que é o Supabase

O **Supabase** é uma plataforma de backend pronta para uso. Ele oferece recursos que normalmente exigiriam a criação de um servidor próprio. Em uma aplicação tradicional, seria comum desenvolver um backend do zero para receber requisições, validar dados, acessar o banco, controlar permissões e retornar respostas ao aplicativo.

Com o Supabase, parte dessa estrutura já vem pronta.

Entre os principais recursos do Supabase estão:

**Banco de dados PostgreSQL remoto:** permite armazenar dados em um banco relacional hospedado em servidor, acessível pela internet.

**Autenticação:** permite implementar login, cadastro de usuários e controle de sessão.

**API automática:** permite acessar tabelas do banco sem precisar criar manualmente todos os endpoints de um backend tradicional.

**Armazenamento de arquivos:** permite guardar imagens, documentos e outros arquivos em nuvem.

Neste primeiro momento do projeto Pet Care, o recurso mais importante será o **banco de dados remoto com PostgreSQL**, usado para armazenar os dados da tabela de tutores.

# 3. A tabela de tutores no Supabase

A feature de Tutor já possui dados que antes eram armazenados localmente. No Supabase, esses dados passam a existir em uma tabela remota chamada, por exemplo, `tutors`.

Essa tabela pode conter campos como:

| Campo        | Função no cadastro de tutor                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| `tutor_id`   | Identificador único do tutor. Serve para localizar, editar ou remover um registro específico.                |
| `nome`       | Nome do tutor cadastrado.                                                                                    |
| `email`      | E-mail do tutor, usado como dado de contato e possível identificação.                                        |
| `telefone`   | Telefone do tutor.                                                                                           |
| `created_at` | Data e horário em que o registro foi criado.                                                                 |
| `updated_at` | Data e horário da última atualização do registro.                                                            |
| `deleted_at` | Campo usado para indicar remoção lógica, quando o dado não é apagado fisicamente, mas marcado como removido. |

Com essa estrutura, a aplicação Flutter pode buscar tutores diretamente do Supabase. Assim, qualquer dispositivo autorizado pode acessar a mesma base de dados remota.

Essa mudança é importante porque o dado deixa de pertencer exclusivamente ao aparelho onde foi cadastrado. Ele passa a fazer parte de uma base centralizada.

# 4. SQLite e Supabase: diferenças conceituais importantes

SQLite e Supabase estão relacionados ao armazenamento de dados, mas resolvem problemas diferentes. Eles não devem ser vistos apenas como concorrentes. Em muitos projetos, eles podem até ser usados de forma complementar.

O **SQLite** é uma solução de persistência local. Ele armazena dados dentro do próprio dispositivo. É útil quando o aplicativo precisa funcionar offline, guardar preferências, manter dados temporários ou persistir informações que não precisam ser compartilhadas imediatamente.

O **Supabase**, por outro lado, funciona como uma solução de backend remoto. Ele permite centralizar dados em um servidor, tornando possível que diferentes dispositivos acessem a mesma informação.

Observe a comparação:

| Aspecto                             | SQLite              | Supabase                                            |
| ----------------------------------- | ------------------- | --------------------------------------------------- |
| Local dos dados                     | No dispositivo      | Em servidor remoto                                  |
| Internet obrigatória                | Não                 | Sim, para acessar a base remota                     |
| Compartilhamento entre dispositivos | Não diretamente     | Sim, se configurado corretamente                    |
| Tipo de uso                         | Persistência local  | Backend remoto                                      |
| Exemplo no projeto                  | Dados salvos no app | Dados em tabela remota                              |
| Complexidade                        | Menor               | Maior, pois envolve rede, permissões e configuração |

A diferença principal é esta: **SQLite resolve bem o armazenamento local; Supabase resolve o armazenamento remoto e compartilhado**.

Isso significa que o Supabase não substitui o SQLite em todos os cenários. Ele resolve outro tipo de necessidade. Um aplicativo pode usar apenas SQLite, apenas Supabase ou uma combinação dos dois, dependendo dos objetivos do sistema.

# 5. Por que usar a feature de Tutor como exemplo

A feature de Tutor foi escolhida porque já possui uma estrutura organizada e operações típicas de CRUD.

CRUD é uma sigla usada para representar quatro operações fundamentais sobre dados:

| Operação | Significado | Exemplo na feature Tutor                     |
| -------- | ----------- | -------------------------------------------- |
| Create   | Criar       | Cadastrar um novo tutor                      |
| Read     | Ler         | Listar tutores ou buscar um tutor específico |
| Update   | Atualizar   | Editar nome, e-mail ou telefone de um tutor  |
| Delete   | Remover     | Excluir ou marcar um tutor como removido     |

Como essas operações já existem usando SQLite, a feature Tutor é um bom ponto de partida para aprender a trocar a fonte de dados sem precisar reconstruir toda a aplicação.

O objetivo não é criar uma aplicação completamente nova. O objetivo é evoluir uma funcionalidade existente.

Em projetos reais, isso é muito comum. Uma funcionalidade começa simples, usando dados locais, e depois precisa crescer para permitir acesso remoto, sincronização, autenticação e compartilhamento entre dispositivos.

# 6. A importância da arquitetura em camadas

A mudança para Supabase fica mais simples porque o projeto já possui separação de responsabilidades.

A estrutura apresentada no material-base envolve camadas como:

**Tela ou página:** responsável pela interface com o usuário.

**Controller:** responsável por controlar ações da tela, estados de carregamento, erros, paginação e chamadas para a camada de dados.

**Repository:** responsável por abstrair as operações de dados. A controller não precisa saber exatamente se os dados vêm do SQLite ou do Supabase.

**Datasource:** responsável por falar diretamente com a fonte de dados concreta, como SQLite ou Supabase.

Essa separação é importante porque evita que a tela fique presa a uma tecnologia específica.

Antes, com SQLite, o fluxo era:

```text
TutorListPage
↓
TutorController
↓
SqliteTutorRepository
↓
TutorLocalDataSource
↓
SQLite
```

Depois, com Supabase, o fluxo passa a ser:

```text
TutorListPage
↓
TutorController
↓
SupabaseTutorRepository
↓
TutorRemoteDataSource
↓
Supabase
```

O ponto mais importante é que **TutorListPage** e **TutorController** podem continuar praticamente iguais. A principal mudança acontece na camada de dados.

Isso é possível porque o repository funciona como um contrato. A controller solicita operações como listar, cadastrar, editar ou remover tutores, mas não precisa conhecer os detalhes internos da tecnologia usada para executar essas operações.

---

# 7. Repository como contrato entre a aplicação e os dados

O repository é uma camada essencial para reduzir acoplamento.

Quando a controller depende diretamente de uma implementação específica, como `SqliteTutorRepository`, a aplicação fica muito presa ao SQLite. Se for necessário trocar para Supabase, várias partes do código podem precisar ser alteradas.

Quando a controller depende de um contrato, como uma abstração `TutorRepository`, fica mais fácil trocar a implementação concreta.

Podem existir duas implementações diferentes:

```text
TutorRepository
├── SqliteTutorRepository
└── SupabaseTutorRepository
```

A primeira usa dados locais no dispositivo. A segunda usa dados remotos no Supabase.

O comportamento esperado continua sendo o mesmo: cadastrar tutor, listar tutores, editar tutor, remover tutor e buscar por identificador. O que muda é o caminho percorrido para acessar os dados.

Essa ideia é muito importante em arquitetura de software: **a regra de uso da aplicação deve depender de contratos, não diretamente de detalhes técnicos**.

---

# 8. O que muda ao sair de uma base local para uma base remota

Quando usamos SQLite, as operações acontecem dentro do próprio dispositivo. Isso geralmente torna as respostas rápidas e elimina a dependência de internet.

Quando usamos Supabase, as operações passam pela rede. Isso muda a forma como a aplicação deve lidar com tempo de resposta, falhas e estados da interface.

## Latência de rede

Latência é o tempo entre o aplicativo enviar uma solicitação e receber uma resposta.

Com SQLite, listar tutores costuma ser quase imediato, pois os dados estão no próprio aparelho. Com Supabase, o aplicativo precisa enviar uma requisição pela internet, aguardar o servidor processar e receber a resposta.

Se a internet estiver lenta, a listagem pode demorar. Por isso, a interface precisa mostrar estados de carregamento.

## Falhas e erros

Em uma base remota, uma operação pode falhar por vários motivos: falta de internet, servidor indisponível, erro de permissão, dados inválidos ou resposta inesperada.

Por exemplo, o usuário pode tentar cadastrar um tutor, mas a conexão cair antes da operação ser concluída. A aplicação precisa informar o erro de forma clara e evitar comportamentos confusos, como duplicar cadastros ou deixar a tela em carregamento infinito.

## Estados de carregamento

Com Supabase, a interface precisa representar corretamente o estado da operação.

A tela pode estar:

```text
carregando dados
exibindo uma lista com tutores
exibindo lista vazia
exibindo mensagem de erro
salvando um novo tutor
atualizando um tutor existente
```

Esses estados ajudam o usuário a entender o que está acontecendo. Sem eles, a aplicação pode parecer travada ou instável.

## Sincronização

Quando o projeto usa apenas Supabase, os dados principais estão na base remota. Quando usa SQLite e Supabase juntos, surge uma questão mais complexa: os dados locais e remotos precisam ser sincronizados.

Por exemplo, um tutor pode ter sido editado offline no celular, enquanto outro dispositivo também alterou o mesmo cadastro no servidor. Decidir qual versão deve prevalecer exige regras específicas.

Esse tema é mais avançado e será tratado depois, mas é importante compreender que misturar base local e remota exige cuidado.

# 9. Supabase como backend pronto e API automática

Em uma aplicação tradicional, seria necessário criar um backend próprio para intermediar a comunicação entre o app Flutter e o banco de dados.

Esse backend normalmente teria responsabilidades como:

| Responsabilidade            | O que significa                                                    |
| --------------------------- | ------------------------------------------------------------------ |
| Receber requisições         | O aplicativo envia pedidos como cadastrar, listar ou editar dados. |
| Validar dados               | O backend verifica se os dados recebidos fazem sentido.            |
| Consultar e salvar no banco | O backend executa operações no banco de dados.                     |
| Retornar respostas          | O backend devolve sucesso, erro ou dados solicitados.              |
| Controlar permissões        | O backend define quem pode acessar, alterar ou remover dados.      |

O Supabase simplifica parte desse processo. Quando uma tabela é criada no Supabase, a plataforma disponibiliza formas de acessá-la sem que você precise escrever manualmente todos os endpoints.

Na tabela de tutores, por exemplo, o Flutter poderá:

```text
inserir um tutor
buscar todos os tutores
buscar um tutor específico
atualizar um tutor
remover ou marcar um tutor como removido
```

Essas operações podem ser feitas usando a biblioteca oficial do Supabase para Flutter.

Isso não significa que a organização do projeto deixa de importar. Mesmo usando Supabase, ainda é necessário pensar em arquitetura, separação de camadas, tratamento de erros, segurança das chaves, validação de dados e regras de acesso.

# 10. Cuidados com chaves e segurança

Para conectar um aplicativo Flutter ao Supabase, normalmente são necessárias informações como a URL do projeto e uma chave pública adequada para uso no cliente.

É importante entender a diferença entre uma chave pública de cliente e uma chave secreta ou administrativa.

A aplicação Flutter é distribuída para os usuários. Isso significa que qualquer informação embutida no aplicativo deve ser tratada como potencialmente exposta. Por isso, **chaves secretas ou administrativas não devem ser colocadas dentro do aplicativo Flutter**.

Uma chave administrativa pode conceder permissões muito amplas. Se ela for exposta, alguém poderia acessar ou alterar dados indevidamente.

Neste primeiro momento, o foco é compreender a configuração básica para aprendizado. Temas como autenticação, permissões detalhadas e regras de acesso devem ser tratados com mais profundidade em etapas posteriores.

A regra prática é:

```text
Use no Flutter apenas informações apropriadas para o cliente.
Nunca coloque chaves secretas ou administrativas dentro do aplicativo.
Configure permissões e regras de acesso de acordo com a necessidade do projeto.
```

# 11. Os três caminhos possíveis para armazenamento de dados

Ao evoluir um projeto Flutter, existem três caminhos principais para lidar com persistência de dados.

## Apenas SQLite

Nesse caminho, os dados ficam somente no dispositivo.

É adequado quando a aplicação precisa funcionar offline, quando os dados pertencem apenas ao usuário local ou quando não há necessidade de compartilhar informações entre dispositivos.

No projeto Pet Care, esse foi o caminho usado inicialmente.

## Apenas Supabase

Nesse caminho, o Supabase passa a ser a fonte principal dos dados.

É adequado quando vários dispositivos precisam acessar a mesma informação, quando existe necessidade de centralização e quando o sistema começa a exigir recursos como autenticação, permissões e acesso remoto.

No próximo passo da feature Tutor, esse será o caminho explorado.

## SQLite e Supabase juntos

Nesse caminho, a aplicação usa uma base local e uma base remota ao mesmo tempo.

Isso pode ser útil para permitir funcionamento offline e sincronização posterior. Porém, é o modelo mais complexo, pois exige regras para decidir como os dados locais e remotos serão conciliados.

Por exemplo, se o usuário alterar um tutor sem internet e depois outro dispositivo alterar o mesmo tutor no Supabase, o sistema precisa ter uma estratégia para resolver o conflito.

# 12. Exemplo comentado: leitura da arquitetura antes e depois

Considere que a controller da feature Tutor precise listar todos os tutores.

Com SQLite, ela poderia chamar um repository que busca dados localmente:

```text
Controller solicita: listar tutores
Repository usado: SqliteTutorRepository
Datasource usado: TutorLocalDataSource

```

Nesse caso, a operação acontece dentro do dispositivo. O aplicativo não depende da internet.

Com Supabase, a mesma intenção continua existindo:

```text
Controller solicita: listar tutores
Repository usado: SupabaseTutorRepository
Datasource usado: TutorRemoteDataSource
Fonte final: Supabase
```

A controller continua pedindo a mesma coisa: listar tutores. O que muda é a implementação concreta que executa a operação.

Esse exemplo mostra por que a separação em camadas é importante. Se a tela e a controller estivessem diretamente acopladas ao SQLite, a migração para Supabase exigiria alterações em várias partes da aplicação.

Com repository e datasource bem definidos, a mudança fica concentrada na camada de dados.

# 13. Aplicação prática resolvida: planejando a evolução da feature Tutor para Supabase

## Cenário

A feature Tutor do projeto Pet Care já possui CRUD funcionando com SQLite. Agora, o sistema precisa permitir que os dados de tutores fiquem em uma base remota, acessível por diferentes dispositivos.

## Objetivo

Planejar a evolução da feature sem quebrar a arquitetura já existente.

## Solução guiada

O primeiro passo é manter as camadas de tela e controller. Elas não devem ser reescritas sem necessidade, porque a responsabilidade delas não é saber se os dados vêm do SQLite ou do Supabase.

O segundo passo é criar uma tabela `tutors` no Supabase com os campos necessários, como `tutor_id`, `nome`, `email`, `telefone`, `created_at`, `updated_at` e `deleted_at`.

O terceiro passo é adaptar o model `Tutor` para conseguir converter dados entre o formato usado no Flutter e o formato esperado pelo Supabase. Isso envolve serialização e desserialização.

O quarto passo é criar um datasource remoto, como `TutorRemoteDataSource`, responsável por conversar diretamente com o Supabase.

O quinto passo é criar um repository remoto, como `SupabaseTutorRepository`, responsável por implementar as operações esperadas pela controller usando o datasource remoto.

O sexto passo é testar as operações principais: cadastrar, listar, editar, buscar e remover tutores.

## Comentário da solução

A solução respeita a arquitetura existente porque não coloca chamadas ao Supabase diretamente na tela. Isso evita acoplamento e mantém o código mais organizado.

A tela continua exibindo dados e reagindo a estados. A controller continua coordenando ações. O repository continua representando as operações da feature. O datasource assume o trabalho técnico de acessar a fonte de dados.

## Resultado esperado

Ao final dessa evolução, a feature Tutor deve conseguir usar Supabase como fonte de dados remota. A listagem de tutores deve buscar dados do servidor, e os formulários devem salvar ou atualizar registros na tabela remota.

## Como validar

A validação pode ser feita observando se:

A aplicação consegue listar tutores vindos do Supabase.

Um tutor cadastrado pelo app aparece na tabela remota.

Uma edição feita pelo app atualiza o registro correspondente no Supabase.

Uma remoção ou marcação de remoção altera corretamente o campo esperado.

A tela exibe carregamento enquanto espera a resposta da rede.

A tela exibe mensagem adequada quando ocorre erro.

## Possíveis erros

Um erro comum é colocar chamadas ao Supabase diretamente na tela. Isso dificulta manutenção e testes.

Outro erro é ignorar estados de carregamento. Como a rede pode demorar, o usuário precisa receber feedback visual.

Também é comum esquecer de tratar falhas. Operações remotas podem falhar, e a aplicação precisa lidar com isso de forma previsível.

Um erro grave é colocar chaves secretas no aplicativo Flutter. Apenas informações apropriadas para uso no cliente devem ser configuradas no app.

# 14. Erros comuns e dúvidas frequentes

## “Supabase substitui completamente o SQLite?”

Não necessariamente. Supabase e SQLite resolvem problemas diferentes. SQLite é adequado para dados locais. Supabase é adequado para dados remotos e centralizados. Dependendo do projeto, é possível usar apenas um deles ou os dois em conjunto.

## “Por que não acessar o Supabase direto pela tela?”

Porque isso mistura responsabilidades. A tela deve cuidar da interface. A comunicação com a fonte de dados deve ficar em camadas apropriadas, como repository e datasource. Essa separação facilita manutenção, testes e futuras trocas de tecnologia.

## “Por que preciso tratar carregamento se antes com SQLite era rápido?”

Porque Supabase depende de rede. A resposta pode demorar, falhar ou variar conforme a conexão. Sem estados de carregamento, o usuário pode pensar que a aplicação travou.

## “O que acontece se a internet cair durante o cadastro?”

A operação pode falhar ou ficar incompleta. A aplicação precisa capturar o erro, informar o usuário e evitar que a interface fique em um estado inconsistente.

## “Posso colocar qualquer chave do Supabase no Flutter?”

Não. Chaves secretas ou administrativas não devem ser colocadas no app. Aplicativos Flutter podem ser distribuídos e analisados por terceiros. Informações sensíveis precisam ser protegidas.

## “Por que a feature Tutor foi escolhida?”

Porque ela já possui CRUD e estrutura em camadas. Isso permite aprender a trocar a fonte de dados sem precisar reconstruir a aplicação inteira.

# 15. Checklist explicado de compreensão e implementação

## Verifique se você compreende a diferença entre base local e base remota

O que verificar: confirme se você sabe explicar que SQLite armazena dados no dispositivo, enquanto Supabase armazena dados em um servidor remoto.

Por que importa: sem essa diferença, é fácil pensar que Supabase é apenas “outro banco”, quando na verdade ele muda o modo como o aplicativo acessa e compartilha dados.

Como validar: tente responder à pergunta: “por que dois celulares diferentes não enxergam automaticamente os mesmos dados quando uso apenas SQLite?”

O que acontece se faltar: você pode escolher a tecnologia errada para o problema ou esperar do SQLite um comportamento que ele não oferece sozinho.

## Verifique se a arquitetura em camadas foi preservada

O que verificar: confirme se a tela e a controller não estão chamando o Supabase diretamente.

Por que importa: quando a tela depende diretamente de uma tecnologia, o projeto fica mais difícil de manter e evoluir.

Como validar: observe se a comunicação com Supabase está concentrada em datasource e repository.

O que acontece se faltar: uma futura troca de tecnologia exigirá mudanças espalhadas por várias partes da aplicação.

## Verifique se o repository funciona como contrato

O que verificar: confirme se a controller depende de uma abstração de repository, e não de uma implementação específica sempre que possível.

Por que importa: isso permite alternar entre `SqliteTutorRepository` e `SupabaseTutorRepository` com menos impacto.

Como validar: analise se as operações esperadas continuam as mesmas: cadastrar, listar, editar, buscar e remover tutores.

O que acontece se faltar: a controller ficará acoplada ao SQLite ou ao Supabase, dificultando testes e mudanças.

## Verifique se a tabela remota representa corretamente os dados do tutor

O que verificar: confirme se a tabela `tutors` possui campos suficientes para representar os dados usados pela aplicação, como identificador, nome, e-mail, telefone e datas de controle.

Por que importa: uma tabela mal planejada causa problemas na hora de salvar, editar, buscar ou remover registros.

Como validar: compare os campos do model `Tutor` com os campos da tabela no Supabase.

O que acontece se faltar: podem surgir erros de serialização, campos ausentes, dados inconsistentes ou falhas nas operações CRUD.

## Verifique se há tratamento de carregamento e erro

O que verificar: confirme se a interface mostra quando uma operação está carregando e quando ocorre falha.

Por que importa: operações remotas dependem de rede e podem demorar ou falhar.

Como validar: teste a aplicação com internet lenta, sem internet ou com uma configuração incorreta.

O que acontece se faltar: o usuário pode não entender o que está acontecendo e a aplicação pode parecer travada.

## Verifique se as chaves estão sendo usadas com segurança

O que verificar: confirme se nenhuma chave secreta ou administrativa foi colocada dentro do aplicativo Flutter.

Por que importa: aplicativos distribuídos ao usuário não devem conter segredos administrativos.

Como validar: revise os arquivos de configuração e procure credenciais sensíveis.

O que acontece se faltar: pessoas não autorizadas podem obter acesso indevido a dados ou permissões do projeto.

# 16. Síntese final

O Supabase permite que um projeto Flutter evolua de uma base local para uma base remota. No projeto Pet Care, essa evolução será aplicada inicialmente à feature Tutor, que já possui operações de CRUD e uma arquitetura organizada em camadas.

O SQLite continua sendo útil para persistência local, mas não resolve sozinho o problema de compartilhamento entre dispositivos. O Supabase, por sua vez, permite centralizar os dados em uma base PostgreSQL remota, acessível pela internet.

A principal mudança acontece na camada de dados. A tela e a controller podem permanecer preservadas, enquanto novas implementações de repository e datasource passam a acessar o Supabase.

Essa abordagem permite aprender Supabase sem abandonar a organização já construída no projeto. O objetivo não é destruir a arquitetura existente, mas evoluí-la.

# Conclusão

Usar Supabase em um projeto Flutter é uma decisão importante quando a aplicação precisa centralizar dados, permitir acesso por múltiplos dispositivos e se preparar para recursos mais avançados, como autenticação, permissões e integração com outros sistemas.

No caso da feature Tutor, o Supabase será introduzido como uma nova fonte de dados remota. A estrutura em camadas continuará sendo essencial para manter o projeto organizado, testável e preparado para mudanças futuras.

O aprendizado central deste material é que a evolução de uma aplicação não deve acontecer de forma improvisada. Ao migrar de SQLite para Supabase, é necessário compreender o papel de cada camada, tratar estados de rede, proteger chaves sensíveis e manter a separação entre interface, regra de uso e acesso aos dados.
