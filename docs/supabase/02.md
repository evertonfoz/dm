# Preparando a Feature Tutor para Trabalhar com Base Remota

## Objetivo do material

Neste material, você aprenderá como a feature de Tutor do projeto Pet Care está organizada para permitir uma evolução futura de uma base local com SQLite para uma base remota com Supabase. O foco não é criar a tabela no Supabase, conectar o Flutter ao serviço remoto ou reescrever a interface. O objetivo é compreender a arquitetura atual, identificar os pontos que já estão bem preparados e entender quais partes deverão ser adicionadas quando a aplicação passar a trabalhar com dados remotos. 

Ao final, você deverá ser capaz de explicar por que a tela não deve acessar o Supabase diretamente, qual é o papel da controller, qual é o papel do repository, qual é o papel do datasource e por que depender de abstrações facilita a troca da origem dos dados.

---

# 1. Contextualização do problema

Em uma aplicação Flutter, é comum começar salvando dados localmente, por exemplo com SQLite. Essa abordagem é útil para desenvolver a feature, testar cadastros, validar telas e organizar a lógica inicial da aplicação.

No projeto Pet Care, a feature Tutor atualmente trabalha com uma base local. Isso significa que os dados dos tutores são armazenados no próprio dispositivo ou em uma estrutura local controlada pelo aplicativo.

Em uma etapa futura, a aplicação passará a usar uma base remota com Supabase. Nesse cenário, os dados deixam de estar apenas no armazenamento local e passam a ser enviados, buscados, atualizados e removidos em um serviço externo, acessado pela rede.

Essa mudança poderia causar muitos problemas se o código estivesse mal organizado. Por exemplo, se a tela de listagem chamasse diretamente comandos do SQLite, seria necessário reescrever a tela quando o Supabase fosse adicionado. Se o formulário conhecesse detalhes do banco local, ele também precisaria ser alterado. Se a controller dependesse de uma classe concreta do SQLite, a troca para o Supabase ficaria mais difícil.

A boa notícia é que a feature Tutor já está organizada em camadas. Essa separação permite que a aplicação evolua sem reescrever toda a interface. A ideia principal é:

```text
Page → Controller → Repository → DataSource → Tecnologia
```

A tela conversa com a controller.
A controller usa um repository.
O repository decide como acessar os dados.
O datasource conversa com uma fonte de dados específica.
A tecnologia concreta pode ser SQLite hoje e Supabase no futuro.

Essa organização reduz acoplamento, facilita manutenção e permite trocar a origem dos dados sem destruir a estrutura existente.

# 2. Estrutura atual da feature Tutor

A feature Tutor está organizada em três camadas principais: `domain`, `data` e `presentation`.

## 2.1 Camada `domain`

A camada `domain` contém elementos próximos da regra de negócio e do conceito principal da feature. No caso da feature Tutor, ela contém:

```text
domain/
  models/
    tutor.dart

  repositories/
    tutor_repository.dart
```

O arquivo `tutor.dart` representa o modelo Tutor. Ele descreve quais dados formam um tutor dentro da aplicação.

O arquivo `tutor_repository.dart` define o contrato de operações que a feature precisa realizar com tutores, como inserir, listar, buscar por identificador, atualizar e remover.

Essa camada não deve depender diretamente de SQLite ou Supabase. Ela representa o núcleo conceitual da feature.

## 2.2 Camada `data`

A camada `data` contém implementações relacionadas à origem dos dados. Atualmente, ela possui uma estrutura voltada para SQLite:

```text
data/
  datasources/
    tutor_local_datasource.dart

  repositories/
    sqlite_tutor_repository.dart
```

O datasource local concentra o acesso ao armazenamento local. O repository SQLite implementa o contrato esperado pela aplicação usando esse datasource local.

Essa separação é importante porque impede que comandos de banco de dados fiquem espalhados pela tela, pela controller ou por widgets.

## 2.3 Camada `presentation`

A camada `presentation` contém elementos ligados à interface do usuário e ao controle de estado usado pela tela:

```text
presentation/
  controllers/
    tutor_controller.dart

  pages/
    tutor_list_page.dart
    tutor_form_page.dart

  widgets/
```

As páginas exibem a interface. A controller organiza estado, carregamento, paginação, inserção, atualização, remoção e mensagens de erro. Os widgets representam partes reutilizáveis da interface.

Essa camada não deve conhecer detalhes de SQLite nem de Supabase. Ela deve pedir dados e reagir aos estados da aplicação, sem controlar diretamente a tecnologia de persistência.

# 3. O model Tutor

A classe `Tutor` representa o conceito de tutor dentro da aplicação. Ela não representa apenas uma linha do SQLite. Ela representa uma entidade da feature.

```dart
class Tutor {
  final int? tutorId;
  final String nome;
  final String email;
  final String telefone;
  final DateTime createdAt;
  final DateTime updatedAt;
  final DateTime? deletedAt;

  Tutor({
    this.tutorId,
    required this.nome,
    required this.email,
    required this.telefone,
    required this.createdAt,
    required this.updatedAt,
    this.deletedAt,
  });
}
```

O campo `tutorId` é opcional porque, em muitos fluxos de cadastro, o identificador pode ser gerado pelo banco de dados somente depois da inserção. Antes de salvar, o objeto pode ainda não ter um identificador definitivo.

Os campos `nome`, `email` e `telefone` representam os dados principais do tutor. Eles são obrigatórios porque caracterizam o cadastro.

Os campos `createdAt`, `updatedAt` e `deletedAt` representam datas de controle. `createdAt` indica quando o registro foi criado. `updatedAt` indica quando foi atualizado pela última vez. `deletedAt` pode indicar uma remoção lógica, quando o dado deixa de aparecer como ativo, mas não necessariamente é apagado fisicamente da base.

Esse model continuará fazendo sentido mesmo quando a aplicação passar a usar Supabase. A tecnologia de armazenamento pode mudar, mas o conceito de tutor permanece. A aplicação continuará lidando com tutores que possuem nome, e-mail, telefone e datas de controle.

# 4. O papel do Repository

A feature Tutor possui um contrato chamado `TutorRepository`. Esse contrato define quais operações a feature precisa realizar, sem dizer qual tecnologia será usada para salvar ou buscar os dados.

```dart
abstract class TutorRepository {
  Future<int> insertTutor(Tutor tutor);

  Future<List<Tutor>> getAllTutors({
    int limit = 20,
    int offset = 0,
  });

  Future<Tutor?> getTutorById(int id);

  Future<int> updateTutor(Tutor tutor);

  Future<int> deleteTutor(int id);
}
```

Esse contrato não fala em SQLite. Também não fala em Supabase. Ele fala apenas sobre o que a feature Tutor precisa conseguir fazer.

As operações principais são:

| Operação       | O que faz                               | Por que importa                                        |
| -------------- | --------------------------------------- | ------------------------------------------------------ |
| `insertTutor`  | Insere um novo tutor                    | Permite cadastrar novos tutores na aplicação           |
| `getAllTutors` | Lista tutores com limite e deslocamento | Permite exibir registros em tela com paginação         |
| `getTutorById` | Busca um tutor específico               | Permite abrir detalhes ou editar um cadastro existente |
| `updateTutor`  | Atualiza os dados de um tutor           | Permite corrigir ou modificar informações              |
| `deleteTutor`  | Remove um tutor                         | Permite excluir ou desativar um registro               |

O ponto central é que a controller pode usar esse contrato sem saber se os dados estão vindo do SQLite, do Supabase ou de outra fonte. Isso é uma forma de depender de abstração, não de implementação concreta.

# 5. Implementação atual com SQLite

Atualmente, a feature possui uma implementação concreta chamada `SqliteTutorRepository`. Ela implementa o contrato `TutorRepository` e usa um datasource local para executar as operações.

```dart
class SqliteTutorRepository implements TutorRepository {
  final TutorLocalDataSource _localDataSource;

  SqliteTutorRepository({TutorLocalDataSource? localDataSource})
      : _localDataSource = localDataSource ?? SqliteTutorLocalDataSource();

  @override
  Future<int> insertTutor(Tutor tutor) {
    return _localDataSource.insert(tutor);
  }

  @override
  Future<List<Tutor>> getAllTutors({int limit = 20, int offset = 0}) {
    return _localDataSource.getAll(limit: limit, offset: offset);
  }

  @override
  Future<Tutor?> getTutorById(int id) {
    return _localDataSource.getById(id);
  }

  @override
  Future<int> updateTutor(Tutor tutor) {
    return _localDataSource.update(tutor);
  }

  @override
  Future<int> deleteTutor(int id) {
    return _localDataSource.delete(id);
  }
}
```

Esse código tem uma característica importante: ele adapta as operações esperadas pela feature para chamadas feitas ao datasource local.

Quando a controller chama `insertTutor`, ela não precisa saber como o SQLite insere dados. Ela apenas chama o método definido no contrato. O repository recebe essa chamada e encaminha para `_localDataSource.insert(tutor)`.

O mesmo ocorre com listagem, busca por identificador, atualização e remoção. O repository funciona como uma ponte entre a necessidade da aplicação e a origem concreta dos dados.

No futuro, será possível criar uma classe `SupabaseTutorRepository` também implementando `TutorRepository`. A controller continuará chamando os mesmos métodos, mas a execução será feita por uma implementação remota.

# 6. Evolução da arquitetura: do local para o remoto

A principal mudança para trabalhar com Supabase deverá acontecer na camada de dados. A tela e a controller não devem ser reconstruídas do zero.

O cenário atual pode ser entendido assim:

```text
TutorController
  → SqliteTutorRepository
    → TutorLocalDataSource
      → SQLite
```

O cenário futuro com Supabase poderá ser entendido assim:

```text
TutorController
  → SupabaseTutorRepository
    → TutorRemoteDataSource
      → Supabase
```

A controller continua no mesmo lugar. A tela continua conversando com a controller. O contrato `TutorRepository` continua servindo como ponto de contato entre a controller e a camada de dados.

A troca ocorre porque a controller depende de `TutorRepository`, e não diretamente de `SqliteTutorRepository`.

Essa é uma decisão arquitetural importante. Quando uma classe depende de um contrato, ela fica mais flexível. Quando depende de uma implementação concreta, ela fica presa àquela tecnologia.

---

# 7. O papel do DataSource

O datasource é a classe que conversa com uma fonte de dados específica. No caso atual, o datasource local conversa com SQLite.

Um contrato local pode ser representado assim:

```dart
abstract class TutorLocalDataSource {
  Future insert(Tutor tutor);

  Future<List<Tutor>> getAll({
    int limit = 20,
    int offset = 0,
  });

  Future<Tutor?> getById(int id);

  Future update(Tutor tutor);

  Future delete(int id);
}
```

O datasource não tem o mesmo papel do repository.

O datasource sabe lidar com uma fonte específica. Por exemplo, o datasource local sabe como falar com SQLite. No futuro, o datasource remoto saberá como falar com Supabase.

O repository representa a implementação da regra de acesso a dados esperada pela aplicação. Ele pode usar um datasource local, um datasource remoto ou, em uma etapa mais avançada, combinar os dois.

Essa diferença evita confusão:

| Elemento   | Papel principal                                              | Exemplo                                               |
| ---------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| DataSource | Conversa com uma fonte de dados específica                   | SQLite ou Supabase                                    |
| Repository | Entrega para a aplicação as operações esperadas pela feature | Inserir, listar, buscar, atualizar e remover tutores  |
| Controller | Controla estado e aciona operações da feature                | Carregamento, paginação, erro, inserção e atualização |
| Page       | Exibe a interface e responde às interações do usuário        | Lista de tutores e formulário de tutor                |

---

# 8. Estrutura futura de pastas

Para adicionar Supabase sem apagar a estrutura local, a camada `data` poderá evoluir para algo como:

```text
data/
  datasources/
    tutor_local_datasource.dart
    tutor_remote_datasource.dart

  repositories/
    sqlite_tutor_repository.dart
    supabase_tutor_repository.dart
```

Essa organização permite que a feature tenha uma origem local e uma origem remota, cada uma com sua responsabilidade.

O arquivo `tutor_local_datasource.dart` continua representando o contrato ou implementação relacionada ao acesso local.

O arquivo `tutor_remote_datasource.dart` passa a concentrar as operações específicas de acesso remoto.

O arquivo `sqlite_tutor_repository.dart` mantém a implementação baseada em SQLite.

O arquivo `supabase_tutor_repository.dart` adiciona uma implementação baseada em Supabase, respeitando o mesmo contrato `TutorRepository`.

Essa evolução é progressiva. Em vez de destruir a implementação anterior, a aplicação ganha uma nova possibilidade de persistência.

---

# 9. O que não devemos fazer

Ao adicionar Supabase, pode parecer mais simples chamar o serviço remoto diretamente dentro da tela de listagem ou do formulário. Esse caminho pode funcionar em um teste inicial, mas prejudica a organização do projeto.

A abordagem incorreta seria:

```text
TutorListPage → Supabase
TutorFormPage → Supabase
```

Nesse caso, a tela passaria a acumular responsabilidades demais. Ela deixaria de apenas exibir interface e passaria também a buscar dados, tratar banco remoto, interpretar resposta de rede e lidar com erros técnicos.

A abordagem correta é:

```text
Page → Controller → Repository → DataSource → Tecnologia
```

A tela deve exibir dados e acionar ações do usuário. A controller deve controlar estado e chamar operações do repository. O repository deve implementar a regra de acesso a dados. O datasource deve conversar com a tecnologia concreta.

Quando a tela chama Supabase diretamente, surgem problemas práticos:

A interface fica acoplada à tecnologia de banco. Se a origem dos dados mudar, a tela precisa mudar.

O tratamento de erros técnicos fica misturado com código visual. Isso dificulta manutenção e testes.

A reutilização da lógica fica menor. Outras telas ou fluxos não conseguem reaproveitar facilmente as mesmas operações.

A evolução para sincronização local e remota fica mais difícil. Se o acesso aos dados estiver espalhado, combinar SQLite e Supabase no futuro se torna mais trabalhoso.

# 10. A controller atual e a injeção de dependência

A `TutorController` já depende de um `TutorRepository`. Esse é um ponto positivo, porque ela recebe o repository no construtor.

```dart
class TutorController extends ChangeNotifier {
  final TutorRepository _repository;

  TutorController({TutorRepository? repository})
      : _repository = repository ?? SqliteTutorRepository();

  final List<Tutor> _tutors = [];
  bool _isLoading = false;
  bool _isPaginating = false;
  bool _isInserting = false;
  bool _isUpdating = false;
  bool _isDeleting = false;
  String? _errorMessage;

  int _limit = 7;
  int _offset = 0;
  bool _hasMoreData = true;
}
```

O trecho mais importante é:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SqliteTutorRepository();
```

Isso significa que a controller pode receber uma implementação externa. Se nenhuma implementação for enviada, ela usa `SqliteTutorRepository` como padrão.

Hoje, o uso padrão é:

```dart
TutorController()
```

Nesse caso, a controller cria ou usa internamente o repository SQLite.

No futuro, será possível fazer algo como:

```dart
final controller = TutorController(
  repository: SupabaseTutorRepository(),
);
```

A controller continuará chamando os mesmos métodos:

```dart
_repository.getAllTutors();
_repository.insertTutor(tutor);
_repository.updateTutor(tutor);
_repository.deleteTutor(id);
```

Quem muda é a implementação que executa essas operações. Antes, quem executava era o repository local. Depois, poderá ser o repository remoto.

Esse mecanismo é uma forma simples de injeção de dependência. A controller não cria obrigatoriamente uma dependência fixa. Ela aceita receber uma dependência externa, desde que essa dependência respeite o contrato `TutorRepository`.

# 11. Diferença entre Repository e DataSource

É comum confundir repository e datasource, porque ambos ficam na camada de dados. Porém, eles não têm a mesma responsabilidade.

O datasource é mais próximo da tecnologia. Ele sabe como executar operações em uma fonte de dados específica. Um datasource local conhece detalhes do SQLite. Um datasource remoto conhecerá detalhes do Supabase.

O repository é mais próximo da aplicação. Ele entrega as operações que a feature precisa, usando um ou mais datasources por baixo.

Na implementação atual, a relação é:

```text
SqliteTutorRepository → TutorLocalDataSource → SQLite
```

Na implementação futura, a relação poderá ser:

```text
SupabaseTutorRepository → TutorRemoteDataSource → Supabase
```

Em uma etapa mais avançada, uma implementação de sincronização poderia ser:

```text
SyncTutorRepository → LocalDataSource + RemoteDataSource
```

Nesse caso, o repository poderia decidir quando buscar dados locais, quando enviar dados ao remoto, quando atualizar cache e como lidar com conflitos. Essa etapa é mais complexa e não precisa ser implementada agora, mas a arquitetura atual já prepara o caminho.

# 12. O que muda e o que permanece

Ao migrar ou evoluir a feature Tutor para Supabase, nem tudo precisa mudar.

## O que permanece

A classe `Tutor` permanece, porque o conceito da entidade continua o mesmo.

O contrato `TutorRepository` permanece, porque as operações da feature continuam sendo inserir, listar, buscar, atualizar e remover.

A `TutorController` permanece, porque ela já depende da abstração `TutorRepository`.

As páginas `TutorListPage` e `TutorFormPage` permanecem, porque a interface não deve conversar diretamente com o banco.

A lógica de cadastro, edição, remoção e listagem permanece em termos gerais, porque o comportamento da feature continua o mesmo.

Os estados de carregamento, erro e paginação permanecem, porque a tela continuará precisando representar esses estados para o usuário.

## O que será adicionado

Será adicionada uma fonte de dados remota.

Será adicionado um repository remoto.

Serão necessários métodos de conversão para o formato esperado pelo Supabase.

Será necessária a configuração de conexão com o Supabase.

Será necessário um tratamento mais cuidadoso para erros de rede.

## O que poderá mudar pontualmente

A implementação padrão usada pela controller poderá mudar.

A forma de mapear os campos do banco poderá mudar.

A forma de paginar dados poderá mudar conforme a estratégia usada no Supabase.

O tempo de resposta das operações poderá mudar, pois operações remotas dependem de rede.

As mensagens de erro exibidas ao usuário poderão precisar de ajustes para diferenciar erro de validação, erro de conexão e erro de serviço remoto.

# 13. Por que não remover o SQLite agora

Neste momento, não é necessário apagar o código do SQLite. Manter a implementação local tem valor didático, técnico e estratégico.

Do ponto de vista didático, o SQLite permite comparar duas abordagens lado a lado: uma implementação local e uma implementação remota. Essa comparação ajuda a entender melhor o papel das camadas.

Do ponto de vista técnico, a implementação local continua sendo uma referência de funcionamento. Ela mostra como a feature já salva, lista, atualiza e remove tutores.

Do ponto de vista estratégico, o SQLite poderá ser usado novamente quando o projeto discutir sincronização entre dados locais e remotos. Uma aplicação pode, por exemplo, salvar localmente quando estiver sem internet e sincronizar depois com a base remota.

A melhor estratégia é adicionar uma nova possibilidade de persistência, não destruir a implementação anterior sem necessidade.

---

# 14. Cuidados antes da implementação remota

Antes de escrever o código do Supabase, alguns cuidados precisam estar claros.

A tela não deve chamar Supabase diretamente. Toda comunicação com fontes de dados deve passar pelas camadas corretas, porque isso mantém a interface isolada da tecnologia de persistência.

A controller deve continuar trabalhando com `TutorRepository`. O contrato abstrato é o ponto de contato entre a controller e os dados. Se a controller passar a conhecer Supabase diretamente, a arquitetura perde flexibilidade.

O Supabase deve entrar na camada `data`. O datasource remoto e o repository remoto pertencem a essa camada, porque estão relacionados à origem dos dados.

A implementação local não precisa ser apagada. SQLite e Supabase podem coexistir no projeto, cada um representado por sua própria implementação.

A troca da origem dos dados deve ser controlada por injeção de dependência. Isso permite escolher qual repository será usado sem alterar a lógica interna da controller.

Erros de rede exigem mais atenção. Diferentemente de erros locais, operações remotas podem falhar por falta de conexão, instabilidade, timeout, indisponibilidade do serviço ou problemas de permissão.

# 15. Preparação conceitual: mapeamento de campos

A próxima etapa da evolução será criar a tabela de tutores no Supabase. Para isso, é necessário comparar os campos da classe `Tutor` com os campos que existirão no banco remoto.

No Flutter, usando Dart, é comum utilizar a convenção `camelCase`:

```text
tutorId
nome
email
telefone
createdAt
updatedAt
deletedAt
```

No Supabase, que usa PostgreSQL, é comum utilizar a convenção `snake_case`:

```text
tutor_id
nome
email
telefone
created_at
updated_at
deleted_at
```

Essa diferença de nomes não é um problema, desde que o model saiba converter os dados corretamente.

No SQLite, o projeto já usa métodos como `toMap()` e `fromMap()`. Para o Supabase, poderão ser criados métodos específicos, como:

```dart
Map<String, dynamic> toSupabaseMap() {
  return {
    'tutor_id': tutorId,
    'nome': nome,
    'email': email,
    'telefone': telefone,
    'created_at': createdAt.toIso8601String(),
    'updated_at': updatedAt.toIso8601String(),
    'deleted_at': deletedAt?.toIso8601String(),
  };
}
```

Esse método transforma um objeto `Tutor` em um mapa compatível com os nomes de campos esperados no Supabase.

Também será necessário converter os dados vindos do Supabase para um objeto `Tutor`:

```dart
factory Tutor.fromSupabaseMap(Map<String, dynamic> map) {
  return Tutor(
    tutorId: map['tutor_id'] as int?,
    nome: map['nome'] as String,
    email: map['email'] as String,
    telefone: map['telefone'] as String,
    createdAt: DateTime.parse(map['created_at'] as String),
    updatedAt: DateTime.parse(map['updated_at'] as String),
    deletedAt: map['deleted_at'] == null
        ? null
        : DateTime.parse(map['deleted_at'] as String),
  );
}
```

Esse método transforma um registro remoto em uma entidade da aplicação.

O ponto principal é que a diferença entre `camelCase` e `snake_case` deve ficar concentrada no model ou em uma camada de mapeamento apropriada. A tela e a controller não devem se preocupar com o nome das colunas do banco.

# 16. Exemplo comentado: troca de repository sem alterar a controller

Imagine que a controller possui o seguinte código interno para listar tutores:

```dart
Future<void> loadTutors() async {
  _isLoading = true;
  notifyListeners();

  try {
    final result = await _repository.getAllTutors(
      limit: _limit,
      offset: _offset,
    );

    _tutors.clear();
    _tutors.addAll(result);
    _errorMessage = null;
  } catch (error) {
    _errorMessage = 'Não foi possível carregar os tutores.';
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

Esse método não sabe se os dados vêm de SQLite ou Supabase. Ele apenas chama:

```dart
_repository.getAllTutors(...)
```

Se `_repository` for um `SqliteTutorRepository`, a listagem virá do SQLite.

Se `_repository` for um `SupabaseTutorRepository`, a listagem virá do Supabase.

A controller continua responsável por estado de carregamento, tratamento de erro e atualização da interface. A origem dos dados fica escondida atrás do contrato.

Esse é o benefício prático de usar repository com abstração.

# 17. Aplicação prática resolvida: preparando a feature para receber Supabase

## Cenário

A feature Tutor já funciona com SQLite. Agora, a equipe deseja preparar a estrutura para adicionar Supabase em uma próxima etapa, sem quebrar a implementação atual.

## Objetivo

Organizar a camada de dados para permitir uma implementação remota, mantendo a tela e a controller sem dependência direta do Supabase.

## Solução

Primeiro, mantenha o contrato principal da feature:

```dart
abstract class TutorRepository {
  Future<int> insertTutor(Tutor tutor);

  Future<List<Tutor>> getAllTutors({
    int limit = 20,
    int offset = 0,
  });

  Future<Tutor?> getTutorById(int id);

  Future<int> updateTutor(Tutor tutor);

  Future<int> deleteTutor(int id);
}
```

Esse contrato continua sendo o ponto de contato da controller.

Depois, preserve a implementação local existente:

```text
data/
  datasources/
    tutor_local_datasource.dart

  repositories/
    sqlite_tutor_repository.dart
```

Em seguida, prepare a estrutura para a origem remota:

```text
data/
  datasources/
    tutor_remote_datasource.dart

  repositories/
    supabase_tutor_repository.dart
```

O contrato remoto pode começar com as mesmas operações essenciais, adaptadas para a fonte remota:

```dart
abstract class TutorRemoteDataSource {
  Future<int> insert(Tutor tutor);

  Future<List<Tutor>> getAll({
    int limit = 20,
    int offset = 0,
  });

  Future<Tutor?> getById(int id);

  Future<int> update(Tutor tutor);

  Future<int> delete(int id);
}
```

Depois, o repository remoto poderá implementar o contrato usado pela controller:

```dart
class SupabaseTutorRepository implements TutorRepository {
  final TutorRemoteDataSource _remoteDataSource;

  SupabaseTutorRepository({
    required TutorRemoteDataSource remoteDataSource,
  }) : _remoteDataSource = remoteDataSource;

  @override
  Future<int> insertTutor(Tutor tutor) {
    return _remoteDataSource.insert(tutor);
  }

  @override
  Future<List<Tutor>> getAllTutors({int limit = 20, int offset = 0}) {
    return _remoteDataSource.getAll(limit: limit, offset: offset);
  }

  @override
  Future<Tutor?> getTutorById(int id) {
    return _remoteDataSource.getById(id);
  }

  @override
  Future<int> updateTutor(Tutor tutor) {
    return _remoteDataSource.update(tutor);
  }

  @override
  Future<int> deleteTutor(int id) {
    return _remoteDataSource.delete(id);
  }
}
```

## Comentário da solução

A controller não foi alterada. A tela não foi alterada. O contrato `TutorRepository` não foi removido. A implementação local também não foi apagada.

A mudança ficou concentrada na camada `data`, que é o local correto para adicionar novas fontes de dados.

## Resultado esperado

Depois dessa preparação, a aplicação poderá escolher qual implementação usar:

```dart
final localController = TutorController(
  repository: SqliteTutorRepository(),

```

ou futuramente:

```dart
final remoteController = TutorController(
  repository: SupabaseTutorRepository(
    remoteDataSource: SupabaseTutorRemoteDataSource(),

```

A controller continuará chamando os mesmos métodos do contrato.

## Como validar

A validação conceitual é verificar se nenhuma página chama Supabase diretamente. A validação arquitetural é confirmar se a controller depende de `TutorRepository`, e não de uma classe concreta obrigatória. A validação estrutural é conferir se datasources e repositories estão na camada `data`.

## Possíveis erros

Um erro comum seria colocar chamadas ao Supabase dentro de `TutorListPage`. Isso funcionaria inicialmente, mas acoplaria a interface à tecnologia remota.

Outro erro seria apagar a implementação SQLite antes de concluir a remota. Isso reduziria a capacidade de comparação, teste e evolução progressiva.

Também seria um erro fazer a controller depender diretamente de `SupabaseTutorRepository`. O ideal é que ela continue dependendo de `TutorRepository`.

# 18. Erros comuns e dúvidas frequentes

## Erro 1: chamar Supabase diretamente na tela

Esse erro ocorre quando a página de listagem ou formulário executa consultas remotas diretamente.

O problema é que a tela passa a misturar interface, estado, acesso remoto e tratamento técnico de erro. Isso aumenta o acoplamento e dificulta manutenção.

A forma correta é manter a tela chamando a controller, e a controller chamando o repository.

## Erro 2: confundir repository com datasource

O datasource conversa com uma fonte específica. O repository entrega para a aplicação as operações esperadas pela feature.

Se o código de Supabase ficar dentro do repository sem separação, ainda pode funcionar, mas a organização fica menos clara. Separar datasource remoto facilita manutenção e testes.

## Erro 3: remover SQLite cedo demais

Remover SQLite antes de implementar Supabase pode atrapalhar a evolução. A implementação local serve como comparação e pode ser útil em uma futura estratégia de sincronização.

## Erro 4: alterar a controller para cada tecnologia

A controller não deve ser reescrita sempre que a origem dos dados mudar. Se isso estiver acontecendo, é sinal de que a abstração não está sendo usada corretamente.

## Erro 5: ignorar o mapeamento de campos

Dart usa frequentemente `camelCase`, enquanto bancos relacionais costumam usar `snake_case`. Se essa conversão não for tratada, podem surgir erros de campo inexistente, dados nulos inesperados ou falhas de parsing de datas.

## Erro 6: tratar erro remoto como se fosse erro local

Operações remotas podem falhar por instabilidade de rede, autenticação, permissão, timeout ou indisponibilidade do serviço. O tratamento de erro precisa ser mais cuidadoso do que em operações puramente locais.

# 19. Checklist explicado

## Verifique se a tela não acessa diretamente a fonte de dados

O que verificar: procure chamadas diretas ao SQLite ou ao Supabase dentro de páginas como `TutorListPage` e `TutorFormPage`.

Por que importa: a tela deve cuidar da interface, não da tecnologia de persistência. Quando a tela conhece o banco, qualquer troca de tecnologia exige alteração visual.

Como validar: confirme se as páginas chamam métodos da controller, e não métodos de banco ou cliente remoto.

O que acontece se faltar: a feature fica acoplada, difícil de testar e mais trabalhosa para evoluir.

## Verifique se a controller depende de `TutorRepository`

O que verificar: a controller deve receber ou armazenar uma referência do tipo `TutorRepository`.

Por que importa: depender do contrato permite trocar SQLite por Supabase sem reescrever a controller.

Como validar: observe se o atributo interno da controller é declarado como `TutorRepository`, e não exclusivamente como `SqliteTutorRepository` ou `SupabaseTutorRepository`.

O que acontece se faltar: a controller fica presa a uma implementação específica.

## Verifique se existe separação entre repository e datasource

O que verificar: o repository deve implementar as operações esperadas pela aplicação, enquanto o datasource deve concentrar a comunicação com SQLite ou Supabase.

Por que importa: essa separação evita que detalhes técnicos se espalhem pela aplicação.

Como validar: confira se existe uma estrutura parecida com `repositories/` e `datasources/` dentro da camada `data`.

O que acontece se faltar: o código pode funcionar, mas tende a ficar mais difícil de manter e expandir.

## Verifique se a implementação local foi preservada

O que verificar: confirme se `sqlite_tutor_repository.dart` e o datasource local continuam existindo enquanto a implementação remota é adicionada.

Por que importa: manter a implementação local permite comparação, testes e evolução para sincronização no futuro.

Como validar: execute ou revise os fluxos locais antes de adicionar a implementação remota.

O que acontece se faltar: a equipe perde uma referência funcional e pode dificultar a evolução progressiva.

## Verifique se o mapeamento de campos está planejado

O que verificar: identifique como os campos `tutorId`, `createdAt`, `updatedAt` e `deletedAt` serão convertidos para `tutor_id`, `created_at`, `updated_at` e `deleted_at`.

Por que importa: nomes diferentes entre Dart e PostgreSQL precisam ser convertidos de forma consistente.

Como validar: crie e revise métodos como `toSupabaseMap()` e `fromSupabaseMap()`.

O que acontece se faltar: podem ocorrer erros de leitura, escrita ou conversão de dados.

## Verifique se os erros remotos serão tratados adequadamente

O que verificar: observe se haverá tratamento para falhas de rede, ausência de conexão, erro de permissão e retorno inesperado do serviço.

Por que importa: uma base remota depende de fatores externos que não existem no mesmo nível em uma base local.

Como validar: simule falhas e confira se a controller atualiza `_errorMessage` ou estados equivalentes de forma adequada.

O que acontece se faltar: o usuário pode ficar sem retorno claro quando a operação falhar.

# 20. Síntese final

A feature Tutor já está bem preparada para evoluir de SQLite para Supabase porque foi organizada em camadas. A tela não conversa diretamente com o banco. A controller depende de um contrato. O repository implementa as operações esperadas pela aplicação. O datasource concentra o acesso à tecnologia específica.

A mudança para Supabase deve ocorrer principalmente na camada `data`, com a criação de um datasource remoto e de um repository remoto. A controller poderá continuar usando `TutorRepository`, sem precisar conhecer os detalhes do Supabase.

A implementação SQLite não precisa ser removida agora. Ela continua útil para comparação, testes e uma possível etapa futura de sincronização entre dados locais e remotos.

A preparação também exige atenção ao mapeamento de campos, porque o Dart geralmente usa `camelCase`, enquanto o PostgreSQL usa `snake_case`. Métodos de conversão como `toSupabaseMap()` e `fromSupabaseMap()` ajudam a manter essa diferença isolada.

# Conclusão

Preparar a feature Tutor para trabalhar com uma base remota não significa reescrever tudo. Significa respeitar a arquitetura existente e adicionar novas peças no lugar correto.

A tela deve continuar focada na interface. A controller deve continuar focada em estado e ações. O repository deve continuar sendo o contrato de acesso aos dados. O datasource deve concentrar a comunicação com a tecnologia concreta.

Com essa organização, a aplicação pode evoluir de SQLite para Supabase de forma progressiva, segura e mais fácil de manter.
