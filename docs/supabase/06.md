# Criando o DataSource Remoto da Feature Tutor com Supabase

## Objetivo do material

Neste material, você aprenderá a criar o **DataSource remoto da feature Tutor** em um projeto Flutter que utiliza Supabase. O DataSource remoto é a camada responsável por acessar diretamente a tabela `tutors` no banco remoto, concentrando em uma classe própria as operações de cadastro, listagem, busca por identificador, atualização e exclusão lógica de tutores. 

Ao final, a feature Tutor terá um arquivo chamado:

```text
lib/features/tutor/data/datasources/tutor_remote_datasource.dart
```

Esse arquivo ficará na camada `data/datasources`, ao lado do DataSource local, mas com uma responsabilidade diferente: acessar a base remota no Supabase.

---

## Contextualização do problema

Em uma aplicação organizada em camadas, telas e controllers não devem conhecer detalhes técnicos de acesso ao banco remoto. Se uma tela precisar chamar diretamente métodos como `.from()`, `.select()`, `.insert()` ou `.update()`, o código fica mais acoplado, mais difícil de testar e mais difícil de manter.

Por isso, criamos uma classe específica para conversar com o Supabase. Essa classe recebe o nome de **DataSource remoto**.

O DataSource remoto resolve três problemas principais:

1. **Isola o acesso ao Supabase**
   A controller e as telas não precisam saber como a biblioteca `supabase_flutter` funciona.

2. **Organiza as operações da feature Tutor**
   Todas as chamadas relacionadas à tabela `tutors` ficam concentradas em um único arquivo.

3. **Facilita testes e manutenção**
   Como a classe pode receber um `SupabaseClient` externo, fica mais simples substituir o cliente real por um cliente controlado em testes.

---

## Conceitos fundamentais

### O que é um DataSource remoto

Um **DataSource remoto** é uma classe responsável por acessar uma fonte de dados externa à aplicação. Neste caso, a fonte externa é o Supabase.

Na feature Tutor, o DataSource remoto acessa a tabela `tutors` e executa operações como:

```text
inserir tutor
listar tutores ativos
buscar tutor por ID
atualizar tutor
realizar exclusão lógica
```

Ele não deve conter regra de interface, navegação de tela ou lógica visual. Sua função é técnica: enviar comandos ao banco remoto e converter os resultados em objetos da aplicação.

### O que é um contrato de DataSource

O contrato é uma classe abstrata que define quais operações o DataSource deve oferecer. Ele funciona como uma promessa: qualquer implementação concreta desse contrato precisa implementar os métodos definidos.

No caso da feature Tutor, o contrato será:

```dart
abstract class TutorRemoteDataSource {
  Future<int> insert(Tutor tutor);
  Future<List<Tutor>> getAll({int limit = 20, int offset = 0});
  Future<Tutor?> getById(int id);
  Future<int> update(Tutor tutor);
  Future<int> delete(int id);
}
```

Esse contrato indica que a fonte remota deve conseguir inserir, listar, buscar, atualizar e excluir logicamente tutores.

### O que é a implementação concreta

A implementação concreta é a classe que realmente executa as chamadas ao Supabase. Ela implementa o contrato `TutorRemoteDataSource`.

Neste material, essa classe será chamada de:

```dart
SupabaseTutorRemoteDataSource
```

Ela utilizará um `SupabaseClient` para acessar a tabela `tutors`.

---

## Diferença entre DataSource local e DataSource remoto

O DataSource local e o DataSource remoto podem ter assinaturas parecidas, mas acessam fontes diferentes.

O **DataSource local** costuma acessar uma base armazenada no próprio dispositivo, como SQLite, Hive ou outro mecanismo local. Ele é útil para funcionamento offline, cache ou persistência interna.

O **DataSource remoto** acessa um serviço externo, como o Supabase. Ele depende de comunicação com a internet, permissões da tabela e configuração correta do projeto remoto.

Manter os dois com métodos parecidos facilita a troca de origem de dados. Por exemplo, se tanto o DataSource local quanto o remoto oferecem `insert`, `getAll`, `getById`, `update` e `delete`, o restante da aplicação pode trabalhar de forma mais padronizada.

```dart
import 'package:pet_care/features/tutor/domain/models/tutor.dart';
import 'package:supabase_flutter/supabase_flutter.dart';
```

O import do `Tutor` é necessário porque os métodos recebem e retornam objetos desse tipo. O import do Supabase é necessário porque a implementação concreta usará `SupabaseClient`.

# Criando o contrato do DataSource remoto

O primeiro trecho do arquivo define o contrato:

```dart
abstract class TutorRemoteDataSource {
  Future<int> insert(Tutor tutor);

  Future<List<Tutor>> getAll({
    int limit = 20,
    int offset = 0,
  });

  Future<Tutor?> getById(int id);

  Future<int> update(Tutor tutor);

  Future<int> delete(int id);
}
```

Cada método tem uma responsabilidade específica.

O método `insert` recebe um objeto `Tutor` e retorna o identificador do tutor criado. O retorno é `Future<int>` porque a operação é assíncrona e o ID será conhecido apenas depois da resposta do Supabase.

O método `getAll` retorna uma lista de tutores. Ele recebe `limit` e `offset` para permitir paginação. O `limit` indica quantos registros devem ser buscados. O `offset` indica a partir de qual posição a busca deve começar.

O método `getById` retorna um `Tutor?`. O ponto de interrogação indica que o retorno pode ser nulo. Isso acontece porque pode não existir tutor com o ID informado.

O método `update` recebe um tutor e altera seus dados no banco remoto. Ele retorna `1` quando a operação é executada, mantendo compatibilidade com o padrão usado em DataSources locais.

O método `delete` recebe o ID do tutor e realiza uma exclusão lógica. Ele não apaga fisicamente o registro da tabela.

# Criando a implementação com Supabase

Depois do contrato, criamos a classe concreta:

```dart
class SupabaseTutorRemoteDataSource implements TutorRemoteDataSource {
  final SupabaseClient _client;
  static const String _tableName = 'tutors';

  SupabaseTutorRemoteDataSource({SupabaseClient? client})
      : _client = client ?? Supabase.instance.client;
}
```

A classe implementa `TutorRemoteDataSource`, portanto precisa oferecer todos os métodos definidos no contrato.

A propriedade `_client` armazena o cliente do Supabase que será usado nas consultas.

A constante `_tableName` centraliza o nome da tabela:

```dart
static const String _tableName = 'tutors';
```

Isso evita repetir a string `'tutors'` em vários pontos do código. Se o nome da tabela precisasse ser alterado, a mudança seria feita em um único lugar.

O construtor aceita um `SupabaseClient?` opcional:

```dart
SupabaseTutorRemoteDataSource({SupabaseClient? client})
    : _client = client ?? Supabase.instance.client;
```

Se um cliente externo for informado, a classe usa esse cliente. Se nenhum cliente for informado, ela usa o cliente padrão:

```dart
Supabase.instance.client
```

Essa estratégia deixa a classe simples para uso normal e mais flexível para testes.

# Método insert: inserindo um tutor

O método `insert` cadastra um novo tutor na tabela `tutors`.

```dart
@override
Future<int> insert(Tutor tutor) async {
  final result = await _client
      .from(_tableName)
      .insert(tutor.toSupabaseMap())
      .select('tutor_id')
      .single();

  return result['tutor_id'] as int;
}
```

A chamada começa com:

```dart
_client.from(_tableName)
```

Esse trecho aponta para a tabela `tutors`.

Depois, os dados do tutor são enviados:

```dart
.insert(tutor.toSupabaseMap())
```

O método `toSupabaseMap()` deve converter o objeto `Tutor` para um `Map` compatível com os nomes das colunas no Supabase. Essa conversão é importante porque o Dart trabalha com propriedades como `tutorId`, enquanto o banco pode usar nomes como `tutor_id`.

Em seguida, o código solicita que o Supabase retorne o campo `tutor_id`:

```dart
.select('tutor_id')
```

Isso é necessário porque, depois de inserir um registro, a aplicação precisa saber qual ID foi gerado.

O método `.single()` indica que esperamos apenas um registro de resposta:

```dart
.single()
```

Por fim, o ID é extraído do resultado:

```dart
return result['tutor_id'] as int;
```

O retorno será o identificador do tutor recém-cadastrado.

# Método getAll: listando tutores ativos

O método `getAll` busca uma página de tutores ativos, ou seja, tutores que não foram removidos logicamente.

```dart
@override
Future<List<Tutor>> getAll({
  int limit = 20,
  int offset = 0,
}) async {
  final from = offset;
  final to = offset + limit - 1;

  final result = await _client
      .from(_tableName)
      .select()
      .isFilter('deleted_at', null)
      .order('nome', ascending: true)
      .range(from, to);

  return result.map<Tutor>((map) {
    return Tutor.fromSupabaseMap(map);
  }).toList();
}
```

A primeira parte calcula o intervalo da paginação:

```dart
final from = offset;
final to = offset + limit - 1;
```

Esse cálculo é necessário porque o método `.range()` do Supabase usa um intervalo inclusivo. Isso significa que tanto o índice inicial quanto o índice final entram no resultado.

Por exemplo, para buscar 7 registros a partir do início:

```text
offset = 0
limit = 7
from = 0
to = 0 + 7 - 1
to = 6
```

O intervalo será de `0` a `6`, totalizando 7 registros.

A consulta começa assim:

```dart
_client.from(_tableName).select()
```

Esse trecho seleciona registros da tabela `tutors`.

Depois, o filtro de exclusão lógica é aplicado:

```dart
.isFilter('deleted_at', null)
```

Esse filtro garante que apenas registros com `deleted_at` nulo sejam retornados. Se `deleted_at` estiver preenchido, significa que o tutor foi removido logicamente e não deve aparecer nas consultas comuns.

A ordenação é feita pelo nome:

```dart
.order('nome', ascending: true)
```

Isso retorna os tutores em ordem alfabética crescente.

A paginação é aplicada com:

```dart
.range(from, to)
```

Esse trecho limita a quantidade de registros retornados.

Por fim, cada item retornado pelo Supabase é convertido para objeto `Tutor`:

```dart
return result.map<Tutor>((map) {
  return Tutor.fromSupabaseMap(map);
}).toList();
```

A função `Tutor.fromSupabaseMap(map)` deve interpretar os dados vindos do banco e criar uma instância válida de `Tutor`.

# Método getById: buscando um tutor pelo identificador

O método `getById` busca um tutor específico pelo campo `tutor_id`.

```dart
@override
Future<Tutor?> getById(int id) async {
  final result = await _client
      .from(_tableName)
      .select()
      .eq('tutor_id', id)
      .isFilter('deleted_at', null)
      .maybeSingle();

  if (result == null) {
    return null;
  }

  return Tutor.fromSupabaseMap(result);
}
```

O filtro por ID é feito com:

```dart
.eq('tutor_id', id)
```

Esse trecho busca apenas o registro cujo campo `tutor_id` seja igual ao valor recebido no parâmetro `id`.

O método também aplica o filtro de exclusão lógica:

```dart
.isFilter('deleted_at', null)
```

Assim, mesmo que exista um registro com o ID informado, ele não será retornado se tiver sido marcado como excluído.

O método usa:

```dart
.maybeSingle()
```

Esse método é adequado porque a consulta pode retornar um registro ou nenhum registro. Se não existir tutor ativo com o ID informado, o resultado será `null`.

Por isso, o retorno do método é `Future<Tutor?>`, permitindo que a controller trate o caso de tutor não encontrado.

# Método update: atualizando um tutor

O método `update` altera os dados de um tutor existente.

```dart
@override
Future<int> update(Tutor tutor) async {
  if (tutor.tutorId == null) {
    throw ArgumentError(
      'Não é possível atualizar um tutor sem tutorId.',
    );
  }

  final tutorAtualizado = tutor.copyWith(
    updatedAt: DateTime.now(),
  );

  await _client
      .from(_tableName)
      .update(tutorAtualizado.toSupabaseMap())
      .eq('tutor_id', tutor.tutorId!);

  return 1;
}
```

Antes de atualizar, o método verifica se o tutor possui identificador:

```dart
if (tutor.tutorId == null) {
  throw ArgumentError(
    'Não é possível atualizar um tutor sem tutorId.',
  );
}
```

Essa validação é essencial. Sem `tutorId`, não há como saber qual registro da tabela deve ser atualizado.

Depois, o objeto é copiado com uma nova data de atualização:

```dart
final tutorAtualizado = tutor.copyWith(
  updatedAt: DateTime.now(),
);
```

O método `copyWith` cria uma nova versão do objeto, preservando os dados existentes e alterando apenas os campos informados. Neste caso, o campo `updatedAt` recebe a data e hora atuais.

A atualização no Supabase é feita com:

```dart
await _client
    .from(_tableName)
    .update(tutorAtualizado.toSupabaseMap())
    .eq('tutor_id', tutor.tutorId!);
```

O método `.update()` envia os novos dados. O método `.eq()` garante que apenas o registro com o `tutor_id` correspondente seja alterado.

O retorno `1` indica que a operação foi executada e mantém compatibilidade com o padrão usado no DataSource local.

# Método delete: realizando exclusão lógica

O método `delete` não remove fisicamente o registro do banco. Ele realiza uma **exclusão lógica**, preenchendo o campo `deleted_at`.

```dart
@override
Future<int> delete(int id) async {
  final now = DateTime.now().toIso8601String();

  await _client
      .from(_tableName)
      .update({
        'deleted_at': now,
        'updated_at': now,
      })
      .eq('tutor_id', id);

  return 1;
}
```

A primeira linha cria uma data atual em formato ISO:

```dart
final now = DateTime.now().toIso8601String();
```

Esse valor será usado em dois campos:

```dart
'deleted_at': now,
'updated_at': now,
```

O campo `deleted_at` indica quando o tutor foi excluído logicamente. O campo `updated_at` indica quando o registro foi alterado pela última vez.

A atualização é aplicada apenas ao tutor com o ID informado:

```dart
.eq('tutor_id', id)
```

Essa estratégia mantém o registro na tabela, mas impede que ele apareça em consultas que filtram `deleted_at` como nulo.

---

# Por que usar exclusão lógica

A exclusão lógica é útil quando não queremos apagar definitivamente os dados do banco.

Em vez de executar um comando de remoção física, o sistema apenas marca o registro como removido. Isso traz algumas vantagens.

A primeira vantagem é preservar histórico. Mesmo que o tutor não apareça mais nas listagens, o registro ainda existe no banco.

A segunda vantagem é reduzir risco de perda acidental. Se uma exclusão for feita por engano, ainda existe a possibilidade de recuperar ou auditar os dados.

A terceira vantagem é manter coerência com relacionamentos. Se outros registros dependerem do tutor, remover fisicamente o registro poderia causar inconsistências.

No entanto, a exclusão lógica exige disciplina nas consultas. Métodos como `getAll` e `getById` precisam sempre filtrar:

```dart
.isFilter('deleted_at', null)
```

Sem esse filtro, registros excluídos logicamente poderiam aparecer novamente na aplicação.

```dart
  Future<List<Tutor>> getAll({

    int offset = 0,
  });

  Future<Tutor?> getById(int id);

  Future<int> update(Tutor tutor);

  Future<int> delete(int id);
}

      : _client = client ?? Supabase.instance.client;

    final result = await _client
        .from(_tableName)
        .insert(tutor.toSupabaseMap())
        .select('tutor_id')
        .single();

    return result['tutor_id'] as int;
  }

  @override
  Future<List<Tutor>> getAll({
    int limit = 20,
    int offset = 0,
  }) async {
    final from = offset;
    final to = offset + limit - 1;

    final result = await _client
        .from(_tableName)
        .select()

        .order('nome', ascending: true)
        .range(from, to);

    return result.map<Tutor>((map) {
      return Tutor.fromSupabaseMap(map);
    }).toList();
  }

  @override
  Future<Tutor?> getById(int id) async {
    final result = await _client
        .from(_tableName)
        .select()
        .eq('tutor_id', id)
        .isFilter('deleted_at', null)
        .maybeSingle();

    if (result == null) {
      return null;
    }

    return Tutor.fromSupabaseMap(result);
  }

  @override
  Future<int> update(Tutor tutor) async {
    if (tutor.tutorId == null) {
      throw ArgumentError(
        'Não é possível atualizar um tutor sem tutorId.',

    }

    final tutorAtualizado = tutor.copyWith(
      updatedAt: DateTime.now(),
    );

    await _client
        .from(_tableName)
        .update(tutorAtualizado.toSupabaseMap())
        .eq('tutor_id', tutor.tutorId!);

    return 1;
  }

  @override
  Future<int> delete(int id) async {
    final now = DateTime.now().toIso8601String();

    await _client
        .from(_tableName)
        .update({
          'deleted_at': now,
          'updated_at': now,
        })
        .eq('tutor_id', id);

    return 1;
```

# Aplicação prática resolvida: validando o DataSource remoto

## Cenário

A feature Tutor já possui o model `Tutor`, a tabela `tutors` no Supabase e a configuração inicial do Supabase no projeto Flutter. Agora, é necessário validar se o DataSource remoto consegue consultar a tabela.

## Objetivo

Confirmar que a classe `SupabaseTutorRemoteDataSource` consegue acessar a tabela `tutors`, buscar registros ativos e convertê-los para objetos `Tutor`.

## Solução temporária

Depois da inicialização do Supabase, crie um teste temporário:

```dart
final dataSource = SupabaseTutorRemoteDataSource();

final tutores = await dataSource.getAll(
  limit: 5,
  offset: 0,
);

debugPrint('Quantidade de tutores encontrados: ${tutores.length}');
```

## Comentário da solução

A linha abaixo cria uma instância do DataSource usando o cliente padrão do Supabase:

```dart
final dataSource = SupabaseTutorRemoteDataSource();
```

Depois, o método `getAll` busca até 5 tutores ativos:

```dart
final tutores = await dataSource.getAll(
  limit: 5,
  offset: 0,
);
```

Como `limit` é `5` e `offset` é `0`, o DataSource calcula:

```text
from = 0
to = 0 + 5 - 1
to = 4
```

Logo, a consulta busca o intervalo de registros de `0` a `4`.

Por fim, o tamanho da lista é exibido no console:

```dart
debugPrint('Quantidade de tutores encontrados: ${tutores.length}');
```

## Resultado esperado

Se a conexão estiver correta e a tabela estiver acessível, o console exibirá a quantidade de tutores encontrados.

Se existirem registros ativos na tabela, eles serão convertidos para objetos `Tutor`.

## Como validar

A validação deve observar quatro pontos.

Primeiro, o projeto não deve apresentar erro de conexão com o Supabase. Isso indica que a inicialização está funcionando.

Segundo, a tabela `tutors` deve ser encontrada. Se o nome da tabela estiver incorreto, a consulta falhará.

Terceiro, os campos retornados precisam ser compatíveis com o método `Tutor.fromSupabaseMap`. Se o banco retornar `created_at`, por exemplo, o mapper deve saber converter esse campo corretamente.

Quarto, registros com `deleted_at` preenchido não devem aparecer na listagem. Isso confirma que o filtro de exclusão lógica está funcionando.

## Importante

Esse código de teste deve ser removido depois da validação. Ele serve apenas para confirmar a comunicação entre Flutter e Supabase e não deve permanecer como parte definitiva da aplicação.

# Possíveis erros e como resolver

## Erro ao acessar a tabela

Esse erro pode ocorrer quando a tabela não existe ou quando o nome usado no código está diferente do nome real no Supabase.

O código utiliza:

```dart
static const String _tableName = 'tutors';
```

Portanto, a tabela precisa se chamar exatamente:

```text
tutors
```

Também verifique se ela está no schema correto, geralmente `public`.

Se o nome estiver como `tutor`, `Tutors`, `tb_tutors` ou qualquer outra variação, a consulta não encontrará a tabela esperada.

## Erro de campo inexistente

Esse erro aparece quando o código referencia uma coluna que não existe na tabela.

Os principais campos usados neste DataSource são:

```text
tutor_id
nome
created_at
updated_at
deleted_at
```

Dependendo do model `Tutor`, também podem existir campos como:

```text
email
telefone
```

Um erro comum é confundir o nome da propriedade no Dart com o nome da coluna no banco. Por exemplo, no Dart pode existir:

```dart
createdAt
```

Mas no Supabase a coluna pode se chamar:

```text
created_at
```

Por isso, os métodos `toSupabaseMap()` e `fromSupabaseMap()` precisam fazer a conversão corretamente.

## Erro de conversão de data

Se ocorrer erro em `DateTime.parse`, verifique se os campos de data estão preenchidos corretamente.

Campos como `created_at` e `updated_at` normalmente devem possuir valores válidos. Se a tabela foi criada com `default now()`, registros criados corretamente devem receber esses valores automaticamente.

Se algum registro antigo estiver com data nula ou em formato inesperado, o mapper pode falhar ao tentar converter o valor para `DateTime`.

## Erro de permissão

Se a tabela existe, os campos estão corretos, mas a consulta é bloqueada, o problema pode estar relacionado a permissões ou políticas de acesso no Supabase.

Nesse caso, o DataSource pode estar correto, mas o Supabase pode estar impedindo a leitura, inserção ou atualização.

Nesta etapa, o foco é validar a comunicação entre Flutter e Supabase. Regras de segurança, permissões e políticas de acesso devem ser revisadas em uma etapa própria.

## Erro ao atualizar tutor sem ID

O método `update` exige que o objeto tenha `tutorId`.

Se o tutor estiver sem ID, o método lança:

```dart
throw ArgumentError(
  'Não é possível atualizar um tutor sem tutorId.',
);
```

Esse erro é esperado e protege o banco contra atualizações ambíguas. Sem ID, o código não sabe qual linha deve alterar.

## Registros excluídos aparecendo na listagem

Se tutores removidos logicamente aparecerem no resultado, verifique se a consulta possui o filtro:

```dart
.isFilter('deleted_at', null)
```

Esse filtro deve estar presente em consultas que retornam tutores ativos, como `getAll` e `getById`.

## Verifique se o arquivo foi criado no caminho correto

Esse caminho importa porque mantém a organização da feature. Se o arquivo for criado fora da camada `data/datasources`, a separação de responsabilidades fica menos clara e o projeto se torna mais difícil de navegar.

Para validar, confira a estrutura de pastas do projeto e confirme se o DataSource remoto está ao lado do DataSource local.

## Verifique se os imports estão corretos

O arquivo precisa importar o model `Tutor` e o pacote do Supabase:

```dart
import 'package:pet_care/features/tutor/domain/models/tutor.dart';
```

## Verifique se o contrato possui todos os métodos necessários

Para validar, compare o contrato com a implementação concreta e confirme se todos os métodos foram implementados.

## Verifique se o nome da tabela está centralizado

A classe deve possuir:

```dart
static const String _tableName = 'tutors';
```

Centralizar o nome da tabela evita repetição e reduz risco de erro. Se o nome fosse escrito manualmente em cada método, uma pequena diferença de digitação poderia causar falhas difíceis de perceber.

Para validar, procure chamadas diretas como `.from('tutors')`. O ideal é usar `.from(_tableName)`.

```dart
.select('tutor_id')

```

Isso garante que o Supabase retorne o identificador do registro criado.

Sem esse retorno, a aplicação poderia inserir o tutor, mas não saber qual ID foi gerado. Isso dificultaria operações posteriores, como atualização ou navegação para detalhes do tutor.

Para validar, faça uma inserção de teste e confira se o método retorna um número inteiro.

## Verifique se getAll filtra registros excluídos logicamente

```dart
.isFilter('deleted_at', null)
```

Esse filtro impede que registros marcados como excluídos apareçam na listagem.

Sem esse filtro, a exclusão lógica perde parte do sentido, pois registros removidos continuariam aparecendo para o usuário.

Para validar, marque um tutor com `deleted_at` preenchido e confirme que ele não aparece no retorno de `getAll`.

## Verifique se a paginação calcula o intervalo corretamente

A paginação deve calcular:

```dart

final to = offset + limit - 1;
```

Esse cálculo é necessário porque o intervalo do Supabase é inclusivo.

Se o `- 1` for esquecido, a consulta pode retornar um item a mais do que o esperado. Por exemplo, com `limit = 5`, o intervalo de `0` a `5` retornaria 6 registros.

Para validar, use `limit: 5` e confirme se a lista retorna no máximo 5 itens.

## Verifique se getById usa maybeSingle

O método `getById` deve usar:

```dart
.maybeSingle()
```

Esse método é adequado porque pode existir um tutor ou nenhum tutor com o ID informado.

Se fosse usado `.single()` e nenhum registro fosse encontrado, a consulta poderia gerar erro. Com `.maybeSingle()`, o código consegue retornar `null` de forma controlada.

Para validar, busque um ID inexistente e confirme se o método retorna `null`.

## Verifique se update exige tutorId

```dart
if (tutor.tutorId == null) {
```

Para validar, tente chamar `update` com um tutor sem ID em ambiente controlado e confirme se o erro é lançado.

## Verifique se delete faz exclusão lógica

Ele não deve apagar o registro fisicamente.

Para validar, execute `delete` em um registro de teste e confira no Supabase se o campo `deleted_at` foi preenchido.
