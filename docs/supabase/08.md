# Usando Supabase na Listagem e no Formulário de Tutor

## Objetivo do material

Neste material, você aprenderá a conectar a feature de **Tutor** ao **Supabase**, fazendo com que a listagem, o formulário, a edição e a remoção deixem de depender de uma implementação local com SQLite e passem a usar uma fonte de dados remota.

A ideia principal é manter a estrutura da aplicação organizada por contratos, especialmente por meio do `TutorRepository`, mas trocar a implementação concreta usada pela `TutorController`. Com isso, as telas continuam chamando os mesmos métodos, enquanto os dados passam a ser lidos e gravados na tabela `tutors` do Supabase. 

---

## Contextualização do problema

Em uma aplicação Flutter organizada com Clean Architecture, as telas não devem depender diretamente de detalhes de banco de dados. A tela de listagem de tutores não precisa saber se os dados vêm do SQLite, do Supabase ou de outra fonte. Da mesma forma, o formulário de cadastro e edição não deve conhecer a lógica interna de acesso remoto.

Essa separação é importante porque permite trocar a origem dos dados com o menor impacto possível. Antes, a feature de Tutor usava uma implementação local, baseada em `SqliteTutorRepository`. Agora, o objetivo é fazer a mesma feature usar `SupabaseTutorRepository`, que acessa a tabela `tutors` no Supabase.

O ganho prático é que a aplicação passa a trabalhar com dados remotos no fluxo real de uso: cadastrar tutor, listar tutores, editar dados e realizar remoção lógica.

---

## Conceitos fundamentais

### TutorRepository

`TutorRepository` é o contrato usado pela camada de apresentação para manipular tutores. Ele define quais operações a aplicação precisa realizar, como buscar, inserir, atualizar e remover tutores.

A controller conversa com esse contrato, não com uma implementação específica. Isso significa que a controller não precisa saber se os dados vêm de SQLite ou Supabase.

Esse princípio reduz acoplamento. Quando a aplicação precisa trocar a origem dos dados, a mudança fica concentrada na implementação usada, e não espalhada por todas as telas.

---

### SqliteTutorRepository

`SqliteTutorRepository` é uma implementação concreta do contrato `TutorRepository` voltada para armazenamento local. Ela usa SQLite como fonte de dados.

Esse tipo de repository é útil quando a aplicação precisa salvar dados no próprio dispositivo, funcionar offline ou testar a feature sem depender de uma conexão remota.

No contexto deste material, ele será substituído como implementação padrão da controller.

---

### SupabaseTutorRepository

`SupabaseTutorRepository` é a implementação concreta do contrato `TutorRepository` que utiliza o Supabase como fonte de dados.

Ele permite que a feature Tutor continue usando os mesmos métodos definidos pelo contrato, mas agora com persistência remota. Isso significa que operações como cadastro, listagem, edição e remoção passam a acontecer na tabela `tutors`.

---

### SupabaseTutorRemoteDataSource

`SupabaseTutorRemoteDataSource` é a camada responsável pelo acesso direto à tabela `tutors` no Supabase.

Enquanto o repository representa uma abstração de persistência para o domínio da aplicação, o data source remoto conhece os detalhes de comunicação com o Supabase. Ele sabe como buscar registros, inserir linhas, atualizar dados e aplicar a remoção lógica.

---

### TutorController

`TutorController` é a classe que coordena as ações da feature de Tutor na camada de apresentação.

Ela é usada pelas telas para carregar tutores, cadastrar novos registros, atualizar dados existentes, remover tutores e controlar estados como carregamento, erro, paginação e lista atual.

A mudança central deste material acontece nessa controller: ela deixará de usar `SqliteTutorRepository` como padrão e passará a usar `SupabaseTutorRepository`.

---

## Diferença entre contrato e implementação concreta

Um ponto essencial para entender esta integração é distinguir **contrato** de **implementação concreta**.

O contrato define o que precisa ser feito. A implementação concreta define como isso será feito.

No caso da feature Tutor:

```dart
TutorRepository
```

é o contrato. Ele representa as operações esperadas para manipular tutores.

Já estas classes são implementações concretas:

```dart
SqliteTutorRepository
SupabaseTutorRepository
```

Ambas podem cumprir o mesmo contrato, mas usando estratégias diferentes. A primeira acessa dados locais. A segunda acessa dados remotos.

Essa separação permite que a controller continue usando `TutorRepository`, enquanto a implementação padrão muda de SQLite para Supabase.

---

## Mudança principal na TutorController

A alteração mais importante está no construtor da `TutorController`.

Antes, a controller usava SQLite como implementação padrão:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SqliteTutorRepository();
```

Depois da mudança, a controller passa a usar Supabase como implementação padrão:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SupabaseTutorRepository();
```

Essa troca é pequena no código, mas grande no comportamento da aplicação. A controller continua trabalhando com o contrato `TutorRepository`, porém, quando nenhuma implementação específica é passada, ela instancia `SupabaseTutorRepository`.

Na prática, isso significa que as telas que criam a controller assim:

```dart
final TutorController _controller = TutorController();
```

passam automaticamente a usar o Supabase, desde que o construtor padrão tenha sido alterado corretamente.

---

## Atualizando os imports da TutorController

Depois de trocar a implementação padrão, é necessário revisar os imports do arquivo da controller.

O arquivo esperado é:

```text
lib/features/tutor/presentation/controllers/tutor_controller.dart
```

Se a controller não usa mais SQLite como padrão, o import do repository SQLite pode ser removido:

```dart
import 'package:pet_care/features/tutor/data/repositories/sqlite_tutor_repository.dart';
```

Em seguida, deve ser adicionado o import do repository Supabase:

```dart
import 'package:pet_care/features/tutor/data/repositories/supabase_tutor_repository.dart';
```

A controller precisa conhecer a classe `SupabaseTutorRepository` para conseguir instanciá-la no construtor padrão.

Um erro comum nessa etapa é alterar o construtor, mas esquecer o import. Nesse caso, o projeto não compila, porque o Dart não reconhece a classe usada.

---

## Métodos da controller que permanecem iguais

A troca do repository não exige que os métodos chamados pelas telas sejam alterados. Esse é um dos principais benefícios de programar contra contratos.

A controller continuará usando métodos como:

```dart
getAllTutors()
insertTutor(tutor)
updateTutor(tutor)
deleteTutor(id)
```

A diferença é o destino da operação.

`getAllTutors()` passa a buscar tutores ativos na tabela remota `tutors`.

`insertTutor(tutor)` passa a inserir um novo registro no Supabase.

`updateTutor(tutor)` passa a atualizar os dados de um tutor existente, incluindo campos de controle como `updated_at`, quando essa lógica estiver implementada no repository ou data source.

`deleteTutor(id)` passa a realizar remoção lógica, preenchendo o campo `deleted_at`, em vez de apagar fisicamente o registro.

Essa mudança preserva a interface usada pelas telas e altera apenas a infraestrutura de dados por trás da feature.

## Conferindo a integração na tela de listagem

A tela de listagem normalmente fica em:

```text
lib/features/tutor/presentation/pages/tutor_list_page.dart
```

Nessa tela, procure onde a controller é criada. Um exemplo comum é:

```dart
final TutorController _controller = TutorController();
```

Quando a controller é instanciada dessa forma, sem receber um repository explicitamente, ela usa o repository padrão definido no construtor.

Portanto, se o construtor da `TutorController` foi alterado para usar `SupabaseTutorRepository`, a tela de listagem já passa a buscar dados no Supabase.

O ponto principal a validar é se a listagem chama o carregamento inicial dos dados, geralmente no `initState`, por meio de algum método como `loadTutors()` ou equivalente.

---

## Conferindo a integração no formulário de Tutor

O formulário normalmente fica em:

```text
lib/features/tutor/presentation/pages/tutor_form_page.dart
```

Esse formulário pode criar uma nova instância de `TutorController` ou receber uma controller por parâmetro. As duas abordagens podem funcionar, mas precisam ser analisadas com atenção.

Se o formulário cria a controller assim:

```dart
final TutorController _controller = TutorController();
```

ele também passará a usar Supabase automaticamente, desde que o construtor padrão tenha sido alterado.

Se o formulário recebe a controller por parâmetro, é necessário verificar de onde essa instância vem. O ideal é que a instância usada pelo formulário esteja coerente com a origem de dados usada pela listagem.

O importante é evitar uma situação inconsistente, em que a listagem usa Supabase e o formulário ainda usa SQLite, ou o contrário.

---

## Fluxo esperado após o cadastro

Quando um tutor é cadastrado pelo formulário, o registro deve ser salvo na tabela `tutors` do Supabase. Depois disso, a tela de listagem precisa ser atualizada para buscar novamente os dados.

O fluxo esperado é:

1. O usuário abre o formulário.
2. O usuário preenche os dados do tutor.
3. O formulário salva os dados no Supabase.
4. O formulário retorna para a tela de listagem informando que houve alteração.
5. A listagem executa um novo carregamento.
6. O tutor recém-cadastrado aparece na lista.

O ponto mais importante é o retorno do formulário. A tela de listagem precisa saber que algo mudou.

---

## Retornando sucesso do formulário

Após cadastrar ou atualizar um tutor com sucesso, o formulário deve retornar `true` para a tela anterior:

```dart
Navigator.pop(context, true);
```

Esse `true` funciona como um sinal. Ele informa à tela de listagem que a operação foi concluída e que os dados devem ser recarregados.

Se o formulário fizer apenas:

```dart
Navigator.pop(context);
```

a tela anterior não recebe uma indicação clara de alteração. Nesse caso, a listagem pode continuar exibindo dados antigos, mesmo que o cadastro tenha sido salvo corretamente no Supabase.

---

## Recarregando a listagem após voltar do formulário

Na tela de listagem, é possível capturar o retorno do formulário com `await Navigator.push`.

Exemplo:

```dart
final result = await Navigator.push(
  context,
  MaterialPageRoute(
    builder: (context) => const TutorFormPage(),
  ),
);

if (result == true) {
  await _controller.refresh();
}
```

Esse código funciona da seguinte forma:

A chamada `Navigator.push` abre o formulário e aguarda o retorno.

Quando o formulário fecha com:

```dart
Navigator.pop(context, true);
```

a variável `result` recebe `true`.

Se `result == true`, a listagem chama:

```dart
await _controller.refresh();
```

Assim, a lista é limpa e carregada novamente a partir do Supabase.

---

## Criando o método refresh na controller

Caso a controller ainda não tenha um método para recarregar os dados, é possível adicionar um método `refresh()`.

Exemplo:

```dart
Future<void> refresh() async {
  _tutors.clear();
  _offset = 0;
  _hasMoreData = true;
  _errorMessage = null;
  await loadTutors();
}
```

Esse método tem uma função importante: ele reinicia o estado interno da listagem antes de buscar os dados novamente.

A linha:

```dart
_tutors.clear();
```

remove os tutores atualmente armazenados na lista da controller.

A linha:

```dart
_offset = 0;
```

reinicia o controle de paginação. Isso é importante quando a listagem trabalha com carregamento em partes.

A linha:

```dart
_hasMoreData = true;
```

informa que a controller deve considerar que ainda pode haver dados a carregar.

A linha:

```dart
_errorMessage = null;
```

limpa mensagens de erro anteriores. Isso evita que um erro antigo continue aparecendo depois de uma nova tentativa bem-sucedida.

Por fim:

```dart
await loadTutors();
```

executa novamente o carregamento dos tutores.

Se o projeto já possuir um método equivalente, não é necessário duplicar comportamento. O ideal é usar o método já existente, desde que ele limpe o estado corretamente e carregue novamente os dados.

## Aplicação prática resolvida: conectando Tutor ao Supabase

### Cenário

A feature de Tutor já possui uma estrutura de acesso remoto criada anteriormente:

```text
TutorRemoteDataSource
SupabaseTutorRemoteDataSource
SupabaseTutorRepository
```

A aplicação também já possui telas de listagem e formulário funcionando com a controller.

O problema é que a controller ainda usa SQLite como implementação padrão.

---

### Objetivo

Alterar a aplicação para que a feature Tutor use Supabase no fluxo real de cadastro, listagem, edição e remoção.

---

### Solução

Primeiro, abra o arquivo:

```text
lib/features/tutor/presentation/controllers/tutor_controller.dart
```

Remova o import do repository SQLite, caso ele não seja mais usado:

```dart
import 'package:pet_care/features/tutor/data/repositories/sqlite_tutor_repository.dart';
```

Adicione o import do repository Supabase:

```dart
import 'package:pet_care/features/tutor/data/repositories/supabase_tutor_repository.dart';
```

Depois, altere o construtor da controller.

Antes:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SqliteTutorRepository();
```

Depois:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SupabaseTutorRepository();
```

Em seguida, verifique a tela de listagem:

```text
lib/features/tutor/presentation/pages/tutor_list_page.dart
```

Confirme se a controller é criada sem repository explícito:

```dart
final TutorController _controller = TutorController();
```

Se estiver assim, a listagem usará automaticamente o Supabase.

Agora, ajuste o retorno do formulário após salvar:

```dart
Navigator.pop(context, true);
```

Por fim, na listagem, capture esse retorno:

```dart
final result = await Navigator.push(
  context,
  MaterialPageRoute(
    builder: (context) => const TutorFormPage(),
  ),
);

if (result == true) {
  await _controller.refresh();
}
```

Caso necessário, adicione o método `refresh()` à controller:

```dart
Future<void> refresh() async {
  _tutors.clear();
  _offset = 0;
  _hasMoreData = true;
  _errorMessage = null;
  await loadTutors();
}
```

---

### Comentário da solução

A solução funciona porque a aplicação já estava organizada com uma abstração chamada `TutorRepository`. A controller não precisa ser reescrita para Supabase. Ela apenas passa a receber outra implementação do mesmo contrato.

A listagem e o formulário também continuam chamando os mesmos métodos da controller. Isso evita mudanças desnecessárias na camada de apresentação.

O ajuste do `Navigator.pop(context, true)` é necessário porque salvar no Supabase não garante, por si só, que a listagem será atualizada visualmente. A tela precisa ser avisada de que houve alteração para buscar novamente os dados.

---

### Resultado esperado

Depois da alteração, a aplicação deve apresentar o seguinte comportamento:

Ao abrir a listagem, os tutores ativos da tabela `tutors` devem aparecer.

Ao cadastrar um novo tutor, o registro deve ser salvo no Supabase.

Ao voltar do formulário, a lista deve ser recarregada.

Ao editar um tutor, os dados devem ser atualizados na tabela remota.

Ao remover um tutor, o registro não deve ser apagado fisicamente; o campo `deleted_at` deve ser preenchido, e o tutor não deve mais aparecer na listagem.

---

### Como validar

Execute o aplicativo:

```bash
flutter run
```

Abra a tela de tutores. Se existirem registros ativos na tabela `tutors`, eles devem aparecer.

Cadastre um tutor preenchendo nome, e-mail e telefone. Depois de salvar, confirme se o aplicativo voltou para a listagem e se o novo tutor apareceu.

No painel do Supabase, confira se o registro foi inserido na tabela `tutors`.

Edite um tutor existente e salve. Confirme se os dados foram alterados na tabela remota e se o campo `updated_at`, quando usado pelo projeto, recebeu nova data e hora.

Remova um tutor pela interface. Verifique se o campo `deleted_at` foi preenchido. O tutor removido logicamente não deve mais aparecer na listagem.

---

### Possíveis erros

Se a aplicação continuar usando SQLite, provavelmente o construtor da `TutorController` não foi alterado ou alguma tela está passando explicitamente um `SqliteTutorRepository`.

Se o cadastro salvar, mas a lista não atualizar, provavelmente o formulário não está retornando `true` ou a listagem não está chamando `refresh()` após receber esse retorno.

Se a edição falhar, verifique se o objeto tutor possui identificador, como `tutorId`. Sem esse identificador, o Supabase não sabe qual linha deve ser atualizada.

Se houver erro de permissão, a tabela pode estar bloqueando leitura ou escrita por causa das políticas de segurança do Supabase.

---

## Testando a integração com Supabase

### Teste da listagem

Abra a tela de tutores.

Se houver registros ativos na tabela `tutors`, eles devem ser exibidos. Um registro ativo é aquele que não possui `deleted_at` preenchido.

Se a tabela estiver vazia, ou se todos os registros estiverem com `deleted_at` preenchido, a tela deve exibir o estado vazio previsto no projeto.

Esse teste confirma se a leitura remota está funcionando.

---

### Teste do cadastro

Abra o formulário de tutor, preencha os campos necessários e salve.

Depois do salvamento, verifique três pontos:

O aplicativo voltou para a listagem.

A listagem foi atualizada.

O registro apareceu na tabela `tutors` no Supabase.

Esse teste confirma se a criação remota está funcionando e se a navegação entre formulário e listagem está bem integrada.

---

### Teste da edição

Selecione um tutor existente, altere algum dado e salve.

Depois, confira no Supabase se o campo alterado foi atualizado. Se o projeto usa o campo `updated_at`, verifique se ele recebeu nova data e hora.

Esse teste confirma se a aplicação está enviando o identificador correto do tutor e se o método de atualização está alterando a linha certa.

---

### Teste da remoção

Remova um tutor pela interface.

O comportamento esperado não é apagar o registro da tabela. O esperado é preencher o campo `deleted_at`.

Depois da remoção, o tutor não deve mais aparecer na listagem, porque a listagem deve buscar apenas registros ativos.

Esse teste confirma se a remoção lógica está funcionando.

---

## Remoção lógica com deleted_at

A remoção lógica é uma estratégia em que o registro continua existindo no banco de dados, mas passa a ser considerado removido pelo sistema.

Em vez de executar uma exclusão física, a aplicação preenche um campo como:

```text
deleted_at
```

Esse campo registra o momento em que o item foi removido.

A listagem deve ignorar registros com `deleted_at` preenchido. Assim, o usuário não vê mais o tutor na aplicação, mas o dado ainda existe para auditoria, histórico ou recuperação futura.

Esse comportamento exige cuidado: se a consulta remota não filtrar corretamente os registros ativos, tutores removidos logicamente podem continuar aparecendo na tela.

## Alternando entre SQLite e Supabase durante testes

Durante o desenvolvimento, pode ser útil alternar entre a origem local e a origem remota.

Para usar Supabase como padrão:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SupabaseTutorRepository();
```

Para voltar temporariamente ao SQLite:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SqliteTutorRepository();
```

Essa troca manual é suficiente para fins didáticos e para validações simples.

Em uma aplicação mais avançada, essa decisão poderia ser centralizada em uma configuração de ambiente. Por exemplo, o app poderia usar Supabase em produção e SQLite em determinados testes locais. Porém, neste momento, a alteração direta no construtor já resolve o objetivo do material.

## Problemas comuns e soluções

### A tela abre, mas não mostra dados

Esse problema pode acontecer mesmo quando a conexão com Supabase está funcionando.

Primeiro, verifique se existem registros na tabela `tutors`.

Depois, confira se esses registros estão ativos. Um tutor ativo deve estar com `deleted_at` vazio. Se todos os registros estiverem com `deleted_at` preenchido, a listagem corretamente não exibirá tutores.

Também é importante verificar se a consulta feita pelo data source remoto está usando o filtro correto para buscar apenas registros ativos.

---

### O cadastro salva, mas a listagem não atualiza

Esse problema geralmente está relacionado ao retorno do formulário.

Confirme se, após salvar com sucesso, o formulário executa:

```dart
Navigator.pop(context, true);
```

Depois, confirme se a tela de listagem captura esse retorno:

```dart
if (result == true) {
  await _controller.refresh();
}
```

Se qualquer uma dessas partes faltar, a listagem pode continuar mostrando o estado anterior.

---

### O app continua usando SQLite

Verifique o construtor da `TutorController`.

Ele deve estar assim:

```dart
TutorController({TutorRepository? repository})
    : _repository = repository ?? SupabaseTutorRepository();
```

Também procure por instâncias em que uma implementação é passada manualmente:

```dart
TutorController(repository: SqliteTutorRepository())
```

Quando isso acontece, o repository passado por parâmetro tem prioridade sobre o padrão do construtor. Portanto, mesmo que o padrão tenha sido alterado para Supabase, aquela instância específica continuará usando SQLite.

---

### Erro ao atualizar tutor

A atualização depende de um identificador.

Se o objeto enviado para atualização não tiver `tutorId`, o data source remoto não consegue saber qual linha da tabela `tutors` deve ser alterada.

Antes de chamar `updateTutor(tutor)`, confirme se o tutor representa um registro já existente e se o identificador foi carregado corretamente.

---

### Erro de permissão no Supabase

Se o Supabase retornar erro de permissão, o problema pode estar relacionado às políticas de segurança da tabela.

Nesse caso, registre ou observe a mensagem de erro retornada. Ela ajuda a entender se a falha ocorreu em leitura, inserção, atualização ou remoção lógica.

As permissões do Supabase podem depender de configurações como autenticação e políticas de Row Level Security. O importante, neste material, é saber que um erro de permissão não significa necessariamente erro na controller. Ele pode estar na configuração da tabela remota.

---

## Checklist explicado de validação

### Verifique se a TutorController usa SupabaseTutorRepository como padrão

O que verificar: confirme se o construtor da controller instancia `SupabaseTutorRepository()` quando nenhum repository é passado.

Por que importa: essa é a alteração central da integração. Sem ela, as telas podem continuar usando SQLite.

Como validar: abra `tutor_controller.dart` e confira o construtor.

O que acontece se faltar: a aplicação pode continuar funcionando, mas usando dados locais em vez de dados remotos.

---

### Verifique se os imports da controller estão corretos

O que verificar: confirme se o import do `SupabaseTutorRepository` foi adicionado e se o import do `SqliteTutorRepository` foi removido quando não for mais usado.

Por que importa: o Dart precisa conhecer a classe usada no construtor. Imports desnecessários também confundem a leitura do código.

Como validar: rode o projeto e observe se há erro de compilação relacionado a classes não encontradas ou imports não usados.

O que acontece se faltar: o projeto pode não compilar, ou a controller pode continuar dependendo de uma implementação antiga.

---

### Verifique se a listagem cria a controller sem forçar SQLite

O que verificar: procure na tela de listagem se existe algo como `TutorController(repository: SqliteTutorRepository())`.

Por que importa: quando um repository é passado explicitamente, ele substitui o padrão do construtor.

Como validar: revise `tutor_list_page.dart` e busque por `TutorController`.

O que acontece se faltar: a listagem pode continuar usando SQLite mesmo após a mudança no construtor.

---

### Verifique se o formulário retorna true após salvar

O que verificar: confirme se, após cadastro ou edição bem-sucedida, o formulário executa `Navigator.pop(context, true)`.

Por que importa: a tela de listagem precisa receber um sinal de que houve alteração nos dados.

Como validar: salve um tutor e confira se a listagem atualiza ao voltar.

O que acontece se faltar: o registro pode ser salvo no Supabase, mas a lista pode continuar desatualizada na interface.

---

### Verifique se a listagem chama refresh ao receber true

O que verificar: confirme se a tela de listagem captura o retorno do formulário e chama `refresh()` quando `result == true`.

Por que importa: sem recarregamento, a tela não busca novamente os dados remotos.

Como validar: cadastre ou edite um tutor e veja se a alteração aparece imediatamente na listagem.

O que acontece se faltar: o usuário pode precisar sair e entrar novamente na tela para ver os dados atualizados.

---

### Verifique se o método refresh reinicia o estado da listagem

O que verificar: confirme se o método limpa a lista, reinicia o offset, redefine o controle de existência de mais dados, limpa erros antigos e chama o carregamento.

Por que importa: apenas chamar `loadTutors()` pode não ser suficiente quando há paginação ou estado acumulado.

Como validar: depois de cadastrar um tutor, observe se a listagem não duplica registros e se carrega desde o início.

O que acontece se faltar: podem surgir dados duplicados, paginação incorreta ou mensagens de erro antigas.

---

### Verifique se a remoção é lógica

O que verificar: confirme se a remoção preenche `deleted_at` em vez de apagar fisicamente o registro.

Por que importa: o material trabalha com remoção lógica, mantendo o registro no banco para histórico.

Como validar: remova um tutor e confira no Supabase se o registro continua existindo com `deleted_at` preenchido.

O que acontece se faltar: o registro pode ser apagado definitivamente ou continuar aparecendo na listagem.

---

## Síntese final

A feature Tutor passa a usar Supabase quando a `TutorController` troca sua implementação padrão de `SqliteTutorRepository` para `SupabaseTutorRepository`.

Essa alteração funciona bem porque a controller depende do contrato `TutorRepository`. As telas continuam usando a controller normalmente, e a controller continua chamando os mesmos métodos. O que muda é a implementação concreta responsável por acessar os dados.

Para a integração ficar completa, não basta trocar o repository. Também é necessário garantir que a listagem seja atualizada após cadastro ou edição. Por isso, o formulário deve retornar `true` após salvar, e a listagem deve chamar `refresh()` ao receber esse retorno.

A validação deve cobrir quatro operações principais: listagem, cadastro, edição e remoção lógica. Cada uma confirma uma parte do fluxo real com Supabase.

---

## Conclusão

A integração com Supabase transforma a feature Tutor em uma funcionalidade conectada a uma base remota. A aplicação deixa de apenas ter uma estrutura preparada para acesso remoto e passa a usar essa estrutura no fluxo real.

A tela de listagem e o formulário continuam trabalhando com a `TutorController`. A `TutorController` continua trabalhando com o contrato `TutorRepository`. A diferença é que a implementação concreta do repository agora acessa a tabela `tutors` no Supabase.

Esse desenho preserva a organização da arquitetura, reduz mudanças nas telas e permite evoluir a aplicação com mais segurança.
