# Adaptando o Model `Tutor` para Dados Remotos com Supabase

## Objetivo do material

Neste material, você aprenderá a adaptar a classe `Tutor` para trabalhar com dados vindos de duas origens diferentes: a base local SQLite e a base remota Supabase. O foco é criar métodos específicos para converter os dados entre o formato usado no Flutter e o formato usado na tabela `tutors` no Supabase, sem remover os métodos que já funcionam com SQLite. 

Ao final, a classe `Tutor` será capaz de:

* manter a conversão local com `toMap()` e `fromMap()`;
* enviar dados para o Supabase com os nomes corretos das colunas;
* reconstruir um objeto `Tutor` a partir dos dados retornados pelo Supabase;
* lidar com diferenças de nomes entre Dart/Flutter e PostgreSQL;
* tratar datas nulas e identificadores de forma mais segura;
* usar `copyWith()` para criar cópias modificadas do objeto.

---

# 1. Contextualização do problema

Em uma aplicação Flutter, é comum representar os dados usando classes Dart. Por exemplo, um tutor pode ser representado por uma classe chamada `Tutor`, com atributos como `nome`, `email`, `telefone`, `createdAt`, `updatedAt` e `deletedAt`.

Quando esses dados são salvos localmente com SQLite, a aplicação usa um formato de mapa, geralmente `Map<String, dynamic>`, compatível com a estrutura local do projeto.

Quando os mesmos dados precisam ser enviados para o Supabase, surge um detalhe importante: os nomes dos campos no Dart podem ser diferentes dos nomes das colunas no PostgreSQL.

No Dart, é comum usar o padrão `camelCase`, como:

```dart
tutorId
createdAt
updatedAt
deletedAt
```

No Supabase/PostgreSQL, é comum usar o padrão `snake_case`, como:

```sql
tutor_id
created_at
updated_at
deleted_at
```

Essa diferença não impede a integração, mas exige uma camada de conversão. Sem essa conversão, a aplicação pode tentar enviar campos com nomes que não existem na tabela remota, causando erros de inserção, atualização ou leitura.

---

# 2. Por que adaptar o model antes do datasource remoto?

Antes de criar um datasource remoto, a aplicação precisa saber transformar seus objetos em dados compatíveis com o banco remoto.

O datasource remoto será responsável por acessar o Supabase, fazer consultas, inserir registros, atualizar dados e recuperar informações. Porém, ele não deve carregar sozinho toda a responsabilidade de “traduzir” os nomes dos campos.

Essa tradução pertence ao model, porque o model representa a estrutura dos dados e sabe como transformar um objeto em mapa e um mapa em objeto.

A adaptação do model evita duplicação de código. Em vez de espalhar conversões por várias classes, a regra fica centralizada na própria classe `Tutor`.

---

# 3. Conceitos fundamentais

## Classe model

Uma classe model representa uma entidade do domínio da aplicação. Neste caso, a entidade é um tutor.

A classe `Tutor` concentra os dados principais de um tutor e define como esses dados são construídos, copiados e convertidos.

Exemplo simplificado:

```dart
class Tutor {
  final int? tutorId;
  final String nome;
  final String email;
  final String telefone;
  final DateTime createdAt;
  final DateTime updatedAt;
  final DateTime? deletedAt;

  Tutor({
    this.tutorId,
    required this.nome,
    required this.email,
    required this.telefone,
    required this.createdAt,
    required this.updatedAt,
    this.deletedAt,
  });
}
```

Observe que `tutorId` e `deletedAt` são opcionais. Isso faz sentido porque um tutor novo pode ainda não ter identificador gerado pelo banco, e um tutor ativo normalmente não possui data de exclusão.

---

## `Map<String, dynamic>`

Em Flutter, um `Map<String, dynamic>` é uma estrutura muito usada para representar dados vindos de bancos, APIs ou arquivos.

A chave do mapa é uma `String`, geralmente o nome do campo ou da coluna. O valor é `dynamic`, porque pode variar entre `String`, `int`, `DateTime`, `null` ou outros tipos.

Exemplo:

```dart
final map = {
  'nome': 'Marcos Pereira',
  'email': 'marcos.pereira@email.com',
  'telefone': '(45) 99999-1001',
};
```

Esse mapa representa dados de um tutor, mas ainda não é um objeto `Tutor`. Para transformar esse mapa em objeto, usamos um método como `fromMap()` ou `fromSupabaseMap()`.

---

## Conversão nos dois sentidos

A conversão precisa acontecer em dois sentidos:

Quando a aplicação envia dados para o banco, ela transforma um objeto `Tutor` em `Map<String, dynamic>`.

Quando a aplicação recebe dados do banco, ela transforma um `Map<String, dynamic>` em um objeto `Tutor`.

Esses dois movimentos são essenciais:

```text
Objeto Tutor → Map<String, dynamic> → Banco de dados
Banco de dados → Map<String, dynamic> → Objeto Tutor
```

Se a conversão estiver incorreta, a aplicação pode salvar campos errados, perder informações ou quebrar em tempo de execução.

---

# 4. Diferenças entre o formato do Flutter e o formato do Supabase

A principal diferença está nos nomes dos campos.

| Dart / Flutter | Supabase / PostgreSQL |
| -------------- | --------------------- |
| `tutorId`      | `tutor_id`            |
| `nome`         | `nome`                |
| `email`        | `email`               |
| `telefone`     | `telefone`            |
| `createdAt`    | `created_at`          |
| `updatedAt`    | `updated_at`          |
| `deletedAt`    | `deleted_at`          |

Os campos `nome`, `email` e `telefone` permanecem com o mesmo nome. Já o identificador e as datas mudam de padrão.

Essa distinção é importante porque o Supabase espera receber os nomes exatamente como foram definidos na tabela. Se a tabela possui a coluna `created_at`, enviar `createdAt` não terá o mesmo efeito.

---

# 5. Mantendo os métodos do SQLite

A classe `Tutor` já possui métodos usados para persistência local com SQLite:

```dart
Map<String, dynamic> toMap()
```

e

```dart
factory Tutor.fromMap(Map<String, dynamic> map)
```

Esses métodos devem ser mantidos.

Eles continuam úteis porque a aplicação ainda pode usar armazenamento local. Além disso, em projetos que trabalham com dados locais e remotos, esses métodos podem ser importantes em etapas futuras de sincronização.

A ideia não é substituir `toMap()` e `fromMap()`. A ideia é adicionar novos métodos específicos para Supabase.

A separação fica assim:

```text
SQLite:
- toMap()
- fromMap()

Supabase:
- toSupabaseMap()
- toSupabaseMapWithId()
- fromSupabaseMap()
```

Essa organização deixa claro qual conversão pertence a cada tipo de persistência.

---

# 6. Métodos que serão adicionados à classe `Tutor`

A classe `Tutor` passará a ter quatro novos membros principais relacionados ao Supabase:

## `toSupabaseMap()`

Converte o objeto `Tutor` em um mapa compatível com o Supabase, sem incluir o campo `tutor_id`.

Esse método é usado principalmente para inserção de novos registros.

## `toSupabaseMapWithId()`

Converte o objeto `Tutor` em um mapa compatível com o Supabase, incluindo o campo `tutor_id`.

Esse método pode ser útil em cenários específicos, especialmente quando for necessário gerar uma representação completa do objeto.

## `fromSupabaseMap()`

Reconstrói um objeto `Tutor` a partir de um mapa retornado pelo Supabase.

Esse método lê os nomes das colunas remotas, como `tutor_id`, `created_at`, `updated_at` e `deleted_at`.

## `_parseNullableInt()`

Método auxiliar privado usado para converter o identificador de forma mais segura.

Ele trata casos em que o valor pode vir como `int`, `num`, `String` ou `null`.

---

# 7. Método `toSupabaseMap()`

O método `toSupabaseMap()` é usado quando a aplicação precisa enviar um novo tutor para o Supabase.

```dart
Map<String, dynamic> toSupabaseMap() {
  return {
    'nome': nome,
    'email': email,
    'telefone': telefone,
    'created_at': createdAt.toIso8601String(),
    'updated_at': updatedAt.toIso8601String(),
    'deleted_at': deletedAt?.toIso8601String(),
  };
}
```

Esse método não inclui `tutor_id`.

Isso acontece porque a tabela `tutors` foi criada com o campo `tutor_id` como identificador gerado pelo banco. Em uma estrutura desse tipo, o banco é responsável por criar o identificador no momento da inserção.

Por isso, ao inserir um tutor novo, o aplicativo envia apenas os dados necessários:

```dart
'nome'
'email'
'telefone'
'created_at'
'updated_at'
'deleted_at'
```

O banco gera o `tutor_id`.

---

## Comentário do código

A linha abaixo envia o nome sem alteração, porque o campo tem o mesmo nome no Dart e no Supabase:

```dart
'nome': nome,
```

O mesmo acontece com `email` e `telefone`.

Já as datas precisam ser convertidas para texto no formato ISO 8601:

```dart
'created_at': createdAt.toIso8601String(),
```

Essa conversão é importante porque `DateTime` é um tipo do Dart, enquanto o banco recebe e retorna datas em formatos serializáveis. O método `toIso8601String()` transforma a data em uma representação textual padronizada.

O campo `deleted_at` pode ser nulo:

```dart
'deleted_at': deletedAt?.toIso8601String(),
```

O operador `?.` significa: se `deletedAt` não for nulo, execute `toIso8601String()`; se for nulo, mantenha o valor como `null`.

Isso evita erro ao tentar converter uma data inexistente.

---

# 8. Método `toSupabaseMapWithId()`

O método `toSupabaseMapWithId()` gera um mapa incluindo o identificador.

```dart
Map<String, dynamic> toSupabaseMapWithId() {
  return {
    'tutor_id': tutorId,
    'nome': nome,
    'email': email,
    'telefone': telefone,
    'created_at': createdAt.toIso8601String(),
    'updated_at': updatedAt.toIso8601String(),
    'deleted_at': deletedAt?.toIso8601String(),
  };
}
```

A diferença em relação ao método anterior está nesta linha:

```dart
'tutor_id': tutorId,
```

Esse método não deve ser a escolha principal para inserir novos tutores, porque novos registros normalmente devem deixar o banco gerar o identificador.

Para inserção, use:

```dart
toSupabaseMap()
```

Para cenários em que seja necessário representar o objeto completo, incluindo o ID, use:

```dart
toSupabaseMapWithId()
```

Em atualizações no Supabase, geralmente o identificador é usado na condição da consulta, não necessariamente no corpo enviado. Por exemplo, uma atualização pode usar o ID para localizar o registro e enviar apenas os campos alterados.

# 9. Método `fromSupabaseMap()`

O método `fromSupabaseMap()` é usado quando o Supabase retorna dados da tabela `tutors`.

A versão direta do método seria:

```dart
factory Tutor.fromSupabaseMap(Map<String, dynamic> map) {
  return Tutor(
    tutorId: map['tutor_id'] as int?,
    nome: map['nome'] as String,
    email: map['email'] as String,
    telefone: map['telefone'] as String,
    createdAt: DateTime.parse(map['created_at'] as String),
    updatedAt: DateTime.parse(map['updated_at'] as String),
    deletedAt: map['deleted_at'] != null
        ? DateTime.parse(map['deleted_at'] as String)
        : null,
  );
}
```

Esse factory lê os campos usando os nomes da tabela remota.

Por exemplo, ele lê:

```dart
map['tutor_id']
map['created_at']
map['updated_at']
map['deleted_at']
```

e transforma esses valores nos atributos Dart:

```dart
tutorId
createdAt
updatedAt
deletedAt
```

---

## Cuidados com datas

As datas `created_at` e `updated_at` são obrigatórias. Por isso, o código usa:

```dart
DateTime.parse(map['created_at'] as String)
```

e:

```dart
DateTime.parse(map['updated_at'] as String)
```

O campo `deleted_at`, por outro lado, pode ser nulo. Por isso, ele precisa ser verificado antes da conversão:

```dart
deletedAt: map['deleted_at'] != null
    ? DateTime.parse(map['deleted_at'] as String)
    : null,
```

Essa verificação é essencial. Chamar `DateTime.parse()` em um valor nulo causará erro em tempo de execução.

---

# 10. Conversão robusta do identificador com `_parseNullableInt()`

Dependendo de como o dado é retornado, o campo `tutor_id` pode chegar como `int`, como outro tipo numérico ou até como texto numérico.

Para evitar erro de conversão, usamos um método auxiliar:

```dart
static int? _parseNullableInt(dynamic value) {
  if (value == null) return null;
  if (value is int) return value;
  if (value is num) return value.toInt();
  return int.tryParse(value.toString());
}
```

Esse método recebe um valor dinâmico e tenta convertê-lo para `int?`.

A lógica é a seguinte:

Se o valor for `null`, retorna `null`:

```dart
if (value == null) return null;
```

Se o valor já for `int`, retorna o próprio valor:

```dart
if (value is int) return value;
```

Se o valor for outro número, como `num`, converte para inteiro:

```dart
if (value is num) return value.toInt();
```

Se o valor vier como texto, tenta converter:

```dart
return int.tryParse(value.toString());
```

O uso de `tryParse()` é mais seguro que `parse()`, porque `tryParse()` retorna `null` se não conseguir converter, enquanto `parse()` lança erro.

---

# 11. `fromSupabaseMap()` com conversão mais segura

Com `_parseNullableInt()`, o método `fromSupabaseMap()` fica mais robusto:

```dart
factory Tutor.fromSupabaseMap(Map<String, dynamic> map) {
  return Tutor(
    tutorId: _parseNullableInt(map['tutor_id']),
    nome: map['nome'] as String,
    email: map['email'] as String,
    telefone: map['telefone'] as String,
    createdAt: DateTime.parse(map['created_at'] as String),
    updatedAt: DateTime.parse(map['updated_at'] as String),
    deletedAt: map['deleted_at'] != null
        ? DateTime.parse(map['deleted_at'] as String)
        : null,
  );
}
```

A principal mudança está aqui:

```dart
tutorId: _parseNullableInt(map['tutor_id']),
```

Em vez de forçar:

```dart
map['tutor_id'] as int?
```

o código passa a aceitar variações de tipo e tenta convertê-las com segurança.

Essa abordagem reduz a chance de erro caso o retorno do banco tenha alguma diferença de tipo.

# 12. Classe `Tutor` ajustada com os métodos para Supabase

A estrutura geral da classe fica assim:

```dart
class Tutor {
  final int? tutorId;
  final String nome;
  final String email;
  final String telefone;
  final DateTime createdAt;
  final DateTime updatedAt;
  final DateTime? deletedAt;

  Tutor({
    this.tutorId,
    required this.nome,
    required this.email,
    required this.telefone,
    required this.createdAt,
    required this.updatedAt,
    this.deletedAt,
  });

  // SQLite
  Map<String, dynamic> toMap() {
    // Implementação já existente no projeto
    throw UnimplementedError();
  }

  factory Tutor.fromMap(Map<String, dynamic> map) {
    // Implementação já existente no projeto
    throw UnimplementedError();
  }

  // Supabase
  Map<String, dynamic> toSupabaseMap() {
    return {
      'nome': nome,
      'email': email,
      'telefone': telefone,
      'created_at': createdAt.toIso8601String(),
      'updated_at': updatedAt.toIso8601String(),
      'deleted_at': deletedAt?.toIso8601String(),
    };
  }

  Map<String, dynamic> toSupabaseMapWithId() {
    return {
      'tutor_id': tutorId,
      'nome': nome,
      'email': email,
      'telefone': telefone,
      'created_at': createdAt.toIso8601String(),
      'updated_at': updatedAt.toIso8601String(),
      'deleted_at': deletedAt?.toIso8601String(),
    };
  }

  factory Tutor.fromSupabaseMap(Map<String, dynamic> map) {
    return Tutor(
      tutorId: _parseNullableInt(map['tutor_id']),
      nome: map['nome'] as String,
      email: map['email'] as String,
      telefone: map['telefone'] as String,
      createdAt: DateTime.parse(map['created_at'] as String),
      updatedAt: DateTime.parse(map['updated_at'] as String),
      deletedAt: map['deleted_at'] != null
          ? DateTime.parse(map['deleted_at'] as String)
          : null,
    );
  }

  static int? _parseNullableInt(dynamic value) {
    if (value == null) return null;
    if (value is int) return value;
    if (value is num) return value.toInt();
    return int.tryParse(value.toString());
  }
}
```

Os métodos `toMap()` e `fromMap()` aparecem apenas como indicação, porque devem preservar a implementação local já existente no projeto. O ponto principal é que os métodos do Supabase são adicionados ao lado dos métodos do SQLite, não no lugar deles.

# 13. Método `copyWith()`

O método `copyWith()` permite criar uma nova versão de um objeto alterando apenas alguns campos.

Isso é útil porque os atributos da classe `Tutor` são `final`. Ou seja, depois que o objeto é criado, seus campos não devem ser modificados diretamente.

Em vez de alterar o objeto existente, criamos uma cópia com os campos desejados modificados.

```dart
Tutor copyWith({
  int? tutorId,
  String? nome,
  String? email,
  String? telefone,
  DateTime? createdAt,
  DateTime? updatedAt,
  DateTime? deletedAt,
}) {
  return Tutor(
    tutorId: tutorId ?? this.tutorId,
    nome: nome ?? this.nome,
    email: email ?? this.email,
    telefone: telefone ?? this.telefone,
    createdAt: createdAt ?? this.createdAt,
    updatedAt: updatedAt ?? this.updatedAt,
    deletedAt: deletedAt ?? this.deletedAt,
  );
}
```

Exemplo de uso:

```dart
final tutorAtualizado = tutor.copyWith(
  updatedAt: DateTime.now(),
);
```

Nesse exemplo, a aplicação cria uma nova versão do tutor com a data de atualização modificada. Os demais campos permanecem iguais.

Esse tipo de operação é comum antes de enviar uma atualização ao Supabase, porque o campo `updatedAt` deve refletir o momento da alteração.

---

## Limitação do `copyWith()` apresentado

O `copyWith()` mostrado usa o operador `??`.

Isso significa que, se o valor passado for `null`, o método mantém o valor antigo.

Exemplo:

```dart
deletedAt: deletedAt ?? this.deletedAt,
```

Esse comportamento tem uma limitação: ele não permite limpar `deletedAt` definindo o campo como `null`, caso ele já tenha um valor.

Para esta etapa, isso não é um problema, porque a exclusão lógica normalmente preenche `deletedAt`, em vez de limpar esse campo.

Em cenários mais avançados, pode ser necessário criar uma versão de `copyWith()` capaz de diferenciar duas intenções:

```text
não alterar o campo
alterar o campo para null
```

Essa distinção é importante quando um campo nulo pode representar uma operação real, e não apenas ausência de alteração.

# 14. Aplicação prática resolvida: convertendo um tutor para Supabase

## Cenário

A aplicação possui um objeto `Tutor` criado no Flutter e precisa preparar os dados para inserção no Supabase.

## Objetivo

Converter o objeto `Tutor` em um `Map<String, dynamic>` com os nomes das colunas da tabela remota.

## Solução

```dart
final tutor = Tutor(
  nome: 'Marcos Pereira',
  email: 'marcos.pereira@email.com',
  telefone: '(45) 99999-1001',
  createdAt: DateTime.now(),
  updatedAt: DateTime.now(),
);

final map = tutor.toSupabaseMap();

debugPrint(map.toString());
```

## Comentário da solução

O objeto `Tutor` usa os atributos da classe Dart. Ao chamar `toSupabaseMap()`, o objeto é transformado em um mapa com as chaves esperadas pelo Supabase.

O campo `tutor_id` não aparece, porque o registro ainda será criado no banco remoto. O identificador será gerado pela própria tabela.

## Resultado esperado

O resultado esperado será um mapa semelhante a este:

```dart
{
  nome: Marcos Pereira,
  email: marcos.pereira@email.com,
  telefone: (45) 99999-1001,
  created_at: 2026-...,
  updated_at: 2026-...,
  deleted_at: null
}
```

As datas reais dependem do momento em que o código for executado.

## Como validar

A validação deve observar se:

* as chaves estão em `snake_case` quando pertencem ao Supabase;
* `created_at` e `updated_at` aparecem como texto no formato ISO;
* `deleted_at` aparece como `null` quando o tutor não foi excluído;
* `tutor_id` não aparece no mapa de inserção.

## Possíveis erros

Um erro comum seria enviar `createdAt` em vez de `created_at`. Nesse caso, o Supabase não receberia a coluna esperada.

Outro erro seria incluir `tutor_id` na inserção de um novo registro, mesmo quando o banco deve gerar esse valor automaticamente.

# 15. Aplicação prática resolvida: reconstruindo um tutor vindo do Supabase

## Cenário

O Supabase retornou um mapa com os dados de um tutor armazenado na tabela `tutors`.

## Objetivo

Transformar o mapa retornado pelo Supabase em um objeto `Tutor`.

## Solução

```dart
final map = {
  'tutor_id': 1,
  'nome': 'Beatriz Souza',
  'email': 'beatriz.souza@email.com',
  'telefone': '(45) 99999-1002',
  'created_at': DateTime.now().toIso8601String(),
  'updated_at': DateTime.now().toIso8601String(),
  'deleted_at': null,
};

final tutor = Tutor.fromSupabaseMap(map);

debugPrint(tutor.nome);
debugPrint(tutor.email);
```

## Comentário da solução

O mapa usa os nomes das colunas da tabela remota. O factory `fromSupabaseMap()` lê esses nomes e cria um objeto `Tutor`.

A linha abaixo converte o identificador com segurança:

```dart
tutorId: _parseNullableInt(map['tutor_id']),
```

As datas são reconstruídas com:

```dart
DateTime.parse(...)
```

O campo `deleted_at` é verificado antes da conversão, porque pode ser nulo.

## Resultado esperado

A saída esperada no console será:

```text
Beatriz Souza
beatriz.souza@email.com
```

Isso confirma que a aplicação conseguiu reconstruir um objeto `Tutor` a partir de um mapa remoto.

## Como validar

A validação deve verificar se:

* `tutor.tutorId` recebeu o valor `1`;
* `tutor.nome` recebeu `Beatriz Souza`;
* `tutor.email` recebeu `beatriz.souza@email.com`;
* `tutor.deletedAt` permaneceu `null`;
* `createdAt` e `updatedAt` foram convertidos para objetos `DateTime`.

## Possíveis erros

Um erro comum é tentar ler `map['tutorId']` em vez de `map['tutor_id']`. Como o mapa vem do Supabase, a chave correta é `tutor_id`.

Outro erro é tentar converter `deleted_at` diretamente com `DateTime.parse()` sem verificar se o valor é nulo.

# 16. Erros comuns e dúvidas frequentes

## Remover `toMap()` e `fromMap()`

Não remova os métodos usados pelo SQLite. Eles continuam sendo necessários para persistência local.

O correto é adicionar os métodos do Supabase ao lado dos métodos já existentes.

---

## Usar `toSupabaseMapWithId()` para inserir novos registros

Para inserção de novos tutores, o método mais adequado é:

```dart
toSupabaseMap()
```

O método `toSupabaseMapWithId()` inclui o identificador e deve ser reservado para cenários específicos.

Quando o banco gera o ID automaticamente, enviar o identificador manualmente pode causar conflitos ou comportamento inesperado.

---

## Esquecer de converter datas para ISO 8601

Ao enviar dados para o Supabase, use:

```dart
createdAt.toIso8601String()
```

e:

```dart
updatedAt.toIso8601String()
```

Isso padroniza a representação das datas e facilita o envio para o banco.

---

## Fazer `DateTime.parse()` em valor nulo

Nunca faça:

```dart
DateTime.parse(map['deleted_at'] as String)
```

sem verificar se `deleted_at` é nulo.

O correto é:

```dart
deletedAt: map['deleted_at'] != null
    ? DateTime.parse(map['deleted_at'] as String)
    : null,
```

---

## Forçar o tipo do identificador sem cuidado

Evite depender apenas de:

```dart
map['tutor_id'] as int?
```

Essa conversão pode falhar se o valor vier em outro formato numérico compatível.

A alternativa mais segura é:

```dart
_parseNullableInt(map['tutor_id'])
```

## Misturar regras do SQLite com regras do Supabase

Cada persistência deve ter sua própria conversão.

O SQLite pode usar um formato local. O Supabase usa os nomes da tabela remota. Misturar essas regras deixa o código mais frágil e difícil de manter.

# 18. Síntese final

A adaptação da classe `Tutor` para dados remotos consiste em adicionar métodos específicos para converter dados entre o formato usado no Flutter e o formato usado no Supabase.

A classe passa a ter dois conjuntos de conversão:

```text
SQLite:
- toMap()
- fromMap()

Supabase:
- toSupabaseMap()
- toSupabaseMapWithId()
- fromSupabaseMap()
- _parseNullableInt()
```

O método `toSupabaseMap()` prepara dados para inserção sem enviar o ID.

O método `toSupabaseMapWithId()` gera um mapa completo incluindo o identificador.

O método `fromSupabaseMap()` reconstrói um objeto `Tutor` a partir dos dados retornados pelo banco remoto.

O método `_parseNullableInt()` protege a conversão do identificador contra variações de tipo.

O método `copyWith()` facilita criar uma nova versão do objeto alterando apenas os campos necessários.
