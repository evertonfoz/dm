# Tratamento de Erros Profissional em NestJS: padronizando e otimizando APIs REST

## Objetivo do material

Neste material, você aprenderá a tratar erros em APIs REST desenvolvidas com NestJS de forma clara, previsível, segura e padronizada. O foco é compreender como usar corretamente exceções nativas do NestJS, diferenciar tipos de erro, evitar mensagens técnicas expostas ao cliente e criar um filtro global de exceções para manter um formato único de resposta em toda a aplicação. O conteúdo foi desenvolvido a partir do material-base enviado sobre tratamento profissional de erros em NestJS. 

Ao final, você deverá ser capaz de:

* escolher o código HTTP adequado para cada falha;
* usar exceções como `NotFoundException`, `ConflictException`, `UnauthorizedException` e `ForbiddenException`;
* separar erros de negócio de erros técnicos;
* construir respostas de erro mais úteis para o frontend;
* implementar e registrar um filtro global de exceções;
* validar se a API está retornando erros de forma profissional.

---

## 1. Por que o tratamento de erros é essencial em uma API

Uma API profissional não é avaliada apenas pelas respostas de sucesso. Em sistemas reais, muitas situações podem falhar: um usuário pode não existir, um e-mail pode já estar cadastrado, uma senha pode estar incorreta, um token pode estar ausente ou uma regra de negócio pode impedir determinada operação.

Quando esses cenários não são tratados corretamente, o consumidor da API recebe respostas genéricas, como:

```json
{
  "message": "Internal server error"
}
```

ou:

```json
{
  "error": "Something went wrong"
}
```

Essas mensagens são pouco úteis porque não explicam o que aconteceu, não indicam claramente se o erro foi causado pelo cliente ou pelo servidor e dificultam o tratamento automático no frontend. Uma aplicação frontend depende das respostas da API para decidir, por exemplo, se deve mostrar uma mensagem de validação, redirecionar para a tela de login, bloquear uma ação ou exibir uma tela de acesso negado.

Tratar erros corretamente significa transformar falhas em respostas compreensíveis, seguras e previsíveis.

---

## 2. O papel dos códigos HTTP no tratamento de erros

O código HTTP deve representar a natureza do problema ocorrido. Ele funciona como um sinal padronizado entre backend, frontend e qualquer outro consumidor da API.

Quando uma API retorna um código incorreto, o frontend pode tomar decisões erradas. Por exemplo, se uma senha inválida retorna `500 Internal Server Error`, o frontend pode interpretar que o servidor quebrou, quando na verdade o problema foi uma credencial inválida enviada pelo usuário.

A tabela a seguir apresenta os principais códigos usados no material:

| Código HTTP | Significado              | Quando usar                                                                                 |
| ----------- | ------------------------ | ------------------------------------------------------------------------------------------- |
| `400`       | Requisição inválida      | Quando os dados enviados estão malformados, ausentes ou inválidos.                          |
| `401`       | Não autenticado          | Quando o usuário não enviou token, enviou token inválido ou não possui autenticação válida. |
| `403`       | Sem permissão            | Quando o usuário está autenticado, mas não tem autorização para acessar o recurso.          |
| `404`       | Recurso não encontrado   | Quando a entidade solicitada não existe no banco ou no contexto da aplicação.               |
| `409`       | Conflito de negócio      | Quando a operação viola uma regra, como e-mail duplicado ou conflito de estado.             |
| `500`       | Erro interno do servidor | Quando ocorre uma falha inesperada que não deve ser exposta ao cliente.                     |

A escolha correta do código HTTP ajuda o frontend a tratar cada cenário de forma adequada. Um `401`, por exemplo, pode levar ao redirecionamento para login. Um `403` pode exibir uma mensagem de acesso negado. Um `404` pode mostrar que o recurso não existe. Um `409` pode informar que existe um conflito com uma regra de negócio.

## 3. Exceções nativas do NestJS

O NestJS fornece exceções prontas para uso no pacote `@nestjs/common`. Essas exceções já associam a mensagem ao código HTTP adequado, evitando que o desenvolvedor precise montar manualmente cada resposta.

Exemplo de importação:

```typescript
import {
  BadRequestException,
  UnauthorizedException,
  ForbiddenException,
  NotFoundException,
  ConflictException,
} from '@nestjs/common';
```

Cada exceção deve ser usada em um cenário específico.

A `BadRequestException` representa erro de requisição inválida. Ela é adequada quando os dados enviados pelo cliente estão ausentes, malformados ou não respeitam o formato esperado.

A `UnauthorizedException` representa ausência ou falha de autenticação. Ela deve ser usada quando a API não consegue confirmar quem é o usuário, por exemplo, por token ausente, token inválido ou credenciais incorretas.

A `ForbiddenException` representa falta de autorização. Ela deve ser usada quando o usuário está autenticado, mas não tem permissão para realizar determinada ação.

A `NotFoundException` representa recurso inexistente. Ela é adequada quando o cliente tenta acessar uma entidade que não foi encontrada, como um usuário, produto, pedido ou registro inexistente.

A `ConflictException` representa conflito com uma regra de negócio ou estado atual do sistema. Um exemplo comum é tentar cadastrar um e-mail que já existe.

## 4. Diferenças importantes entre autenticação, autorização, validação e regra de negócio

Um erro comum no desenvolvimento de APIs é usar o mesmo tipo de erro para situações diferentes. Para evitar isso, é importante separar os conceitos.

**Autenticação** responde à pergunta: “Quem é o usuário?”. Quando não há token, o token é inválido ou as credenciais não conferem, o problema é de autenticação. Nesses casos, geralmente se usa `401 Unauthorized`.

**Autorização** responde à pergunta: “Esse usuário pode fazer isso?”. Um usuário pode estar autenticado, mas não ter permissão para acessar uma rota administrativa. Nesse caso, o erro correto é `403 Forbidden`.

**Validação** verifica se os dados enviados estão corretos em formato, presença e tipo. Por exemplo, um campo obrigatório ausente ou um e-mail em formato inválido podem resultar em `400 Bad Request`.

**Regra de negócio** representa uma condição específica do domínio da aplicação. Por exemplo, um e-mail já cadastrado, uma matrícula duplicada, um produto sem estoque ou uma turma lotada. Em muitos desses casos, pode ser usado `409 Conflict`, pois a operação entra em conflito com o estado atual do sistema.

Separar esses conceitos melhora a manutenção da aplicação, evita respostas ambíguas e permite que o consumidor da API trate cada caso corretamente.

## 5. Tratando erros comuns na prática

### 5.1 Recurso inexistente: usando `NotFoundException`

Quando a aplicação procura um registro e ele não existe, a resposta adequada normalmente é `404 Not Found`.

Exemplo:

```typescript
const user = await this.usersRepository.findById(id);

if (!user) {
  throw new NotFoundException('Usuário não encontrado');
}
```

Esse trecho busca um usuário pelo identificador. Se o repositório não retornar nenhum usuário, a aplicação interrompe o fluxo e lança uma exceção informando que o recurso não foi encontrado.

Resposta gerada pelo NestJS:

```json
{
  "statusCode": 404,
  "message": "Usuário não encontrado",
  "error": "Not Found"
}
```

Esse retorno é melhor do que uma mensagem genérica porque informa exatamente o problema. O frontend pode usar essa resposta para exibir uma mensagem como “Usuário não encontrado” ou redirecionar para uma tela apropriada.

Um erro comum seria retornar `500` nesse caso. A ausência de um usuário pesquisado não significa necessariamente que o servidor falhou. Significa que o recurso solicitado não existe.

---

### 5.2 E-mail duplicado: usando `ConflictException`

Quando uma operação entra em conflito com o estado atual do sistema, pode-se usar `409 Conflict`. Um exemplo clássico é o cadastro de um e-mail já existente.

```typescript
const existingUser = await this.usersRepository.findByEmail(email);

if (existingUser) {
  throw new ConflictException('E-mail já cadastrado');
}
```

O código verifica se já existe um usuário com o e-mail informado. Se existir, a API não deve criar um novo usuário com o mesmo e-mail. Em vez de deixar o banco de dados gerar uma mensagem técnica, a aplicação trata o cenário de forma controlada.

Resposta gerada:

```json
{
  "statusCode": 409,
  "message": "E-mail já cadastrado",
  "error": "Conflict"
}
```

Esse tipo de resposta é importante porque comunica uma regra de negócio de maneira compreensível. O cliente da API não precisa conhecer o nome da constraint do banco nem detalhes internos da implementação.

---

### 5.3 Credenciais inválidas: usando `UnauthorizedException`

Quando a senha está incorreta ou as credenciais não permitem autenticar o usuário, o código adequado é `401 Unauthorized`.

```typescript
if (!passwordIsValid) {
  throw new UnauthorizedException('Credenciais inválidas');
}
```

Resposta gerada:

```json
{
  "statusCode": 401,
  "message": "Credenciais inválidas",
  "error": "Unauthorized"
}
```

A mensagem “Credenciais inválidas” é preferível a mensagens como “Senha incorreta” ou “E-mail não encontrado” em fluxos de login, porque evita revelar qual parte da credencial falhou. Isso reduz pistas indevidas para tentativas de enumeração de usuários.

---

### 5.4 Falta de permissão: usando `ForbiddenException`

Quando o usuário está autenticado, mas não possui permissão para executar determinada ação, usa-se `403 Forbidden`.

```typescript
if (user.role !== 'admin') {
  throw new ForbiddenException('Acesso não permitido');
}
```

Resposta gerada:

```json
{
  "statusCode": 403,
  "message": "Acesso não permitido",
  "error": "Forbidden"
}
```

Esse erro é diferente de `401`. No `401`, a aplicação não reconhece uma autenticação válida. No `403`, a aplicação reconhece o usuário, mas nega a ação por falta de autorização.

## 6. Separando erros técnicos de erros de negócio

Nem todo erro tem a mesma origem. Uma API profissional diferencia erros de negócio de erros técnicos.

Erros de negócio são falhas esperadas dentro das regras da aplicação. Exemplos: e-mail já cadastrado, produto sem estoque, turma lotada, disciplina encerrada ou usuário inexistente. Esses erros devem ser comunicados ao cliente com mensagens claras, pois fazem parte do fluxo normal da aplicação.

Erros técnicos são falhas relacionadas à infraestrutura ou à execução inesperada do sistema. Exemplos: banco indisponível, falha de rede, timeout, erro inesperado de servidor ou indisponibilidade de serviço externo. Esses erros devem ser registrados em logs internos, mas não devem expor detalhes técnicos ao cliente.

A diferença é importante porque erros de negócio ajudam o usuário ou o frontend a corrigir a ação. Já erros técnicos exigem investigação do time de desenvolvimento ou operação.

Exemplo inadequado de exposição técnica:

```json
{
  "message": "duplicate key value violates unique constraint users_email_key"
}
```

Esse retorno revela detalhes do banco de dados e da estrutura interna da aplicação. Além de ser pouco amigável, pode representar risco de segurança.

Exemplo adequado:

```json
{
  "message": "E-mail já cadastrado"
}
```

A mensagem adequada comunica o problema sem expor a implementação interna.

## 7. Padronização das respostas de erro

Uma API profissional deve retornar erros em um formato consistente. Quando cada endpoint retorna um formato diferente, o frontend precisa criar regras especiais para cada caso, aumentando a chance de bugs.

Um formato corporativo comum pode ser:

```json
{
  "success": false,
  "statusCode": 404,
  "message": "Usuário não encontrado",
  "timestamp": "2026-06-07T15:30:00Z",
  "path": "/users/10"
}
```

Cada campo tem uma função:

`success` indica que a operação falhou. Mesmo que o código HTTP já informe isso, esse campo pode facilitar tratamentos genéricos em clientes que padronizam respostas.

`statusCode` informa o código HTTP da falha. Ele permite decisões automáticas no frontend.

`message` apresenta uma descrição compreensível do problema.

`timestamp` registra o momento em que o erro ocorreu. Esse dado é útil para rastreamento e comparação com logs.

`path` indica a rota chamada. Isso facilita a investigação, especialmente quando a mesma aplicação possui muitos endpoints.

Esse padrão melhora a experiência de quem consome a API porque torna as respostas previsíveis. O frontend pode criar uma única função de tratamento de erros em vez de interpretar formatos diferentes para cada rota.

## 8. Criando um filtro global de exceções no NestJS

O filtro global de exceções permite interceptar exceções e transformar a resposta em um formato padronizado. Sem um filtro global, cada controller ou service poderia acabar retornando erros de formas diferentes. Com o filtro, a regra de resposta fica centralizada.

Uma estrutura de pastas adequada é:

```text
src
├── common
│   └── filters
│       └── http-exception.filter.ts
├── auth
├── users
├── products
└── ...
```

A pasta `common` concentra recursos compartilhados por toda a aplicação. O filtro de exceções é um bom candidato para essa pasta porque não pertence exclusivamente a um módulo específico.

Arquivo:

```text
common/filters/http-exception.filter.ts
```

Implementação:

```typescript
import {
  ExceptionFilter,
  Catch,
  ArgumentsHost,
  HttpException,
} from '@nestjs/common';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(
    exception: HttpException,
    host: ArgumentsHost,
  ) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    const request = ctx.getRequest();

    response.status(exception.getStatus()).json({
      success: false,
      statusCode: exception.getStatus(),
      timestamp: new Date().toISOString(),
      path: request.url,
      message: exception.message,
    });
  }
}
```

Esse código funciona da seguinte forma:

`@Catch(HttpException)` informa que o filtro deve capturar exceções do tipo `HttpException`, que é a base de muitas exceções HTTP do NestJS.

`ExceptionFilter` é a interface que define o contrato de um filtro de exceção. Ela exige a implementação do método `catch`.

`ArgumentsHost` fornece acesso ao contexto da requisição. Em uma API HTTP, ele permite obter o objeto de request e response.

`host.switchToHttp()` muda o contexto para HTTP, permitindo trabalhar com os objetos típicos de uma requisição web.

`exception.getStatus()` recupera o código HTTP associado à exceção.

`response.status(...).json(...)` define o código HTTP da resposta e envia o corpo padronizado em JSON.

O campo `timestamp` é gerado no momento do erro. O campo `path` usa `request.url`, permitindo identificar qual rota gerou a falha.

---

## 9. Registrando o filtro global no `main.ts`

Criar o filtro não basta. Ele precisa ser registrado para passar a atuar na aplicação.

No arquivo `main.ts`, registre o filtro com:

```typescript
app.useGlobalFilters(
  new HttpExceptionFilter(),
);
```

Depois desse registro, toda exceção do tipo `HttpException` lançada na aplicação seguirá o formato definido no filtro.

Exemplo: se um service lançar:

```typescript
throw new NotFoundException('Usuário não encontrado');
```

A resposta poderá seguir o padrão:

```json
{
  "success": false,
  "statusCode": 404,
  "timestamp": "2026-06-07T15:30:00Z",
  "path": "/users/10",
  "message": "Usuário não encontrado"
}
```

A vantagem é que o desenvolvedor continua usando exceções simples nos services e controllers, enquanto o filtro global cuida da aparência final da resposta.

## 10. Aplicação prática resolvida: padronizando erros em uma API de usuários

### Cenário

Uma API possui um módulo de usuários com duas operações principais: buscar usuário por ID e criar usuário. A busca deve retornar erro quando o usuário não existir. A criação deve impedir o cadastro de e-mail duplicado.

### Objetivo

Implementar tratamento de erro profissional para os seguintes casos:

* usuário inexistente;
* e-mail já cadastrado;
* retorno padronizado para o frontend.

### Solução

Service de usuários:

```typescript
import {
  Injectable,
  NotFoundException,
  ConflictException,
} from '@nestjs/common';

@Injectable()
export class UsersService {
  constructor(
    private readonly usersRepository: UsersRepository,
  ) {}

  async findById(id: string) {
    const user = await this.usersRepository.findById(id);

    if (!user) {
      throw new NotFoundException('Usuário não encontrado');
    }

    return user;
  }

  async create(data: CreateUserDto) {
    const existingUser = await this.usersRepository.findByEmail(data.email);

    if (existingUser) {
      throw new ConflictException('E-mail já cadastrado');
    }

    return this.usersRepository.create(data);
  }
}
```

Filtro global:

```typescript
import {
  ExceptionFilter,
  Catch,
  ArgumentsHost,
  HttpException,
} from '@nestjs/common';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse();
    const request = ctx.getRequest();

    response.status(exception.getStatus()).json({
      success: false,
      statusCode: exception.getStatus(),
      timestamp: new Date().toISOString(),
      path: request.url,
      message: exception.message,
    });
  }
}
```

Registro no `main.ts`:

```typescript
import { HttpExceptionFilter } from './common/filters/http-exception.filter';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalFilters(new HttpExceptionFilter());

  await app.listen(3000);
}

bootstrap();
```

### Comentário da solução

A regra de usuário inexistente é tratada com `NotFoundException`, porque o recurso solicitado não foi encontrado. A regra de e-mail duplicado é tratada com `ConflictException`, porque a tentativa de criação entra em conflito com o estado atual do sistema.

O filtro global evita repetição de código. Sem ele, cada controller precisaria montar manualmente a resposta. Com ele, o service apenas lança a exceção correta, e a padronização fica centralizada.

### Resultado esperado

Ao chamar uma rota como:

```text
GET /users/10
```

e o usuário não existir, a API deve retornar algo semelhante a:

```json
{
  "success": false,
  "statusCode": 404,
  "timestamp": "2026-06-07T15:30:00Z",
  "path": "/users/10",
  "message": "Usuário não encontrado"
}
```

Ao tentar criar um usuário com e-mail já cadastrado, a API deve retornar:

```json
{
  "success": false,
  "statusCode": 409,
  "timestamp": "2026-06-07T15:31:00Z",
  "path": "/users",
  "message": "E-mail já cadastrado"
}
```

### Como validar

A validação pode ser feita com ferramentas como Postman, Insomnia, Thunder Client ou testes automatizados.

Para validar o `404`, envie uma requisição buscando um ID inexistente e confira se o código HTTP é `404`, se `success` é `false`, se a mensagem é compreensível e se o campo `path` corresponde à rota chamada.

Para validar o `409`, tente cadastrar duas vezes o mesmo e-mail e confira se a segunda tentativa retorna conflito de negócio, e não erro interno do servidor.

### Possíveis erros

Um erro comum é esquecer de registrar o filtro no `main.ts`. Nesse caso, a aplicação continuará usando o formato padrão do NestJS, e o padrão corporativo não será aplicado.

Outro erro comum é lançar `Error` genérico em vez de uma exceção HTTP. Por exemplo:

```typescript
throw new Error('Usuário não encontrado');
```

Esse tipo de erro não carrega automaticamente o código HTTP adequado. Em uma API NestJS, prefira exceções específicas quando o cenário for conhecido.

Também é comum expor mensagens internas do banco de dados. Em vez de deixar uma constraint aparecer no retorno, trate o caso antes e envie uma mensagem amigável.

## 11. Benefícios para o frontend

Quando uma API retorna erros de forma consistente, o frontend ganha previsibilidade.

Mensagens amigáveis podem ser exibidas diretamente ao usuário final, sem necessidade de interpretar detalhes técnicos.

Campos com erro podem ser destacados automaticamente quando a resposta informa problemas de validação.

Notificações automáticas podem ser criadas com base em `statusCode` e `message`.

Logs no frontend podem registrar `timestamp` e `path`, facilitando a investigação de problemas.

Cenários específicos podem ser tratados com regras claras: `401` pode redirecionar para login; `403` pode exibir uma tela de acesso negado; `404` pode mostrar que o recurso não foi encontrado; `409` pode orientar o usuário a resolver um conflito.

Com um padrão único, o frontend não precisa criar tratamentos especiais para cada endpoint. Isso reduz bugs, acelera o desenvolvimento e melhora a comunicação entre as equipes.

## 12. Erros comuns e dúvidas frequentes

### Usar `500` para qualquer falha

Nem toda falha é erro interno do servidor. Se o usuário não existe, use `404`. Se o e-mail já está cadastrado, use `409`. Se faltou autenticação, use `401`. Reservar `500` para erros inesperados torna a API mais precisa.

### Confundir `401` com `403`

Use `401` quando o problema for autenticação ausente ou inválida. Use `403` quando o usuário está autenticado, mas não tem permissão para executar a ação.

### Expor mensagens internas

Mensagens de banco de dados, stack traces, nomes de constraints ou detalhes de infraestrutura não devem ser enviados ao cliente. Essas informações devem ir para logs internos.

### Criar formatos diferentes para cada endpoint

Se cada rota retorna um erro diferente, o frontend fica mais complexo. O ideal é usar um formato único em toda a API.

### Lançar erro genérico em vez de exceção específica

`throw new Error()` não comunica automaticamente o código HTTP adequado. Em cenários conhecidos, use exceções nativas do NestJS.

### Esquecer de testar cenários de falha

Muitos testes focam apenas no sucesso. Uma API profissional também precisa ser validada nos caminhos de erro: recurso inexistente, autenticação inválida, falta de permissão, conflito de negócio e dados inválidos.

## 13. Checklist explicado de validação

### Verifique se `NotFoundException` foi usada para recursos inexistentes

O que verificar: confira se buscas por entidades inexistentes retornam `404`.

Por que importa: um recurso inexistente não deve ser tratado como erro interno do servidor.

Como validar: chame uma rota com um ID inexistente e observe o status da resposta.

O que acontece se faltar: o frontend pode exibir uma mensagem errada ou interpretar que o servidor falhou.

### Verifique se `ConflictException` foi usada para conflitos de negócio

O que verificar: confira se regras como e-mail duplicado retornam `409`.

Por que importa: conflitos indicam que a operação não pode ser concluída no estado atual do sistema.

Como validar: tente repetir uma operação que deve ser única, como cadastrar o mesmo e-mail duas vezes.

O que acontece se faltar: o usuário pode receber uma mensagem técnica ou um erro genérico sem orientação clara.

### Verifique se `UnauthorizedException` foi usada para falhas de autenticação

O que verificar: confira se token ausente, token inválido ou credenciais incorretas retornam `401`.

Por que importa: o frontend precisa saber quando deve solicitar login novamente.

Como validar: faça uma requisição protegida sem token ou com token inválido.

O que acontece se faltar: o usuário pode permanecer em uma tela sem acesso claro ou receber uma mensagem inadequada.

### Verifique se `ForbiddenException` foi usada para falta de permissão

O que verificar: confira se usuários autenticados, mas sem autorização, recebem `403`.

Por que importa: autenticação e autorização são problemas diferentes.

Como validar: acesse uma rota administrativa com um usuário comum.

O que acontece se faltar: a API pode confundir falta de permissão com falta de login.

### Verifique se mensagens internas foram removidas

O que verificar: confira se a API não retorna nomes de tabelas, constraints, stack traces ou detalhes de infraestrutura.

Por que importa: detalhes internos podem gerar risco de segurança e dificultar a experiência do usuário.

Como validar: force cenários como e-mail duplicado e observe se a mensagem é amigável.

O que acontece se faltar: a API pode expor informações sensíveis sobre sua arquitetura.

### Verifique se as respostas estão padronizadas

O que verificar: confirme se todas as respostas de erro seguem o mesmo formato, com campos como `success`, `statusCode`, `message`, `timestamp` e `path`.

Por que importa: o frontend depende de previsibilidade para criar tratamentos reutilizáveis.

Como validar: teste diferentes endpoints e compare o formato das respostas.

O que acontece se faltar: cada rota exigirá um tratamento diferente, aumentando bugs e retrabalho.

### Verifique se o filtro global foi criado

O que verificar: confirme se existe um arquivo de filtro, como `common/filters/http-exception.filter.ts`.

Por que importa: o filtro centraliza a padronização das respostas de erro.

Como validar: revise a estrutura de pastas e confira se o filtro implementa `ExceptionFilter`.

O que acontece se faltar: a padronização pode ficar espalhada pelos controllers e services.

### Verifique se o filtro global foi registrado no `main.ts`

O que verificar: confirme se `app.useGlobalFilters(new HttpExceptionFilter())` foi adicionado ao bootstrap da aplicação.

Por que importa: criar o filtro não é suficiente; ele precisa ser ativado.

Como validar: execute a aplicação e provoque um erro conhecido. A resposta deve seguir o padrão definido no filtro.

O que acontece se faltar: a aplicação continuará retornando o formato padrão do NestJS ou formatos inconsistentes.

### Verifique se diferentes cenários de erro foram testados

O que verificar: teste `400`, `401`, `403`, `404`, `409` e, quando possível, falhas inesperadas.

Por que importa: uma API robusta precisa ser previsível tanto no sucesso quanto na falha.

Como validar: use uma ferramenta de requisição ou testes automatizados para simular cada cenário.

O que acontece se faltar: erros importantes podem aparecer apenas em produção, dificultando diagnóstico e correção.

---

## 14. Síntese final

O tratamento profissional de erros em NestJS depende de três pilares: escolha correta do código HTTP, uso adequado das exceções nativas e padronização das respostas.

As exceções nativas do NestJS simplificam o desenvolvimento porque já representam cenários comuns de falha. `NotFoundException` deve ser usada para recursos inexistentes, `ConflictException` para conflitos de negócio, `UnauthorizedException` para falhas de autenticação e `ForbiddenException` para falta de autorização.

A separação entre erro de negócio e erro técnico evita que a API exponha detalhes internos e melhora a comunicação com o cliente. Erros esperados devem ser comunicados com clareza. Erros técnicos devem ser registrados internamente e tratados com segurança.

O filtro global de exceções centraliza a padronização, reduz repetição e garante que a aplicação inteira siga o mesmo formato de resposta.

---

## Conclusão

Uma API profissional deve ser previsível quando funciona e também quando falha. O tratamento adequado de erros reduz o tempo de diagnóstico, facilita a integração com aplicações frontend, melhora a experiência dos desenvolvedores que consomem a API e aumenta a segurança da aplicação.

Ao usar corretamente as exceções do NestJS, evitar mensagens internas e aplicar um filtro global de exceções, a API passa a comunicar falhas de forma clara, consistente e confiável. Esse padrão torna o sistema mais fácil de manter, mais seguro e mais preparado para evoluir.
