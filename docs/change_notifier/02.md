# Atualizando a Interface com ListenableBuilder e ChangeNotifier no Flutter

## Objetivo do material

Neste material, você aprenderá a atualizar automaticamente uma interface Flutter usando `ListenableBuilder` em conjunto com uma controller baseada em `ChangeNotifier`.

O foco é adaptar uma tela de listagem de pets para que ela reaja às mudanças da `PetController` sem depender de várias chamadas manuais de `setState`. A tela continuará sendo responsável por mostrar os dados, os estados de carregamento, erro, lista vazia e lista preenchida, enquanto a controller ficará responsável por armazenar o estado e avisar quando ele mudar.

Ao final, você deverá compreender:

* por que a controller deve ser criada no `initState`;
* por que ela deve ser liberada no `dispose`;
* como o `ListenableBuilder` escuta mudanças da controller;
* como tratar loading, erro, lista vazia e lista com dados;
* como cadastrar e remover itens sem chamar `setState`;
* como validar se a interface está reagindo corretamente às mudanças.

O conteúdo parte da ideia de que a `PetController` já herda de `ChangeNotifier` e já chama `notifyListeners()` quando alguma informação relevante muda. Essa é a base apresentada no material original, que indica que a controller passou a avisar a interface quando há mudanças e que agora a tela será adaptada para escutar essas mudanças com `ListenableBuilder` .

---

## 1. Contextualização do problema

Em aplicações Flutter, a interface visual é construída a partir de estados. Quando uma informação muda, a tela precisa ser reconstruída para mostrar o novo valor.

Uma forma comum de fazer isso é chamar `setState`, como no exemplo abaixo:

```dart
await _controller.addPet(pet);
setState(() {});
```

Esse código funciona, mas cria um problema: a tela precisa lembrar de chamar `setState` depois de cada operação que altera os dados. Se o desenvolvedor esquecer essa chamada após cadastrar, editar, excluir ou recarregar informações, a interface pode ficar desatualizada.

Imagine uma tela de pets com as seguintes ações:

* carregar todos os pets cadastrados;
* adicionar um novo pet;
* remover um pet;
* exibir mensagem de erro quando algo falhar;
* mostrar uma mensagem quando a lista estiver vazia.

Se cada ação depender manualmente de `setState`, a tela fica mais acoplada à lógica de atualização. O código passa a misturar duas responsabilidades:

1. executar a operação;
2. lembrar a interface de que ela precisa ser reconstruída.

Com `ChangeNotifier` e `ListenableBuilder`, essa responsabilidade fica mais organizada. A controller altera o estado e chama `notifyListeners()`. O `ListenableBuilder`, que está escutando a controller, reconstrói a parte da interface que depende dela. O material original descreve esse fluxo: a controller muda, chama `notifyListeners()` e o `ListenableBuilder` reconstrói a interface automaticamente .

## 2. Conceitos fundamentais

### 2.1 `ChangeNotifier`

`ChangeNotifier` é uma classe do Flutter usada para criar objetos capazes de avisar ouvintes quando alguma mudança acontece.

Uma controller que herda de `ChangeNotifier` pode chamar:

```dart
notifyListeners();
```

Essa chamada informa aos ouvintes que o estado mudou. No contexto deste material, a `PetController` pode avisar mudanças como:

* início de carregamento;
* fim de carregamento;
* alteração na lista de pets;
* ocorrência de erro;
* remoção de um pet;
* cadastro de um novo pet.

A controller não decide como a tela será exibida. Ela apenas expõe dados e estados. Por exemplo:

```dart
_controller.isLoading
_controller.errorMessage
_controller.pets
```

Essas informações são usadas pela tela para decidir o que mostrar.

---

### 2.2 `ListenableBuilder`

`ListenableBuilder` é um widget do Flutter que escuta um objeto do tipo `Listenable`. Como `ChangeNotifier` implementa esse comportamento, uma controller baseada em `ChangeNotifier` pode ser usada diretamente no `ListenableBuilder`.

A estrutura geral é esta:

```dart
ListenableBuilder(
  listenable: _controller,
  builder: (context, child) {
    return ...
  },
)
```

O parâmetro `listenable` indica qual objeto será escutado. O parâmetro `builder` contém a parte da interface que será reconstruída quando esse objeto avisar uma mudança.

No caso da tela de pets, o `builder` consulta o estado atual da controller e decide qual conteúdo renderizar:

```dart
if (_controller.isLoading) {
  return const Center(child: CircularProgressIndicator());
}

if (_controller.errorMessage != null) {
  return Center(child: Text(_controller.errorMessage!));
}

if (_controller.pets.isEmpty) {
  return const Center(child: Text('Nenhum pet cadastrado.'));
}

return ListView.builder(...);
```

Essa estrutura aparece no material-base como o centro da abordagem: substituir o corpo da tela por um `ListenableBuilder` para que a interface seja reconstruída sempre que a controller chamar `notifyListeners()` .

---

### 2.3 Controller

A controller é o objeto que concentra o estado da tela e as operações que alteram esse estado.

Neste exemplo, a `PetController` pode conter:

* lista de pets;
* estado de carregamento;
* mensagem de erro;
* método para carregar pets;
* método para adicionar pet;
* método para remover pet.

A tela chama os métodos da controller, mas não precisa controlar manualmente a reconstrução da interface depois de cada chamada. Essa atualização acontece quando a controller notifica os ouvintes.

---

### 2.4 Repository e DataSource

O material-base usa uma organização em camadas:

```dart
final dataSource = PetLocalDataSource();
final repository = SqlitePetRepository(dataSource);
_controller = PetController(repository);
```

Essa estrutura indica uma separação de responsabilidades:

* `PetLocalDataSource`: representa a fonte local de dados;
* `SqlitePetRepository`: organiza o acesso aos dados usando SQLite;
* `PetController`: usa o repositório para carregar, adicionar e remover pets;
* `PetListPage`: exibe a interface e chama a controller.

Essa separação ajuda a manter a tela menos sobrecarregada. A tela não precisa saber os detalhes de persistência local; ela apenas usa a controller.

## 3. Diferenças conceituais importantes

### 3.1 `setState` e `notifyListeners`

`setState` é usado dentro de um `StatefulWidget` para informar que o estado interno daquele widget mudou e que a interface precisa ser reconstruída.

`notifyListeners`, por outro lado, é chamado dentro de um objeto que herda de `ChangeNotifier`, como uma controller. Ele avisa todos os ouvintes registrados que houve mudança.

A diferença principal está em quem controla a atualização.

Com `setState`, a própria tela precisa lembrar de se atualizar:

```dart
await _controller.addPet(pet);
setState(() {});
```

Com `notifyListeners`, a controller avisa que mudou, e a tela apenas escuta:

```dart
await _controller.addPet(pet);
```

Nesse segundo caso, não há chamada manual de `setState` após a operação. O material original destaca exatamente essa mudança: após usar `ListenableBuilder`, operações como cadastro, remoção e carregamento não devem mais depender de `setState` para atualizar a tela .

---

### 3.2 `StatefulWidget` e `ListenableBuilder`

O `ListenableBuilder` não elimina obrigatoriamente a necessidade de um `StatefulWidget`.

Neste caso, a tela continua sendo um `StatefulWidget` porque ainda precisa controlar o ciclo de vida da controller. A controller deve ser criada quando a tela inicia e liberada quando a tela for encerrada.

Por isso, a página mantém:

```dart
initState()
dispose()
```

O `ListenableBuilder` substitui a necessidade de chamar `setState` para estados controlados pela controller, mas não substitui automaticamente todo o ciclo de vida da tela.

---

### 3.3 Estado da aplicação e decisão visual

A controller guarda informações de estado, como:

```dart
isLoading
errorMessage
pets
```

A tela decide como mostrar essas informações.

Por exemplo, a controller informa:

```dart
isLoading == true
```

A tela decide mostrar:

```dart
CircularProgressIndicator()
```

Esse detalhe é importante: a controller não deve ser responsável por montar widgets. Ela deve expor dados. A tela interpreta esses dados e constrói a interface adequada.

## 4. Estrutura inicial da página

A tela de listagem de pets será representada por um `StatefulWidget`.

```dart
class PetListPage extends StatefulWidget {
  const PetListPage({super.key});

  @override
  State<PetListPage> createState() => _PetListPageState();
}
```

O estado da página terá uma instância da controller:

```dart
class _PetListPageState extends State<PetListPage> {

}
```

O uso de `late final` indica que a controller será inicializada depois da criação do objeto, mas apenas uma vez. Isso combina com o uso no `initState`.

## 6. Criando a controller no `initState`

A controller deve ser criada no `initState` porque esse método é executado uma vez quando o estado da tela é inicializado.

```dart
@override
void initState() {
  super.initState();

  final dataSource = PetLocalDataSource();
  final repository = SqlitePetRepository(dataSource);

  _controller = PetController(repository);
  _controller.loadPets();
}
```

Esse trecho realiza quatro passos:

1. cria a fonte de dados local;
2. cria o repositório que usa essa fonte;
3. cria a controller com o repositório;
4. carrega os pets ao iniciar a tela.

A controller não deve ser criada dentro do `build`, porque o método `build` pode ser executado várias vezes. Se a controller fosse criada ali, ela poderia ser recriada a cada reconstrução da interface, causando perda de estado, recarregamentos desnecessários e comportamento inesperado. O material-base reforça que a controller deve ser criada uma única vez quando a tela inicia e que criá-la dentro do `build` poderia recriá-la várias vezes durante reconstruções da interface .

---

## 7. Liberando a controller no `dispose`

Como a controller herda de `ChangeNotifier`, ela mantém uma estrutura interna de ouvintes. Quando a tela deixa de existir, é necessário liberar esses recursos.

```dart
@override
void dispose() {
  _controller.dispose();
  super.dispose();
}
```

A chamada a `_controller.dispose()` evita que a controller permaneça ocupando memória depois que a tela foi encerrada.

Esse cuidado é importante porque objetos que escutam ou notificam mudanças podem manter referências internas. Se essas referências não forem liberadas, podem ocorrer vazamentos de memória ou atualizações em objetos que já não deveriam existir. O material-base recomenda liberar a controller no `dispose` para evitar manter objetos desnecessários em memória e prevenir memory leaks .

## 8. Usando `ListenableBuilder` no corpo da tela

O corpo da tela será construído com base no estado atual da controller.

```dart
body: ListenableBuilder(
  listenable: _controller,
  builder: (context, child) {
    if (_controller.isLoading) {
      return const Center(
        child: CircularProgressIndicator(),
      );
    }

    if (_controller.errorMessage != null) {
      return Center(
        child: Text(_controller.errorMessage!),
      );
    }

    if (_controller.pets.isEmpty) {
      return const Center(
        child: Text('Nenhum pet cadastrado.'),
      );
    }

    return ListView.builder(
      itemCount: _controller.pets.length,
      itemBuilder: (context, index) {
        final pet = _controller.pets[index];

        return ListTile(
          title: Text(pet.name),
          subtitle: Text(pet.species),
        );
      },
    );
  },
)
```

Esse código trata quatro situações principais.

### Estado de carregamento

```dart
if (_controller.isLoading) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}
```

Esse estado deve aparecer quando a controller está buscando os dados. Ele informa ao usuário que a tela ainda está processando uma operação.

### Estado de erro

```dart
if (_controller.errorMessage != null) {
  return Center(
    child: Text(_controller.errorMessage!),
  );
}
```

Esse estado aparece quando a controller registra uma mensagem de erro. A tela não precisa saber exatamente onde o erro ocorreu; ela apenas mostra a mensagem disponível.

### Estado de lista vazia

```dart
if (_controller.pets.isEmpty) {
  return const Center(
    child: Text('Nenhum pet cadastrado.'),
  );
}
```

Esse estado aparece quando a operação foi concluída, não há erro, mas a lista não possui itens.

### Estado de lista com dados

```dart
return ListView.builder(
  itemCount: _controller.pets.length,
  itemBuilder: (context, index) {
    final pet = _controller.pets[index];

    return ListTile(
      title: Text(pet.name),
      subtitle: Text(pet.species),
    );
  },
);
```

Esse estado aparece quando há pets cadastrados. O `ListView.builder` é adequado porque constrói os itens conforme necessário, usando a lista mantida pela controller.

## 9. Adicionando botão para cadastrar pet

O cadastro será acionado por um `FloatingActionButton`.

```dart
floatingActionButton: FloatingActionButton(
  onPressed: _addPet,
  child: const Icon(Icons.add),
),
```

O método `_addPet` cria um novo objeto `Pet` e delega a operação para a controller:

```dart
Future<void> _addPet() async {
  final pet = Pet(
    name: 'Novo pet',
    species: 'Cachorro',
    age: 1,
  );

  await _controller.addPet(pet);
}
```

Observe que não há `setState` após o cadastro. Isso acontece porque a atualização da tela deve ser consequência da notificação emitida pela controller.

O fluxo esperado é:

1. o usuário toca no botão;
2. `_addPet` chama `_controller.addPet(pet)`;
3. a controller adiciona o pet;
4. a controller chama `notifyListeners()`;
5. o `ListenableBuilder` reconstrói a interface;
6. a lista aparece atualizada.

## 10. Adicionando ação para remover pet

A remoção pode ser adicionada em cada item da lista com um botão no `trailing` do `ListTile`.

```dart
return ListTile(
  title: Text(pet.name),
  subtitle: Text(pet.species),
  trailing: IconButton(
    icon: const Icon(Icons.delete),
    onPressed: () => _deletePet(pet.id!),
  ),
);
```

O método de remoção delega a operação para a controller:

```dart
Future<void> _deletePet(int id) async {
  await _controller.deletePet(id);
}
```

Assim como no cadastro, não há `setState`. A controller remove o item, notifica os ouvintes, e o `ListenableBuilder` reconstrói a lista.

## 11. Confirmando remoção com `AlertDialog`

Remover um item é uma ação destrutiva. Para evitar exclusões acidentais, é recomendável pedir confirmação ao usuário antes de concluir a operação.

```dart
Future<void> _confirmDeletePet(int id) async {
  final shouldDelete = await showDialog<bool>(
    context: context,
    builder: (context) {
      return AlertDialog(
        title: const Text('Remover pet'),
        content: const Text('Deseja realmente remover este pet?'),
        actions: [
          TextButton(
            onPressed: () => Navigator.pop(context, false),
            child: const Text('Cancelar'),
          ),
          TextButton(
            onPressed: () => Navigator.pop(context, true),
            child: const Text('Remover'),
          ),
        ],
      );
    },
  );

  if (shouldDelete == true) {
    await _controller.deletePet(id);
  }
}
```

A chamada no botão fica assim:

```dart
onPressed: () => _confirmDeletePet(pet.id!)
```

Esse fluxo melhora a experiência do usuário porque dá uma chance de cancelar a ação antes que o item seja removido. O material-base inclui essa confirmação com `AlertDialog` para evitar exclusão acidental .

## 12. Melhorando a tela de erro

Uma mensagem de erro simples é funcional, mas pode ser pouco útil. Uma alternativa melhor é mostrar a mensagem e oferecer uma ação para tentar novamente.

```dart
if (_controller.errorMessage != null) {
  return Center(
    child: Padding(
      padding: const EdgeInsets.all(16),
      child: Column(
        mainAxisAlignment: MainAxisAlignment.min,
        children: [
          Text(
            _controller.errorMessage!,
            textAlign: TextAlign.center,
          ),
          const SizedBox(height: 12),
          ElevatedButton(
            onPressed: _controller.loadPets,
            child: const Text('Tentar novamente'),
          ),
        ],
      ),
    ),
  );
}
```

Essa versão é melhor porque não apenas informa que houve uma falha, mas também oferece uma forma de recuperação. O usuário não precisa sair da tela ou reiniciar o aplicativo para tentar carregar os dados novamente.

## 14. Cuidados com chamadas assíncronas

As operações da controller normalmente são assíncronas porque podem envolver acesso a banco de dados, arquivos ou outras fontes de dados.

Por isso, use `await`:

```dart
await _controller.deletePet(id);
```

O `await` garante que a operação seja aguardada antes de continuar o fluxo do método. Isso é especialmente importante quando a próxima ação depende do resultado da operação anterior.

Outro cuidado importante envolve o uso de `context` depois de uma operação assíncrona. Se a operação demorar e o usuário sair da tela antes de ela terminar, a tela pode não estar mais montada.

Nesses casos, verifique:

```dart
if (!mounted) {
  return;
}
```

Esse cuidado evita erros ao tentar usar o `context` de uma tela que já foi descartada. O material-base alerta que ignorar `mounted` pode causar erros em operações assíncronas longas, especialmente quando se tenta acessar elementos da árvore de widgets depois que a tela foi desativada .

## 15. Exemplo completo comentado

A seguir está uma versão completa da tela usando `ListenableBuilder`, criação da controller no `initState`, liberação no `dispose`, cadastro de pet, confirmação de remoção e tratamento de estados.

```dart
import 'package:flutter/material.dart';

import '../data/datasources/pet_local_datasource.dart';
import '../data/repositories/sqlite_pet_repository.dart';
import '../domain/models/pet.dart';
import '../controllers/pet_controller.dart';

class PetListPage extends StatefulWidget {
  const PetListPage({super.key});

  @override
  State<PetListPage> createState() => _PetListPageState();
}

class _PetListPageState extends State<PetListPage> {
  late final PetController _controller;

  @override
  void initState() {
    super.initState();

    final dataSource = PetLocalDataSource();
    final repository = SqlitePetRepository(dataSource);

    _controller = PetController(repository);
    _controller.loadPets();
  }

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  Future<void> _addPet() async {
    final pet = Pet(
      name: 'Novo pet',
      species: 'Cachorro',
      age: 1,
    );

    await _controller.addPet(pet);
  }

  Future<void> _confirmDeletePet(int id) async {
    final shouldDelete = await showDialog<bool>(
      context: context,
      builder: (context) {
        return AlertDialog(
          title: const Text('Remover pet'),
          content: const Text('Deseja realmente remover este pet?'),
          actions: [
            TextButton(
              onPressed: () => Navigator.pop(context, false),
              child: const Text('Cancelar'),
            ),
            TextButton(
              onPressed: () => Navigator.pop(context, true),
              child: const Text('Remover'),
            ),
          ],
        );
      },
    );

    if (shouldDelete == true) {
      await _controller.deletePet(id);
    }
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(
        title: const Text('Pets'),
      ),
      body: ListenableBuilder(
        listenable: _controller,
        builder: (context, child) {
          if (_controller.isLoading) {
            return const Center(
              child: CircularProgressIndicator(),
            );
          }

          if (_controller.errorMessage != null) {
            return Center(
              child: Padding(
                padding: const EdgeInsets.all(16),
                child: Column(
                  mainAxisAlignment: MainAxisAlignment.min,
                  children: [
                    Text(
                      _controller.errorMessage!,
                      textAlign: TextAlign.center,
                    ),
                    const SizedBox(height: 12),
                    ElevatedButton(
                      onPressed: _controller.loadPets,
                      child: const Text('Tentar novamente'),
                    ),
                  ],
                ),
              ),
            );
          }

          if (_controller.pets.isEmpty) {
            return Center(
              child: Padding(
                padding: const EdgeInsets.all(24),
                child: Column(
                  mainAxisAlignment: MainAxisAlignment.min,
                  children: [
                    const Icon(Icons.pets, size: 48),
                    const SizedBox(height: 12),
                    const Text(
                      'Nenhum pet cadastrado',
                      style: TextStyle(
                        fontSize: 18,
                        fontWeight: FontWeight.bold,
                      ),
                    ),
                    const SizedBox(height: 8),
                    const Text(
                      'Cadastre o primeiro pet para começar a usar o aplicativo.',
                      textAlign: TextAlign.center,
                    ),
                    const SizedBox(height: 16),
                    ElevatedButton.icon(
                      onPressed: _addPet,
                      icon: const Icon(Icons.add),
                      label: const Text('Cadastrar pet'),
                    ),
                  ],
                ),
              ),
            );
          }

          return ListView.builder(
            itemCount: _controller.pets.length,
            itemBuilder: (context, index) {
              final pet = _controller.pets[index];

              return ListTile(
                title: Text(pet.name),
                subtitle: Text(
                  '${pet.species} • ${pet.age} ano(s)',
                ),
                trailing: IconButton(
                  icon: const Icon(Icons.delete),
                  onPressed: pet.id == null
                      ? null
                      : () => _confirmDeletePet(pet.id!),
                ),
              );
            },
          );
        },
      ),
      floatingActionButton: FloatingActionButton(
        onPressed: _addPet,
        child: const Icon(Icons.add),
      ),
    );
  }
}
```

### Comentário do exemplo

A tela é um `StatefulWidget` porque precisa controlar o ciclo de vida da controller. A controller é criada no `initState`, recebe suas dependências e carrega os dados iniciais com `loadPets`.

O `dispose` libera a controller quando a tela é encerrada. Isso é necessário porque `ChangeNotifier` mantém ouvintes internamente.

O corpo do `Scaffold` usa `ListenableBuilder`. Isso significa que a parte principal da interface será reconstruída quando a controller chamar `notifyListeners`.

O método `_addPet` cria um pet de exemplo e chama `_controller.addPet(pet)`. Não há `setState` porque a controller deve notificar a mudança.

A remoção passa por `_confirmDeletePet`, que abre um `AlertDialog`. Se o usuário confirmar, a controller remove o pet. A lista será atualizada automaticamente quando a controller notificar os ouvintes.

O botão de exclusão é desabilitado quando `pet.id == null`. Esse cuidado evita tentar remover um item sem identificador válido.

## 16. Aplicação prática resolvida e comentada

### Cenário

Você está implementando uma tela de listagem de pets. A controller já possui os métodos `loadPets`, `addPet` e `deletePet`, além dos estados `isLoading`, `errorMessage` e `pets`.

A tela precisa:

* carregar os pets ao iniciar;
* mostrar loading durante o carregamento;
* mostrar erro quando houver falha;
* mostrar mensagem de lista vazia quando não houver pets;
* mostrar a lista quando houver dados;
* cadastrar pet pelo botão flutuante;
* remover pet com confirmação;
* não usar `setState` para atualizar dados vindos da controller.

### Objetivo

Atualizar a tela para que ela escute a `PetController` com `ListenableBuilder` e seja reconstruída automaticamente quando a controller notificar mudanças.

### Solução

A solução consiste em manter a controller como atributo da tela, inicializá-la no `initState`, liberá-la no `dispose` e usar `ListenableBuilder` no corpo do `Scaffold`.

O ponto central é este:

```dart
body: ListenableBuilder(
  listenable: _controller,
  builder: (context, child) {
    if (_controller.isLoading) {
      return const Center(child: CircularProgressIndicator());
    }

    if (_controller.errorMessage != null) {
      return Center(child: Text(_controller.errorMessage!));
    }

    if (_controller.pets.isEmpty) {
      return const Center(child: Text('Nenhum pet cadastrado.'));
    }

    return ListView.builder(
      itemCount: _controller.pets.length,
      itemBuilder: (context, index) {
        final pet = _controller.pets[index];

        return ListTile(
          title: Text(pet.name),
          subtitle: Text(pet.species),
        );
      },
    );
  },
)
```

### Comentário da solução

A ordem dos `if` importa.

O carregamento deve ser verificado primeiro porque, enquanto os dados estão sendo buscados, a tela ainda não deve concluir que a lista está vazia.

O erro vem em seguida porque, se a operação falhou, a tela deve informar o problema ao usuário.

A lista vazia é verificada depois do carregamento e do erro. Assim, a mensagem “Nenhum pet cadastrado” só aparece quando a busca terminou, não há erro e realmente não existem itens.

A lista com dados fica por último, porque só deve ser exibida quando nenhum dos estados anteriores se aplica.

### Resultado esperado

Quando a tela abrir, ela deve chamar `loadPets`. Durante o carregamento, deve exibir um indicador circular. Ao terminar:

* se houver erro, mostra a mensagem;
* se não houver pets, mostra a tela vazia;
* se houver pets, mostra a lista.

Ao cadastrar um pet, ele deve aparecer na lista sem chamada manual de `setState`.

Ao remover um pet, ele deve desaparecer da lista após a confirmação, também sem chamada manual de `setState`.

### Como validar

A validação pode ser feita observando o comportamento da tela.

Primeiro, abra a tela e confirme se `loadPets` é executado ao iniciar. Depois, cadastre um novo pet e observe se a lista muda automaticamente. Em seguida, remova um item e verifique se a lista é reconstruída. Por fim, simule uma situação sem registros e veja se a mensagem de lista vazia aparece.

Também é importante procurar no código se ainda existem chamadas como:

```dart
setState(() {});
```

após operações da controller. Para os estados controlados pela `PetController`, essas chamadas não devem ser necessárias.

### Possíveis erros

Um erro comum é criar a controller dentro do `build`. Isso pode recriar a controller várias vezes e causar recarregamentos desnecessários.

Outro erro comum é esquecer o `dispose`. Isso mantém ouvintes e recursos internos vivos por mais tempo do que deveriam.

Também pode acontecer de a tela mostrar “Nenhum pet cadastrado” antes de terminar o carregamento. Isso geralmente ocorre quando a verificação de lista vazia aparece antes da verificação de `isLoading`.

## 17. Erros comuns e como corrigir

### Erro 1: Criar a controller dentro do `build`

Código problemático:

```dart
@override
Widget build(BuildContext context) {
  final controller = PetController(repository);

  return Scaffold(...);
}
```

Esse código é problemático porque o `build` pode ser chamado muitas vezes. A controller pode ser recriada sem necessidade, perdendo estado e repetindo carregamentos.

Correção:

```dart
late final PetController _controller;

@override
void initState() {
  super.initState();
  _controller = PetController(repository);
  _controller.loadPets();
}
```

A controller deve ser criada uma única vez no ciclo de vida da tela.

---

### Erro 2: Esquecer de chamar `dispose`

Código incompleto:

```dart
@override
void dispose() {
  super.dispose();
}
```

Esse código não libera os recursos da controller.

Correção:

```dart
@override
void dispose() {
  _controller.dispose();
  super.dispose();
}
```

A controller deve ser descartada antes da chamada a `super.dispose()`.

---

### Erro 3: Continuar usando `setState` após operações da controller

Código desnecessário:

```dart
await _controller.addPet(pet);
setState(() {});
```

Se a controller chama `notifyListeners()` corretamente, esse `setState` não é necessário.

Correção:

```dart
await _controller.addPet(pet);
```

A atualização visual deve acontecer por meio do `ListenableBuilder`.

---

### Erro 4: Não tratar todos os estados da interface

Uma tela que mostra apenas a lista pode falhar em situações importantes.

Código limitado:

```dart
return ListView.builder(...);
```

Esse código não trata carregamento, erro nem lista vazia.

Correção:

```dart
if (_controller.isLoading) {
  return const Center(child: CircularProgressIndicator());
}

if (_controller.errorMessage != null) {
  return Center(child: Text(_controller.errorMessage!));
}

if (_controller.pets.isEmpty) {
  return const Center(child: Text('Nenhum pet cadastrado.'));
}

return ListView.builder(...);
```

A tela deve prever os estados mais importantes para oferecer uma experiência clara ao usuário.

---

### Erro 5: Usar `pet.id!` sem verificar se existe identificador

Código arriscado:

```dart
onPressed: () => _confirmDeletePet(pet.id!)
```

Se `pet.id` for `null`, o operador `!` causará erro em tempo de execução.

Correção:

```dart
onPressed: pet.id == null
    ? null
    : () => _confirmDeletePet(pet.id!)
```

Esse cuidado desabilita o botão quando não há identificador válido.

---

### Erro 6: Usar `context` depois de `await` sem considerar se a tela ainda existe

Quando uma operação assíncrona demora, o usuário pode sair da tela antes de ela terminar. Se o código tentar usar o `context` depois disso, pode ocorrer erro.

Correção em cenários que usam `context` após `await`:

```dart
if (!mounted) {
  return;
}
```

Essa verificação impede que o código continue tentando acessar a tela depois que ela foi desmontada.

## 18. Dúvidas frequentes

### O `ListenableBuilder` substitui o `StatefulWidget`?

Não necessariamente. Neste caso, a tela continua sendo um `StatefulWidget` porque precisa criar a controller no `initState` e liberá-la no `dispose`.

O `ListenableBuilder` substitui a necessidade de chamar `setState` para atualizar partes da interface que dependem da controller.

---

### Posso usar `setState` junto com `ListenableBuilder`?

Pode, mas deve ser evitado para estados que pertencem à controller. Se a lista de pets, o loading e a mensagem de erro estão na controller, a atualização deve acontecer por `notifyListeners()`.

O `setState` ainda pode ser usado para estados locais da tela que não pertencem à controller, mas misturar as duas abordagens para o mesmo estado pode deixar o código confuso.

---

### Onde fica a regra de mostrar loading, erro ou lista vazia?

A informação do estado fica na controller. A decisão visual fica na tela.

Por exemplo:

* a controller informa `isLoading == true`;
* a tela mostra `CircularProgressIndicator`.

A controller não precisa saber qual widget será exibido.

---

### Por que chamar `loadPets()` no `initState`?

Porque a lista deve ser carregada quando a tela inicia. O `initState` é o lugar adequado para inicializações que devem acontecer uma única vez no ciclo de vida do widget.

---

### O `ListenableBuilder` exige biblioteca externa?

Não. Ele faz parte do próprio Flutter. Por isso, é uma opção simples para aprender gerenciamento de estado sem adicionar dependências externas.

## 19. Checklist explicado de implementação

### Verifique se a controller é criada no `initState`

O que verificar: confirme se existe um atributo como `late final PetController _controller;` e se ele é inicializado dentro de `initState`.

Por que importa: a controller deve ser criada uma vez quando a tela inicia. Se for criada dentro do `build`, poderá ser recriada em reconstruções da interface.

Como validar: procure no código se há `PetController(...)` dentro do método `build`. Se houver, mova a criação para o `initState`.

O que acontece se faltar: a tela pode perder estado, carregar dados repetidamente ou se comportar de maneira instável.

---

### Verifique se `loadPets()` é chamado ao iniciar a tela

O que verificar: confirme se `_controller.loadPets();` é chamado depois da criação da controller no `initState`.

Por que importa: sem essa chamada, a tela pode abrir sem carregar os dados iniciais.

Como validar: execute a tela e observe se os pets aparecem ao abrir. Também é possível colocar logs temporários na controller para confirmar que o método foi chamado.

O que acontece se faltar: a lista pode ficar vazia mesmo havendo dados cadastrados.

---

### Verifique se a controller é liberada no `dispose`

O que verificar: confirme se existe:

```dart
@override
void dispose() {
  _controller.dispose();
  super.dispose();
}
```

Por que importa: a controller herda de `ChangeNotifier` e pode manter ouvintes internos. Esses recursos devem ser liberados quando a tela é encerrada.

Como validar: revise o método `dispose` e confirme se `_controller.dispose()` aparece antes de `super.dispose()`.

O que acontece se faltar: o aplicativo pode manter objetos desnecessários em memória e aumentar o risco de vazamentos.

---

### Verifique se o corpo da tela usa `ListenableBuilder`

O que verificar: confirme se o `body` do `Scaffold` usa:

```dart
ListenableBuilder(
  listenable: _controller,
  builder: ...
)
```

Por que importa: é o `ListenableBuilder` que reconstrói a interface quando a controller chama `notifyListeners()`.

Como validar: cadastre ou remova um pet e observe se a interface muda sem `setState`.

O que acontece se faltar: a controller pode até mudar internamente, mas a tela não será atualizada automaticamente.

---

### Verifique se os quatro estados principais são tratados

O que verificar: a tela deve tratar carregamento, erro, lista vazia e lista com dados.

Por que importa: uma interface completa precisa responder a diferentes situações, não apenas ao caso ideal em que há dados disponíveis.

Como validar: simule ou observe cada cenário: carregamento inicial, falha, ausência de dados e lista preenchida.

O que acontece se faltar: o usuário pode ver uma tela vazia sem explicação ou não entender que ocorreu um erro.

---

### Verifique se as operações da controller não dependem de `setState`

O que verificar: procure chamadas de `setState` logo após métodos como `addPet`, `deletePet` ou `loadPets`.

Por que importa: se a controller já chama `notifyListeners()`, o `setState` se torna redundante para esses estados.

Como validar: remova chamadas desnecessárias de `setState` e teste se a interface continua atualizando.

O que acontece se faltar: o código fica mais acoplado, repetitivo e sujeito a esquecimentos.

---

### Verifique se ações destrutivas pedem confirmação

O que verificar: confirme se a remoção passa por um `AlertDialog` ou algum mecanismo de confirmação.

Por que importa: remover um pet sem confirmação pode causar exclusões acidentais.

Como validar: toque no botão de excluir e veja se a tela pergunta antes de remover.

O que acontece se faltar: o usuário pode apagar registros sem intenção.

---

### Verifique se chamadas assíncronas usam `await`

O que verificar: métodos assíncronos da controller devem ser chamados com `await` quando o fluxo depende da conclusão da operação.

Por que importa: sem `await`, o código pode continuar antes que a operação termine.

Como validar: revise métodos como `_addPet`, `_confirmDeletePet` e `_deletePet`.

O que acontece se faltar: podem ocorrer comportamentos fora de ordem, especialmente em operações mais lentas.

---

## 20. Síntese final

A atualização da interface com `ListenableBuilder` e `ChangeNotifier` organiza melhor a comunicação entre controller e tela.

A controller concentra o estado e chama `notifyListeners()` quando algo muda. A tela usa `ListenableBuilder` para escutar essa controller e reconstruir a interface automaticamente.

Com essa abordagem:

* a controller é criada uma vez no `initState`;
* os dados são carregados ao iniciar a tela;
* a controller é liberada no `dispose`;
* o corpo da tela reage a mudanças com `ListenableBuilder`;
* loading, erro, lista vazia e lista com dados são tratados explicitamente;
* cadastro e remoção não precisam chamar `setState`;
* ações destrutivas podem ser confirmadas com `AlertDialog`;
* chamadas assíncronas devem ser feitas com cuidado, usando `await` e, quando necessário, `mounted`.

---

## Conclusão

Usar `ListenableBuilder` com uma controller baseada em `ChangeNotifier` permite que a interface Flutter reaja automaticamente às mudanças de estado. Essa abordagem reduz a dependência de `setState`, melhora a separação de responsabilidades e torna o código mais previsível.

A tela continua responsável por exibir a interface, mas não precisa controlar manualmente cada reconstrução. A controller altera os dados, notifica os ouvintes e o `ListenableBuilder` atualiza a parte visual correspondente.

Esse padrão é especialmente útil em telas simples e intermediárias, nas quais se deseja aprender gerenciamento de estado usando recursos nativos do Flutter antes de introduzir bibliotecas externas.
