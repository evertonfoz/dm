# Gerenciamento de Estado com ChangeNotifier no Flutter: evolução da PetController

## Objetivo do material

Neste material, você aprenderá a evoluir uma controller no Flutter para que ela gerencie o estado da interface usando `ChangeNotifier`. O foco será a `PetController`, responsável por controlar uma lista de pets, estados de carregamento e mensagens de erro. A evolução proposta reduz a dependência de vários `setState` espalhados pela página e concentra a lógica de estado em uma camada mais adequada da aplicação. O conteúdo parte da estrutura apresentada no material-base, em que a página chama a controller, a controller chama o repository e o repository se comunica com o datasource/local database. 

---

## 1. Contextualização do problema

Em uma aplicação Flutter, é comum que a interface precise reagir quando os dados mudam. Por exemplo, em uma tela de listagem de pets, a interface deve ser atualizada quando:

* um pet é cadastrado;
* um pet é editado;
* um pet é removido;
* a lista de pets é carregada do banco local;
* uma operação falha e precisa exibir uma mensagem de erro;
* uma operação assíncrona está em andamento e a tela precisa mostrar carregamento.

Uma solução inicial comum é chamar `setState` diretamente na página após cada operação:

```dart
await controller.savePet(pet);
setState(() {});
```

Esse código pode funcionar em telas simples, mas cria um problema de organização: a página passa a ser responsável por lembrar quando deve atualizar a interface. Com o crescimento da aplicação, isso aumenta o risco de inconsistências.

Por exemplo, a tela pode não atualizar depois de um cadastro, pode continuar mostrando um item removido, pode não refletir uma edição ou pode ter vários `setState` espalhados em pontos diferentes. O material-base destaca exatamente esse problema: a página fica acoplada demais aos detalhes de atualização da interface. 

A solução estudada neste material é fazer com que a própria controller avise a interface quando o estado mudar. Para isso, usaremos `ChangeNotifier`.

## 2. Estrutura em camadas do projeto

A aplicação está organizada em camadas. Uma estrutura simplificada é:

```text
lib/
  features/
    pet/
      data/
        datasources/
          pet_local_datasource.dart
        repositories/
          sqlite_pet_repository.dart
      domain/
        models/
          pet.dart
        repositories/
          pet_repository.dart
      presentation/
        controllers/
          pet_controller.dart
        pages/
          pet_list_page.dart
```

Essa separação ajuda a manter responsabilidades claras:

```text
Página → Controller → Repository → DataSource → SQLite
```

A página representa a interface. Ela deve exibir dados, capturar interações do usuário e reagir ao estado.

A controller coordena as ações da interface. Ela chama o repository, armazena estados necessários para a tela e informa quando algo mudou.

O repository define e executa operações de acesso aos dados, sem que a interface precise saber os detalhes.

O datasource lida diretamente com a fonte de dados, como SQLite.

Essa organização é importante porque evita que a tela conheça detalhes internos do banco de dados. Mesmo após a introdução de `ChangeNotifier`, a controller continua dependendo do repository, e não diretamente do SQLite. Essa regra mantém a arquitetura mais limpa e mais fácil de manter.

## 3. O que é ChangeNotifier

`ChangeNotifier` é uma classe nativa do Flutter usada para avisar ouvintes quando alguma informação mudou. Quando uma classe herda de `ChangeNotifier`, ela ganha acesso ao método:

```dart
notifyListeners();
```

Esse método notifica todos os componentes que estão escutando aquela classe. Em termos práticos, o fluxo fica assim:

```text
A controller altera um estado
↓
A controller chama notifyListeners()
↓
A interface é notificada
↓
A tela pode ser reconstruída com os novos dados
```

Isso permite que a página deixe de chamar vários `setState` manualmente. Em vez disso, a controller concentra as mudanças de estado e informa a interface quando há algo novo para exibir.

O `ChangeNotifier` é um recurso nativo do Flutter. Para usá-lo, não é necessário instalar um pacote adicional nesse momento. No código, ele pode ser importado com:

```dart
import 'package:flutter/foundation.dart';
```

---

## 4. Quando usar ChangeNotifier

`ChangeNotifier` é útil quando uma classe precisa armazenar informações que afetam a interface.

No caso da `PetController`, ele será usado para controlar principalmente três elementos:

### Lista de pets

A lista de pets representa os dados carregados do banco local. Ela deve ser mantida internamente pela controller, de preferência como uma lista privada. Assim, outras partes da aplicação podem ler a lista, mas não devem modificá-la diretamente.

### Estado de carregamento

O estado de carregamento indica se uma operação assíncrona está em andamento. Por exemplo, enquanto a lista de pets está sendo carregada do banco, a interface pode mostrar um indicador de progresso.

Esse estado geralmente é representado por um booleano:

```dart
bool _isLoading = false;
```

Quando `_isLoading` for `true`, a interface entende que existe uma operação em andamento. Quando for `false`, a operação terminou.

### Mensagem de erro

A mensagem de erro guarda uma descrição amigável quando alguma operação falha. Por exemplo, se a controller não conseguir carregar os pets, ela pode definir:

```dart
_errorMessage = 'Não foi possível carregar os pets.';
```

A interface pode ler essa mensagem e decidir como apresentá-la ao usuário, por exemplo em um texto, diálogo ou snackbar.

## 5. Evoluindo a PetController com ChangeNotifier

A controller deixa de ser uma classe comum e passa a herdar de `ChangeNotifier`.

Um exemplo completo de implementação é:

```dart
import 'package:flutter/foundation.dart';

import '../domain/models/pet.dart';
import '../domain/repositories/pet_repository.dart';

class PetController extends ChangeNotifier {
  final PetRepository _repository;

  PetController(this._repository);

  final List<Pet> _pets = [];
  bool _isLoading = false;
  String? _errorMessage;

  List<Pet> get pets => List.unmodifiable(_pets);
  bool get isLoading => _isLoading;
  String? get errorMessage => _errorMessage;

  Future<void> loadPets() async {
    _isLoading = true;
    _errorMessage = null;
    notifyListeners();

    try {
      final pets = await _repository.findAll();
      _pets
        ..clear()
        ..addAll(pets);
    } catch (error) {
      _errorMessage = 'Não foi possível carregar os pets.';
    } finally {
      _isLoading = false;
      notifyListeners();
    }
  }

  Future<void> addPet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.insert(pet);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível cadastrar o pet.';
      notifyListeners();
    }
  }

  Future<void> updatePet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.update(pet);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível atualizar o pet.';
      notifyListeners();
    }
  }

  Future<void> deletePet(int id) async {
    try {
      _errorMessage = null;
      await _repository.delete(id);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível remover o pet.';
      notifyListeners();
    }
  }

  void clearError() {
    _errorMessage = null;
    notifyListeners();
  }
}
```

Os caminhos dos imports podem variar conforme a localização real dos arquivos no projeto. O importante é que a controller consiga importar o modelo `Pet`, a abstração `PetRepository` e o `ChangeNotifier`.

## 6. Entendendo a controller parte por parte

### Herança de ChangeNotifier

```dart
class PetController extends ChangeNotifier {
```

Essa linha faz com que `PetController` passe a ser uma classe observável. Isso significa que outros componentes poderão escutá-la e reagir quando ela chamar `notifyListeners()`.

Sem essa herança, a controller poderia continuar chamando o repository normalmente, mas não teria o mecanismo nativo de notificação de mudanças.

---

### Dependência do repository

```dart
final PetRepository _repository;

PetController(this._repository);
```

A controller recebe um `PetRepository` no construtor. Isso mantém a separação de responsabilidades.

A controller não deve saber se os dados vêm de SQLite, API, arquivo local ou memória. Ela apenas chama métodos definidos no repository, como:

```dart
_repository.findAll();
_repository.insert(pet);
_repository.update(pet);
_repository.delete(id);
```

Esse detalhe é importante porque evita acoplamento com a camada de dados. Se no futuro a forma de persistência mudar, a controller tende a sofrer menos alterações.

---

### Lista privada de pets

```dart
final List<Pet> _pets = [];
```

O underline no início do nome indica que `_pets` é privado dentro do arquivo Dart. A ideia é impedir que a página altere a lista diretamente.

A lista representa o estado interno da controller. Por isso, a responsabilidade de modificá-la deve ficar concentrada na própria controller.

---

### Getter com List.unmodifiable

```dart
List<Pet> get pets => List.unmodifiable(_pets);
```

Esse getter permite que a interface leia a lista de pets, mas impede que ela modifique diretamente o conteúdo da lista.

Isso é importante porque a tela não deve fazer algo como:

```dart
controller.pets.add(pet);
```

Se a tela pudesse alterar a lista diretamente, a controller perderia o controle sobre o estado. Além disso, uma alteração direta poderia acontecer sem `notifyListeners()`, fazendo a interface ficar desatualizada.

Com `List.unmodifiable(_pets)`, a lista é exposta apenas para leitura.

---

### Estado de carregamento

```dart
bool _isLoading = false;

bool get isLoading => _isLoading;
```

O campo `_isLoading` informa se existe uma operação em andamento.

A controller altera esse estado antes e depois de operações assíncronas. A interface pode consultar `isLoading` e decidir como reagir.

Por exemplo:

```dart
if (controller.isLoading) {
  return const CircularProgressIndicator();
}
```

A controller não deve decidir qual widget será exibido. Ela apenas informa o estado. A escolha visual continua sendo responsabilidade da interface.

---

### Mensagem de erro

```dart
String? _errorMessage;

String? get errorMessage => _errorMessage;
```

A mensagem de erro é opcional. Por isso, o tipo é `String?`.

Quando não há erro, o valor pode ser `null`. Quando uma operação falha, a controller define uma mensagem amigável.

Exemplo:

```dart
_errorMessage = 'Não foi possível cadastrar o pet.';
```

A interface pode verificar se existe uma mensagem e exibi-la ao usuário.

## 7. O método loadPets

O método `loadPets` carrega a lista de pets a partir do repository:

```dart
Future<void> loadPets() async {
  _isLoading = true;
  _errorMessage = null;
  notifyListeners();

  try {
    final pets = await _repository.findAll();
    _pets
      ..clear()
      ..addAll(pets);
  } catch (error) {
    _errorMessage = 'Não foi possível carregar os pets.';
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

Esse método tem três responsabilidades principais:

1. informar que o carregamento começou;
2. buscar os dados no repository;
3. informar que o carregamento terminou.

No início, a controller faz:

```dart
_isLoading = true;
_errorMessage = null;
notifyListeners();
```

Isso permite que a interface saiba imediatamente que uma operação começou. Assim, ela pode mostrar um indicador de carregamento.

Depois, a controller tenta buscar os dados:

```dart
final pets = await _repository.findAll();
_pets
  ..clear()
  ..addAll(pets);
```

A lista interna é limpa e preenchida novamente com os dados retornados pelo repository. O uso de `clear()` seguido de `addAll()` mantém a mesma lista interna, mas atualiza seu conteúdo.

Se ocorrer erro, o `catch` define uma mensagem:

```dart
_errorMessage = 'Não foi possível carregar os pets.';
```

Por fim, o bloco `finally` sempre será executado:

```dart
finally {
  _isLoading = false;
  notifyListeners();
}
```

Isso garante que o carregamento será encerrado mesmo se a busca falhar.

---

## 8. Por que notifyListeners aparece em dois momentos

No método `loadPets`, `notifyListeners()` aparece no início e no final.

O primeiro chamado acontece logo depois de `_isLoading` virar `true`:

```dart
_isLoading = true;
_errorMessage = null;
notifyListeners();
```

Esse chamado serve para avisar a interface que o carregamento começou. Sem ele, a tela poderia não mostrar o indicador de carregamento no momento certo.

O segundo chamado acontece no `finally`:

```dart
_isLoading = false;
notifyListeners();
```

Esse chamado serve para avisar que a operação terminou. Nesse momento, a interface pode esconder o carregamento e exibir a lista atualizada ou uma mensagem de erro.

Portanto, os dois chamados existem porque representam dois momentos diferentes do estado:

```text
Início da operação → carregando
Final da operação → carregamento encerrado, dados ou erro disponíveis
```

## 9. Uso de try, catch e finally

Operações com banco de dados ou qualquer fonte externa podem falhar. Por isso, métodos assíncronos devem ser tratados com cuidado.

### try

O bloco `try` contém a operação principal:

```dart
try {
  final pets = await _repository.findAll();
  _pets
    ..clear()
    ..addAll(pets);
}
```

É nele que a controller tenta executar a ação esperada.

### catch

O bloco `catch` é executado quando ocorre erro:

```dart
catch (error) {
  _errorMessage = 'Não foi possível carregar os pets.';
}
```

Nesse caso, a controller não expõe o erro técnico diretamente. Ela define uma mensagem compreensível para a interface apresentar ao usuário.

### finally

O bloco `finally` é executado sempre, com ou sem erro:

```dart
finally {
  _isLoading = false;
  notifyListeners();
}
```

Esse bloco é essencial para evitar que a interface fique presa em estado de carregamento. Se `_isLoading` fosse definido como `false` apenas dentro do `try`, uma falha poderia impedir essa atualização.

## 10. Métodos de escrita: cadastrar, atualizar e remover

Além de carregar os pets, a controller precisa modificar os dados.

### Cadastro

```dart
Future<void> addPet(Pet pet) async {
  try {
    _errorMessage = null;
    await _repository.insert(pet);
    await loadPets();
  } catch (error) {
    _errorMessage = 'Não foi possível cadastrar o pet.';
    notifyListeners();
  }
}
```

Esse método limpa a mensagem de erro, chama o repository para inserir o pet e, em seguida, recarrega a lista.

O recarregamento é importante porque garante que a lista exibida na tela reflita o estado atual da fonte de dados.

### Atualização

```dart
Future<void> updatePet(Pet pet) async {
  try {
    _errorMessage = null;
    await _repository.update(pet);
    await loadPets();
  } catch (error) {
    _errorMessage = 'Não foi possível atualizar o pet.';
    notifyListeners();
  }
}
```

Depois de atualizar o pet no repository, a controller chama `loadPets()` para buscar a lista atualizada.

### Remoção

```dart
Future<void> deletePet(int id) async {
  try {
    _errorMessage = null;
    await _repository.delete(id);
    await loadPets();
  } catch (error) {
    _errorMessage = 'Não foi possível remover o pet.';
    notifyListeners();
  }
}
```

Após remover o item, a lista é recarregada. Isso evita que a interface continue mostrando um item que já foi excluído.

## 11. Método para limpar erro

Um método útil na controller é:

```dart
void clearError() {
  _errorMessage = null;
  notifyListeners();
}
```

Esse método permite apagar a mensagem de erro quando ela já foi tratada pela interface.

Por exemplo, se a tela exibir uma mensagem e o usuário fechá-la, a interface pode chamar `clearError()` para impedir que a mesma mensagem continue aparecendo.

Esse método também mantém a regra principal: sempre que um estado que afeta a interface muda, a controller chama `notifyListeners()`.

## 12. Diferença entre setState e ChangeNotifier

A principal diferença entre `setState` e `ChangeNotifier` está na separação de responsabilidades.

Com `setState`, a própria página geralmente altera ou solicita dados e depois manda reconstruir a interface. Isso funciona, mas pode deixar a tela responsável por detalhes demais.

Com `ChangeNotifier`, a controller concentra o estado e avisa quando algo mudou. A página apenas escuta a controller e reage.

Comparação conceitual:

| Aspecto                              | setState                  | ChangeNotifier                            |
| ------------------------------------ | ------------------------- | ----------------------------------------- |
| Onde o estado costuma ficar          | Na própria página         | Em uma classe separada, como a controller |
| Quem avisa que a tela deve atualizar | A página                  | A controller                              |
| Organização em telas maiores         | Pode ficar confusa        | Tende a ficar mais organizada             |
| Reutilização do estado               | Mais limitada             | Mais fácil de reaproveitar                |
| Responsabilidade da interface        | Controlar estado e visual | Reagir ao estado e exibir visual          |

Isso não significa que `setState` seja errado. Ele é útil para estados simples e locais de uma tela. Porém, quando o estado representa dados importantes da funcionalidade, como a lista de pets, uma controller com `ChangeNotifier` melhora a organização.

## 13. Fluxo completo depois da evolução

Após evoluir a controller, o fluxo de cadastro fica assim:

```text
Usuário toca no botão de cadastro
↓
A página chama controller.addPet(pet)
↓
A controller chama repository.insert(pet)
↓
O repository salva no SQLite por meio da camada de dados
↓
A controller chama loadPets()
↓
A lista interna é atualizada
↓
A controller chama notifyListeners()
↓
A interface é notificada e pode atualizar a tela
```

Esse fluxo mantém a responsabilidade de cada camada:

* a página lida com interação e apresentação;
* a controller coordena estado e operações;
* o repository lida com acesso aos dados;
* o datasource executa detalhes de persistência;
* o SQLite armazena os dados localmente.

## 14. Exemplo comentado de uso do estado na interface

A adaptação completa da tela para escutar a controller pode ser feita posteriormente com `ListenableBuilder`. Mesmo assim, é importante entender como a interface pode usar os estados expostos.

Exemplo conceitual:

```dart
if (controller.isLoading) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}

if (controller.errorMessage != null) {
  return Center(
    child: Text(controller.errorMessage!),
  );
}

final pets = controller.pets;

return ListView.builder(
  itemCount: pets.length,
  itemBuilder: (context, index) {
    final pet = pets[index];

    return ListTile(
      title: Text(pet.name),
    );
  },
);
```

Esse exemplo mostra uma regra importante: a controller informa o estado, mas a interface decide como representá-lo visualmente.

A controller informa:

```dart
isLoading
errorMessage
pets
```

A interface decide:

```dart
mostrar CircularProgressIndicator
mostrar Text com erro
mostrar ListView
```

Essa separação evita que a controller fique misturada com regras visuais.

## 15. Aplicação prática resolvida: evolução da PetController

### Cenário

A aplicação possui uma tela de listagem de pets. Antes, depois de cadastrar, editar ou remover um pet, a página precisava chamar `setState` manualmente para atualizar a lista.

Esse comportamento funciona em projetos pequenos, mas aumenta o risco de esquecimentos e inconsistências.

### Objetivo

Evoluir a `PetController` para que ela:

* herde de `ChangeNotifier`;
* mantenha uma lista privada de pets;
* exponha a lista por um getter seguro;
* controle estado de carregamento;
* controle mensagem de erro;
* tenha métodos para carregar, cadastrar, atualizar e remover pets;
* chame `notifyListeners()` sempre que um estado relevante mudar.

### Solução

```dart
import 'package:flutter/foundation.dart';

import '../../domain/models/pet.dart';
import '../../domain/repositories/pet_repository.dart';

class PetController extends ChangeNotifier {
  final PetRepository _repository;

  PetController(this._repository);

  final List<Pet> _pets = [];
  bool _isLoading = false;
  String? _errorMessage;

  List<Pet> get pets => List.unmodifiable(_pets);
  bool get isLoading => _isLoading;
  String? get errorMessage => _errorMessage;

  Future<void> loadPets() async {
    _isLoading = true;
    _errorMessage = null;
    notifyListeners();

    try {
      final pets = await _repository.findAll();
      _pets
        ..clear()
        ..addAll(pets);
    } catch (error) {
      _errorMessage = 'Não foi possível carregar os pets.';
    } finally {
      _isLoading = false;
      notifyListeners();
    }
  }

  Future<void> addPet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.insert(pet);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível cadastrar o pet.';
      notifyListeners();
    }
  }

  Future<void> updatePet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.update(pet);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível atualizar o pet.';
      notifyListeners();
    }
  }

  Future<void> deletePet(int id) async {
    try {
      _errorMessage = null;
      await _repository.delete(id);
      await loadPets();
    } catch (error) {
      _errorMessage = 'Não foi possível remover o pet.';
      notifyListeners();
    }
  }

  void clearError() {
    _errorMessage = null;
    notifyListeners();
  }
}
```

### Comentário da solução

A controller agora centraliza o estado da lista de pets. A página não deve modificar `_pets` diretamente. Ela apenas lê `pets`.

O método `loadPets()` é responsável por buscar os dados atualizados no repository. Ele também controla `_isLoading` e `_errorMessage`.

Os métodos `addPet`, `updatePet` e `deletePet` executam operações de escrita e, em caso de sucesso, chamam `loadPets()` para recarregar a lista. Em caso de falha, definem uma mensagem de erro e notificam a interface.

O método `clearError()` permite limpar a mensagem de erro de forma controlada.

### Resultado esperado

Depois dessa evolução, a controller passa a ser capaz de avisar quando seus dados mudam. A tela ainda pode estar usando `setState` provisoriamente, mas a controller já está preparada para ser escutada pela interface com mecanismos como `ListenableBuilder`.

### Como validar

A implementação pode ser validada observando os seguintes comportamentos:

Ao chamar `loadPets()`, `_isLoading` deve mudar para `true` no início e voltar para `false` no final. A lista `_pets` deve ser atualizada com os dados retornados pelo repository.

Ao chamar `addPet(pet)`, o pet deve ser inserido e a lista deve ser recarregada.

Ao chamar `updatePet(pet)`, os dados devem ser atualizados e refletidos na lista após o recarregamento.

Ao chamar `deletePet(id)`, o pet removido não deve mais aparecer na lista depois do recarregamento.

Se ocorrer erro em alguma operação, `errorMessage` deve receber uma mensagem adequada e a interface deve ser notificada.

### Possíveis erros

Um erro comum é esquecer de chamar `notifyListeners()` depois de alterar `_isLoading`, `_errorMessage` ou `_pets`. Nesse caso, a interface pode continuar exibindo um estado antigo.

Outro erro é retornar `_pets` diretamente no getter. Isso permite que outras partes da aplicação modifiquem a lista sem passar pela controller.

Também é um erro fazer a controller acessar diretamente o SQLite. A controller deve continuar usando o repository.

## 16. Erros comuns e dúvidas frequentes

### O ChangeNotifier substitui o repository?

Não. O `ChangeNotifier` não substitui o repository. Eles têm responsabilidades diferentes.

O repository cuida do acesso aos dados. O `ChangeNotifier` permite que a controller avise a interface quando seu estado mudar.

### A controller deve acessar diretamente o SQLite?

Não. A controller deve chamar o repository. O acesso direto ao SQLite deve permanecer na camada de dados, geralmente no datasource e no repository concreto.

### Ainda preciso usar setState?

Durante uma etapa de transição, a tela ainda pode usar `setState`. Porém, a evolução com `ChangeNotifier` prepara o projeto para reduzir esse uso.

A ideia é que a interface passe a escutar a controller. Assim, quando a controller chamar `notifyListeners()`, a tela poderá atualizar automaticamente.

### Por que usar List.unmodifiable?

`List.unmodifiable` impede que a interface altere diretamente a lista interna da controller.

Isso protege o estado da aplicação. Se qualquer parte do código pudesse modificar a lista, seria mais difícil controlar quando a interface deve ser notificada.

### O ChangeNotifier serve para aplicações grandes?

`ChangeNotifier` pode funcionar bem em projetos pequenos e médios. Em aplicações maiores, pode ser necessário estudar outras soluções de gerenciamento de estado, como Provider, Riverpod ou Bloc.

Neste momento, `ChangeNotifier` é uma boa escolha porque permite evoluir o projeto de forma gradual sem adicionar complexidade desnecessária.

### Posso colocar widgets dentro da controller?

Não é uma boa prática. A controller deve informar estados, como `isLoading`, `errorMessage` e `pets`. A interface decide quais widgets serão exibidos.

Por exemplo, a controller não deve decidir que a tela mostrará um `CircularProgressIndicator`. Ela deve apenas informar que está carregando.

## 17. Checklist explicado

### Verifique se a controller herda de ChangeNotifier

A controller precisa declarar:

```dart
class PetController extends ChangeNotifier
```

Isso importa porque somente assim ela poderá chamar `notifyListeners()` e ser escutada por componentes da interface. Se essa herança faltar, a controller continuará funcionando como classe comum, mas não terá o mecanismo de notificação de mudanças.

### Verifique se a lista interna é privada

A lista deve ser declarada como privada:

```dart
final List<Pet> _pets = [];
```

Isso importa porque a lista representa o estado interno da controller. Se a página puder alterar essa lista diretamente, a controller perde o controle sobre as mudanças e a interface pode ficar inconsistente.

### Verifique se o getter da lista usa List.unmodifiable

O getter deve proteger a lista:

```dart
List<Pet> get pets => List.unmodifiable(_pets);
```

Isso importa porque a interface deve conseguir ler os pets, mas não modificar a lista diretamente. Se o getter retornar `_pets` sem proteção, qualquer parte do código poderá alterar o estado sem notificação.

### Verifique se existe estado de carregamento

A controller deve ter um campo como:

```dart
bool _isLoading = false;
```

e um getter público:

```dart
bool get isLoading => _isLoading;
```

Isso importa porque operações assíncronas não terminam imediatamente. Sem esse estado, a interface não tem uma forma clara de saber quando deve mostrar ou esconder carregamento.

### Verifique se existe mensagem de erro

A controller deve ter um campo opcional:

```dart
String? _errorMessage;
```

e um getter:

```dart
String? get errorMessage => _errorMessage;
```

Isso importa porque falhas podem acontecer ao carregar, cadastrar, editar ou remover dados. Sem uma mensagem de erro, a interface pode falhar silenciosamente, prejudicando a experiência do usuário.

### Verifique se notifyListeners é chamado após mudanças de estado

Sempre que a controller alterar dados que afetam a interface, ela deve chamar:

```dart
notifyListeners();
```

Isso importa porque a interface precisa ser avisada quando algo muda. Se esse chamado faltar, a mudança pode acontecer internamente, mas a tela continuará exibindo o estado anterior.

### Verifique se o bloco finally encerra o carregamento

No método `loadPets`, o carregamento deve ser finalizado no `finally`:

```dart
finally {
  _isLoading = false;
  notifyListeners();
}
```

Isso importa porque o `finally` é executado mesmo quando ocorre erro. Se `_isLoading` não for redefinido para `false`, a tela pode ficar presa no indicador de carregamento.

### Verifique se a controller continua usando o repository

A controller deve chamar o repository:

```dart
await _repository.findAll();
await _repository.insert(pet);
await _repository.update(pet);
await _repository.delete(id);
```

Isso importa porque mantém a separação entre apresentação, regra de coordenação e acesso a dados. Se a controller acessar diretamente o SQLite, a arquitetura fica mais acoplada e mais difícil de manter.

### Verifique se a controller não contém regras visuais

A controller deve expor estados, não widgets. Ela pode informar que está carregando, mas não deve decidir como o carregamento será exibido.

Isso importa porque a controller pertence à lógica de apresentação e estado, enquanto os widgets pertencem à interface. Misturar essas responsabilidades dificulta manutenção e testes.

## 18. Síntese final

A evolução da `PetController` com `ChangeNotifier` melhora a organização do gerenciamento de estado no Flutter.

Antes, a página precisava chamar `setState` manualmente após operações importantes. Isso fazia a interface acumular responsabilidades e aumentava o risco de inconsistências.

Depois da evolução, a controller passa a guardar a lista de pets, o estado de carregamento e a mensagem de erro. Sempre que algum desses estados muda, ela chama `notifyListeners()` para avisar a interface.

A controller continua chamando o repository, e não o SQLite diretamente. Isso preserva a separação em camadas:

```text
Página → Controller → Repository → DataSource → SQLite
```

O principal ganho é a separação de responsabilidades: a controller controla o estado, enquanto a interface apenas reage às mudanças.

## Conclusão

`ChangeNotifier` é uma forma simples e nativa de evoluir o gerenciamento de estado em uma aplicação Flutter. Ao aplicá-lo na `PetController`, a aplicação passa a ter um ponto central para controlar dados, carregamento e erros relacionados aos pets.

Essa abordagem reduz a dependência de múltiplos `setState`, melhora a previsibilidade do fluxo e prepara o projeto para que a interface escute a controller de forma automática, por exemplo com `ListenableBuilder`.

Com essa evolução, o código fica mais organizado, mais fácil de manter e mais preparado para crescer.
