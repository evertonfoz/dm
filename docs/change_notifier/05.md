# Estados de carregamento, fim da lista e tratamento de erro em paginação infinita no Flutter

## Objetivo do material

Neste material, você aprenderá a organizar os estados de uma listagem paginada em Flutter, especialmente em telas que usam rolagem infinita. O foco é diferenciar corretamente o carregamento inicial, o carregamento de novas páginas, a lista vazia, o fim da lista e os erros de carregamento.

O conteúdo parte de uma tela de listagem de pets que já possui paginação, `ScrollController`, `ChangeNotifier` e `ListenableBuilder`, e aprofunda a forma correta de representar os estados da interface para melhorar a experiência do usuário e a manutenção do código. O material-base apresenta esses estados principais: carregamento inicial, lista vazia, lista com dados, carregando mais, fim da lista, erro inicial e erro incremental .

---

## 1. Contextualização do problema

Em uma tela com paginação infinita, os dados não são carregados todos de uma vez. A aplicação busca uma primeira página de registros e, conforme o usuário rola a lista, novas páginas são solicitadas.

Esse comportamento melhora o desempenho, porque evita carregar muitos registros de uma só vez. Porém, ele também cria um desafio: a interface precisa saber exatamente o que exibir em cada momento.

Uma tela paginada pode estar em diferentes situações:

* ainda carregando os primeiros dados;
* sem nenhum registro encontrado;
* exibindo itens já carregados;
* buscando mais itens no final da lista;
* sem mais registros disponíveis;
* com erro antes de qualquer dado aparecer;
* com erro apenas ao tentar carregar a próxima página.

Esses estados não devem ser tratados da mesma forma. Um erro inicial, por exemplo, pode ocupar a tela inteira, porque ainda não existe conteúdo para mostrar. Já um erro incremental não deve apagar os itens existentes; ele deve aparecer apenas no rodapé da lista.

---

## 2. Conceitos fundamentais

### Paginação

Paginação é a técnica de dividir uma grande quantidade de dados em partes menores chamadas páginas. Em vez de buscar todos os registros de uma vez, a aplicação solicita apenas uma quantidade limitada por requisição.

No exemplo do material, a controller usa um limite fixo:

```dart
final int _limit = 10;
```

Isso significa que cada busca tenta carregar até 10 registros por vez.

A página atual é controlada por:

```dart
int _currentPage = 0;
```

A partir da página atual e do limite, a aplicação calcula o deslocamento, chamado de `offset`:

```dart
final offset = _currentPage * _limit;
```

Se `_currentPage` for `0` e `_limit` for `10`, o `offset` será `0`. A primeira busca começa no primeiro registro. Se `_currentPage` for `1`, o `offset` será `10`, indicando que a próxima busca começa depois dos 10 primeiros registros.

### Rolagem infinita

Rolagem infinita é a técnica em que a próxima página é carregada automaticamente quando o usuário se aproxima do fim da lista.

No Flutter, isso costuma ser feito com um `ScrollController`. A tela observa a posição atual da rolagem e, quando o usuário chega perto do final, chama o método que busca a próxima página.

O trecho abaixo representa essa ideia:

```dart
final isNearBottom = position.pixels >= position.maxScrollExtent - 200;

if (isNearBottom) {
  _controller.loadNextPage();
}
```

A condição verifica se o usuário está a menos de 200 pixels do final da lista. Esse valor funciona como uma margem de antecipação. Assim, a aplicação pode iniciar o carregamento antes de o usuário realmente chegar ao último item.

### Estado da interface

Estado da interface é o conjunto de informações que define o que a tela deve mostrar em determinado momento.

Em uma listagem paginada, os estados principais são:

* `isLoading`: indica se existe uma operação de carregamento em andamento;
* `hasMoreItems`: indica se ainda existem mais registros a carregar;
* `errorMessage`: guarda uma mensagem de erro, quando algo falha;
* `pets`: armazena os itens já carregados;
* `isEmpty`: indica se a lista está vazia após uma tentativa de carregamento.

O objetivo é transformar essas informações em decisões visuais claras.

## 3. Diferença entre carregamento inicial e carregamento adicional

Uma das distinções mais importantes em paginação infinita é separar o carregamento inicial do carregamento adicional.

### Carregamento inicial

O carregamento inicial acontece quando a tela ainda não possui nenhum item carregado. Nesse momento, faz sentido ocupar a tela inteira com um indicador de progresso, porque ainda não há conteúdo útil para exibir.

Exemplo:

```dart
if (_controller.isLoading && _controller.pets.isEmpty) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}
```

Esse código verifica duas condições ao mesmo tempo:

1. a controller está carregando dados;
2. a lista de pets ainda está vazia.

Quando as duas condições são verdadeiras, a tela mostra um `CircularProgressIndicator` centralizado.

### Carregamento adicional

O carregamento adicional acontece quando a tela já possui itens, mas precisa buscar a próxima página.

Nesse caso, a lista não deve desaparecer. O usuário deve continuar vendo os itens já carregados, e o indicador de progresso deve aparecer apenas no final.

Exemplo:

```dart
if (index == _controller.pets.length && _controller.isLoading) {
  return const Padding(
    padding: EdgeInsets.all(16),
    child: Center(
      child: CircularProgressIndicator(),
    ),
  );
}
```

A condição `index == _controller.pets.length` identifica o item extra no final da lista. Esse item não representa um pet; ele representa o rodapé da listagem.

Essa separação evita que a tela “pisque” ou substitua todos os itens por um loading toda vez que uma nova página for carregada.

## 4. Controller com estados mais claros

A controller é responsável por armazenar os dados da lista, controlar o carregamento, registrar erros e avisar a interface quando algo muda.

Uma estrutura adequada para a controller pode começar com os seguintes atributos:

```dart
class PetController extends ChangeNotifier {
  final PetRepository _repository;

  PetController(this._repository);

  final List<Pet> _pets = [];
  final int _limit = 10;

  int _currentPage = 0;
  bool _isLoading = false;
  bool _hasMoreItems = true;
  String? _errorMessage;
}
```

Cada atributo possui uma função específica.

`_pets` guarda os itens carregados até o momento. Ele é privado para impedir alterações diretas pela interface.

`_limit` define quantos itens serão buscados por página.

`_currentPage` indica qual página será buscada a seguir.

`_isLoading` evita carregamentos simultâneos e permite que a interface exiba indicadores de progresso.

`_hasMoreItems` informa se ainda existem registros a buscar.

`_errorMessage` guarda uma mensagem quando ocorre erro.

## 5. Getters públicos e encapsulamento

A interface precisa consultar os dados da controller, mas não deve modificar seus atributos internos diretamente. Para isso, usamos getters.

```dart
List<Pet> get pets => List.unmodifiable(_pets);
bool get isLoading => _isLoading;
bool get hasMoreItems => _hasMoreItems;
String? get errorMessage => _errorMessage;
bool get hasError => _errorMessage != null;
bool get isEmpty => _pets.isEmpty && !_isLoading && !hasError;
```

O getter `pets` retorna uma lista não modificável. Isso é importante porque a tela pode ler os pets, mas não pode adicionar ou remover itens diretamente. Toda alteração deve passar pela controller.

O getter `hasError` transforma uma verificação técnica em uma informação semântica. Em vez de a tela perguntar se `_errorMessage != null`, ela pergunta se existe erro.

O getter `isEmpty` centraliza a regra de lista vazia. A lista só é considerada vazia quando não há pets, não existe carregamento em andamento e não existe erro. Isso evita que a interface mostre uma mensagem de lista vazia enquanto ainda está carregando ou enquanto ocorreu uma falha.

---

## 6. Getters auxiliares para melhorar a leitura da interface

Além dos getters básicos, a controller pode oferecer getters que representam estados específicos da tela.

```dart
bool get isInitialLoading => _isLoading && _pets.isEmpty;
bool get isLoadingMore => _isLoading && _pets.isNotEmpty;
bool get canLoadMore => !_isLoading && _hasMoreItems;
```

Esses getters não criam novas informações. Eles apenas dão nomes claros a combinações de estado.

Antes, a tela precisava escrever:

```dart
if (_controller.isLoading && _controller.pets.isEmpty) {
  // loading inicial
}
```

Depois, a tela pode escrever:

```dart
if (_controller.isInitialLoading) {
  // loading inicial
}
```

Essa mudança parece simples, mas melhora bastante a manutenção. O método `build` passa a expressar intenções, não detalhes internos.

O getter `canLoadMore` também é essencial. Ele impede que a tela solicite uma nova página quando já existe carregamento em andamento ou quando todos os itens já foram carregados.

## 7. Controller completa com paginação e tratamento de estados

Abaixo está uma versão completa da controller, com carregamento inicial, carregamento incremental, CRUD e estados auxiliares.

```dart
class PetController extends ChangeNotifier {
  final PetRepository _repository;

  PetController(this._repository);

  final List<Pet> _pets = [];
  final int _limit = 10;

  int _currentPage = 0;
  bool _isLoading = false;
  bool _hasMoreItems = true;
  String? _errorMessage;

  List<Pet> get pets => List.unmodifiable(_pets);
  bool get isLoading => _isLoading;
  bool get hasMoreItems => _hasMoreItems;
  String? get errorMessage => _errorMessage;
  bool get hasError => _errorMessage != null;

  bool get isInitialLoading => _isLoading && _pets.isEmpty;
  bool get isLoadingMore => _isLoading && _pets.isNotEmpty;
  bool get isEmpty => _pets.isEmpty && !_isLoading && !hasError;
  bool get canLoadMore => !_isLoading && _hasMoreItems;

  Future<void> loadFirstPage() async {
    _currentPage = 0;
    _hasMoreItems = true;
    _errorMessage = null;
    _pets.clear();

    notifyListeners();

    await loadNextPage();
  }

  Future<void> loadNextPage() async {
    if (_isLoading || !_hasMoreItems) {
      return;
    }

    _isLoading = true;
    _errorMessage = null;
    notifyListeners();

    try {
      final offset = _currentPage * _limit;

      final newPets = await _repository.findPage(
        limit: _limit,
        offset: offset,
      );

      _pets.addAll(newPets);
      _currentPage++;

      if (newPets.length < _limit) {
        _hasMoreItems = false;
      }
    } catch (error) {
      _errorMessage = 'Não foi possível carregar os pets.';
    } finally {
      _isLoading = false;
      notifyListeners();
    }
  }

  Future<void> addPet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.insert(pet);
      await loadFirstPage();
    } catch (error) {
      _errorMessage = 'Não foi possível cadastrar o pet.';
      notifyListeners();
    }
  }

  Future<void> updatePet(Pet pet) async {
    try {
      _errorMessage = null;
      await _repository.update(pet);
      await loadFirstPage();
    } catch (error) {
      _errorMessage = 'Não foi possível atualizar o pet.';
      notifyListeners();
    }
  }

  Future<void> deletePet(int id) async {
    try {
      _errorMessage = null;
      await _repository.delete(id);
      await loadFirstPage();
    } catch (error) {
      _errorMessage = 'Não foi possível remover o pet.';
      notifyListeners();
    }
  }

  void clearError() {
    _errorMessage = null;
    notifyListeners();
  }
}
```

### Comentário da implementação

O método `loadFirstPage` reinicia a paginação. Ele volta a página atual para zero, informa que podem existir mais itens, limpa erros antigos e remove os itens já carregados.

Isso é adequado quando a tela precisa ser recarregada do início, como após cadastrar, atualizar ou remover um pet.

O método `loadNextPage` é responsável por buscar a próxima página. Antes de iniciar, ele verifica:

```dart
if (_isLoading || !_hasMoreItems) {
  return;
}
```

Essa verificação evita dois problemas comuns. O primeiro é iniciar duas requisições ao mesmo tempo. O segundo é tentar carregar dados mesmo depois de a aplicação já saber que não existem mais itens.

Dentro do `try`, a controller calcula o `offset`, busca os dados no repositório, adiciona os novos pets à lista e avança a página atual.

A condição abaixo identifica o fim da lista:

```dart
if (newPets.length < _limit) {
  _hasMoreItems = false;
}
```

Se a aplicação pediu 10 itens, mas recebeu menos de 10, isso indica que não há uma próxima página completa. Portanto, a listagem chegou ao fim.

O bloco `catch` registra uma mensagem de erro. O bloco `finally` garante que `_isLoading` volte para `false` mesmo quando a busca falha.

## 8. Uso dos estados na tela

A tela deve consultar os getters da controller e decidir o que exibir.

Um exemplo de uso com `ListenableBuilder`:

```dart
body: ListenableBuilder(
  listenable: _controller,
  builder: (context, child) {
    if (_controller.isInitialLoading) {
      return const Center(
        child: CircularProgressIndicator(),
      );
    }

    if (_controller.hasError && _controller.pets.isEmpty) {
      return _InitialErrorView(
        message: _controller.errorMessage!,
        onRetry: _controller.loadFirstPage,
      );
    }

    if (_controller.isEmpty) {
      return _EmptyPetsView(
        onAddPressed: _addPet,
      );
    }

    return _buildPetsList();
  },
),
```

Esse trecho organiza a tela em uma ordem lógica:

1. Se está no carregamento inicial, mostra loading centralizado.
2. Se houve erro e ainda não há dados, mostra erro inicial.
3. Se não há dados, não está carregando e não há erro, mostra lista vazia.
4. Caso contrário, mostra a lista de pets.

A ordem é importante. Se a tela verificasse `isEmpty` antes de `isInitialLoading`, poderia mostrar lista vazia durante o carregamento. Por isso, estados mais específicos devem ser avaliados primeiro.

## 9. Widget de erro inicial

O erro inicial ocorre quando a primeira página falha e não existem itens carregados.

Nesse cenário, a interface pode ocupar a tela inteira com uma mensagem de erro e um botão de nova tentativa.

```dart
class _InitialErrorView extends StatelessWidget {
  final String message;
  final VoidCallback onRetry;

  const _InitialErrorView({
    required this.message,
    required this.onRetry,
  });

  @override
  Widget build(BuildContext context) {
    return Center(
      child: Padding(
        padding: const EdgeInsets.all(24),
        child: Column(
          mainAxisSize: MainAxisSize.min,
          children: [
            const Icon(Icons.error_outline, size: 48),
            const SizedBox(height: 12),
            const Text(
              'Algo deu errado',
              style: TextStyle(
                fontSize: 18,
                fontWeight: FontWeight.bold,
              ),
            ),
            const SizedBox(height: 8),
            Text(
              message,
              textAlign: TextAlign.center,
            ),
            const SizedBox(height: 16),
            ElevatedButton.icon(
              onPressed: onRetry,
              icon: const Icon(Icons.refresh),
              label: const Text('Tentar novamente'),
            ),
          ],
        ),
      ),
    );
  }
}
```

Esse widget recebe a mensagem de erro e uma função de retry. No exemplo, o retry chama `loadFirstPage`, pois a tentativa precisa recomeçar desde a primeira página.

Esse tipo de erro não deve ser exibido apenas em um rodapé, porque ainda não existe lista visível. A tela inteira precisa explicar o problema e oferecer uma ação clara.

## 10. Widget de lista vazia

Lista vazia não é erro. Ela significa que a busca funcionou, mas não encontrou registros.

Nesse caso, a interface deve orientar o usuário sobre o próximo passo.

```dart
class _EmptyPetsView extends StatelessWidget {
  final VoidCallback onAddPressed;

  const _EmptyPetsView({
    required this.onAddPressed,
  });

  @override
  Widget build(BuildContext context) {
    return Center(
      child: Padding(
        padding: const EdgeInsets.all(24),
        child: Column(
          mainAxisSize: MainAxisSize.min,
          children: [
            const Icon(Icons.pets, size: 48),
            const SizedBox(height: 12),
            const Text(
              'Nenhum pet cadastrado',
              style: TextStyle(
                fontSize: 18,
                fontWeight: FontWeight.bold,
              ),
            ),
            const SizedBox(height: 8),
            const Text(
              'Cadastre o primeiro pet para começar a organizar a lista.',
              textAlign: TextAlign.center,
            ),
            const SizedBox(height: 16),
            ElevatedButton.icon(
              onPressed: onAddPressed,
              icon: const Icon(Icons.add),
              label: const Text('Cadastrar pet'),
            ),
          ],
        ),
      ),
    );
  }
}
```

Esse widget melhora a experiência do usuário porque transforma uma tela vazia em uma orientação de ação.

Em vez de apenas mostrar “nenhum item encontrado”, a tela explica o que aconteceu e oferece o botão para cadastrar o primeiro pet.

## 11. Criação da lista com item extra de rodapé

Uma técnica comum em paginação infinita é adicionar um item extra ao final da lista. Esse item extra não é um dado real. Ele serve para exibir estados do rodapé, como carregamento, erro ou fim da lista.

```dart
Widget _buildPetsList() {
  final itemCount = _controller.pets.length + 1;

  return ListView.builder(
    controller: _scrollController,
    itemCount: itemCount,
    itemBuilder: (context, index) {
      if (index == _controller.pets.length) {
        return _buildListFooter();
      }

      final pet = _controller.pets[index];

      return ListTile(
        title: Text(pet.name),
        subtitle: Text('${pet.species} • ${pet.age} ano(s)'),
        trailing: IconButton(
          tooltip: 'Remover pet',
          icon: const Icon(Icons.delete),
          onPressed: pet.id == null
              ? null
              : () => _confirmDeletePet(pet.id!),
        ),
      );
    },
  );
}
```

A linha abaixo é essencial:

```dart
final itemCount = _controller.pets.length + 1;
```

Ela reserva um espaço adicional para o rodapé.

A condição abaixo identifica esse espaço:

```dart
if (index == _controller.pets.length) {
  return _buildListFooter();
}
```

Como os índices da lista começam em zero, o último índice válido para pets é `_controller.pets.length - 1`. Portanto, quando o índice é igual a `_controller.pets.length`, a tela chegou ao item extra.

## 12. Rodapé da lista

O rodapé concentra os estados que acontecem depois que a lista já possui itens.

Ele pode exibir:

* indicador de carregamento incremental;
* erro ao carregar mais itens;
* mensagem de fim da lista;
* espaço vazio quando nada precisa ser mostrado.

```dart
Widget _buildListFooter() {
  if (_controller.isLoadingMore) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Center(
        child: CircularProgressIndicator(),
      ),
    );
  }

  if (_controller.hasError) {
    return Padding(
      padding: const EdgeInsets.all(16),
      child: Center(
        child: Column(
          children: [
            Text(
              _controller.errorMessage!,
              textAlign: TextAlign.center,
            ),
            const SizedBox(height: 8),
            TextButton.icon(
              onPressed: _controller.loadNextPage,
              icon: const Icon(Icons.refresh),
              label: const Text('Tentar novamente'),
            ),
          ],
        ),
      ),
    );
  }

  if (!_controller.hasMoreItems) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Center(
        child: Text('Todos os pets foram carregados.'),
      ),
    );
  }

  return const SizedBox(height: 16);
}
```

### Comentário do rodapé

O primeiro estado verificado é `isLoadingMore`, porque o carregamento em andamento deve ter prioridade visual.

Depois, a tela verifica `hasError`. Nesse ponto, se a lista já possui dados, o erro é incremental. Isso significa que os dados existentes continuam visíveis, e a falha aparece apenas no final.

Em seguida, a tela verifica `!hasMoreItems`. Quando não há mais itens, o usuário recebe uma mensagem clara de fim da lista.

Por fim, se nenhum estado especial estiver ativo, o rodapé retorna apenas um pequeno espaço vazio.

## 13. Ajuste do listener de rolagem

O listener de rolagem deve ser cuidadoso para não disparar múltiplas chamadas desnecessárias.

```dart
void _onScroll() {
  if (!_scrollController.hasClients) {
    return;
  }

  if (!_controller.canLoadMore) {
    return;
  }

  final position = _scrollController.position;

  final isNearBottom = position.pixels >=
      position.maxScrollExtent - 200;

  if (isNearBottom) {
    _controller.loadNextPage();
  }
}
```

A primeira verificação impede acessar a posição do scroll quando o controller ainda não está associado a uma lista.

```dart
if (!_scrollController.hasClients) {
  return;
}
```

A segunda verificação impede buscar mais dados em momentos inadequados.

```dart
if (!_controller.canLoadMore) {
  return;
}
```

O getter `canLoadMore` verifica duas condições:

```dart
bool get canLoadMore => !_isLoading && _hasMoreItems;
```

Isso significa que a aplicação só pode carregar mais quando não há carregamento em andamento e ainda existem itens disponíveis para buscar.

Essa regra evita chamadas duplicadas ao repositório e reduz problemas como registros repetidos, concorrência desnecessária e estados inconsistentes.

## 14. Diferença entre erro inicial e erro incremental

A distinção entre erro inicial e erro incremental é essencial para uma boa experiência de uso.

### Erro inicial

O erro inicial acontece quando a primeira página não consegue ser carregada.

Nesse caso:

* não existem itens para mostrar;
* a tela pode exibir uma mensagem centralizada;
* o botão de tentar novamente deve recarregar a primeira página;
* a lista ainda não deve aparecer.

Exemplo de condição:

```dart
if (_controller.hasError && _controller.pets.isEmpty) {
  return _InitialErrorView(
    message: _controller.errorMessage!,
    onRetry: _controller.loadFirstPage,
  );
}
```

### Erro incremental

O erro incremental acontece quando alguns itens já foram carregados, mas a próxima página falha.

Nesse caso:

* a lista existente deve continuar visível;
* o erro aparece no rodapé;
* o usuário pode tentar carregar a próxima página novamente;
* os dados já obtidos não devem ser descartados.

Exemplo de tratamento no rodapé:

```dart
if (_controller.hasError) {
  return Padding(
    padding: const EdgeInsets.all(16),
    child: Center(
      child: Column(
        children: [
          Text(
            _controller.errorMessage!,
            textAlign: TextAlign.center,
          ),
          const SizedBox(height: 8),
          TextButton.icon(
            onPressed: _controller.loadNextPage,
            icon: const Icon(Icons.refresh),
            label: const Text('Tentar novamente'),
          ),
        ],
      ),
    ),
  );
}
```

Essa diferença impede que o usuário perca visualmente os dados já carregados quando apenas a próxima página falha.

## 15. Quando limpar mensagens de erro

Mensagens antigas não devem continuar aparecendo depois que uma nova tentativa começa.

Por isso, a controller limpa `_errorMessage` antes de carregar dados:

```dart
_errorMessage = null;
```

Essa limpeza aparece em métodos como `loadFirstPage`, `loadNextPage`, `addPet`, `updatePet` e `deletePet`.

Também é possível criar um método específico:

```dart
void clearError() {
  _errorMessage = null;
  notifyListeners();
}
```

Esse método pode ser útil quando a interface usa formas temporárias de exibição de erro, como `SnackBar`, banner ou dialog.

### Formas comuns de exibir erro

Um `SnackBar` é útil para mensagens temporárias na parte inferior da tela. Ele funciona bem para erros simples ou confirmações.

Um banner é útil para erros persistentes que devem ficar visíveis até o usuário fechar.

Um dialog é mais adequado para erros críticos, que exigem confirmação ou atenção imediata do usuário.

A escolha depende da gravidade do erro e do quanto ele bloqueia a continuidade da ação.

## 16. Evitando estados contraditórios

Quando uma tela possui muitos estados, é possível cair em combinações contraditórias.

Um exemplo problemático seria:

```dart
isLoading = true
hasError = true
hasMoreItems = false
pets = []
```

Essa combinação é confusa porque a tela estaria carregando, com erro, sem mais itens e sem dados ao mesmo tempo. A interface teria dificuldade para decidir se mostra loading, erro, fim da lista ou lista vazia.

Para evitar esse tipo de problema, algumas regras devem ser seguidas:

Ao iniciar um novo carregamento, o erro anterior deve ser limpo. Isso evita mostrar erro antigo enquanto uma nova tentativa está em andamento.

Ao carregar a primeira página, a lista deve ser limpa. Isso garante que a tela represente uma nova busca do início.

Ao receber menos itens que o limite, `hasMoreItems` deve se tornar `false`. Isso informa que a listagem chegou ao fim.

Ao carregar mais itens, a lista existente deve ser preservada. Isso mantém a experiência estável para o usuário.

Ao ocorrer erro incremental, os itens carregados continuam disponíveis. Isso evita que uma falha parcial apague conteúdo útil da tela.

## 17. Estrutura principal da página

Abaixo está uma versão da estrutura principal da tela, reunindo controller, scroll, carregamento inicial, descarte de recursos e estados da interface.

```dart
class _PetListPageState extends State<PetListPage> {
  late final PetController _controller;
  late final ScrollController _scrollController;

  @override
  void initState() {
    super.initState();

    final dataSource = PetLocalDataSource();
    final repository = SqlitePetRepository(dataSource);

    _controller = PetController(repository);
    _scrollController = ScrollController();

    _scrollController.addListener(_onScroll);

    _controller.loadFirstPage();
  }

  @override
  void dispose() {
    _scrollController.removeListener(_onScroll);
    _scrollController.dispose();
    _controller.dispose();

    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(
        title: const Text('Pets'),
      ),
      body: ListenableBuilder(
        listenable: _controller,
        builder: (context, child) {
          if (_controller.isInitialLoading) {
            return const Center(
              child: CircularProgressIndicator(),
            );
          }

          if (_controller.hasError && _controller.pets.isEmpty) {
            return _InitialErrorView(
              message: _controller.errorMessage!,
              onRetry: _controller.loadFirstPage,
            );
          }

          if (_controller.isEmpty) {
            return _EmptyPetsView(
              onAddPressed: _addPet,
            );
          }

          return _buildPetsList();
        },
      ),
      floatingActionButton: FloatingActionButton(
        onPressed: _addPet,
        child: const Icon(Icons.add),
      ),
    );
  }
}
```

### Comentário da estrutura

O método `initState` cria as dependências da tela, registra o listener de rolagem e inicia o carregamento da primeira página.

O método `dispose` remove o listener e descarta os controllers. Isso evita vazamentos de memória e chamadas para objetos que não deveriam mais existir.

O método `build` fica mais legível porque os detalhes dos estados foram encapsulados na controller e em widgets auxiliares.

## 18. Aplicação prática resolvida: refatorando a listagem paginada

### Cenário

Uma aplicação Flutter possui uma tela de listagem de pets. A tela já busca dados paginados em um repositório, mas ainda trata os estados de forma confusa. Quando uma nova página é carregada, a lista pode piscar. Quando ocorre erro ao buscar mais itens, os dados carregados podem desaparecer. Quando não há dados, a tela não orienta claramente o usuário.

### Objetivo

Refatorar a tela para tratar corretamente:

* carregamento inicial;
* carregamento incremental;
* erro inicial;
* erro incremental;
* lista vazia;
* fim da lista;
* controle de chamadas duplicadas durante a rolagem.

### Solução

A primeira etapa é criar getters auxiliares na controller:

```dart
bool get isInitialLoading => _isLoading && _pets.isEmpty;
bool get isLoadingMore => _isLoading && _pets.isNotEmpty;
bool get isEmpty => _pets.isEmpty && !_isLoading && !hasError;
bool get canLoadMore => !_isLoading && _hasMoreItems;
```

Esses getters tornam a tela mais declarativa. Em vez de repetir combinações de variáveis, a interface usa nomes que representam situações reais.

A segunda etapa é ajustar o carregamento de páginas:

```dart
Future<void> loadNextPage() async {
  if (_isLoading || !_hasMoreItems) {
    return;
  }

  _isLoading = true;
  _errorMessage = null;
  notifyListeners();

  try {
    final offset = _currentPage * _limit;

    final newPets = await _repository.findPage(
      limit: _limit,
      offset: offset,
    );

    _pets.addAll(newPets);
    _currentPage++;

    if (newPets.length < _limit) {
      _hasMoreItems = false;
    }
  } catch (error) {
    _errorMessage = 'Não foi possível carregar os pets.';
  } finally {
    _isLoading = false;
    notifyListeners();
  }
}
```

A terceira etapa é ajustar a tela para exibir cada estado:

```dart
if (_controller.isInitialLoading) {
  return const Center(
    child: CircularProgressIndicator(),
  );
}

if (_controller.hasError && _controller.pets.isEmpty) {
  return _InitialErrorView(
    message: _controller.errorMessage!,
    onRetry: _controller.loadFirstPage,
  );
}

if (_controller.isEmpty) {
  return _EmptyPetsView(
    onAddPressed: _addPet,
  );
}

return _buildPetsList();
```

A quarta etapa é criar um rodapé para a lista:

```dart
Widget _buildListFooter() {
  if (_controller.isLoadingMore) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Center(
        child: CircularProgressIndicator(),
      ),
    );
  }

  if (_controller.hasError) {
    return Padding(
      padding: const EdgeInsets.all(16),
      child: Center(
        child: Column(
          children: [
            Text(
              _controller.errorMessage!,
              textAlign: TextAlign.center,
            ),
            const SizedBox(height: 8),
            TextButton.icon(
              onPressed: _controller.loadNextPage,
              icon: const Icon(Icons.refresh),
              label: const Text('Tentar novamente'),
            ),
          ],
        ),
      ),
    );
  }

  if (!_controller.hasMoreItems) {
    return const Padding(
      padding: EdgeInsets.all(16),
      child: Center(
        child: Text('Todos os pets foram carregados.'),
      ),
    );
  }

  return const SizedBox(height: 16);
}
```

### Resultado esperado

Após a refatoração, a tela deve se comportar assim:

Quando abrir pela primeira vez, mostra um loading centralizado.

Se a primeira busca falhar, mostra uma tela de erro com botão de tentar novamente.

Se a primeira busca funcionar, mas não retornar registros, mostra uma tela de lista vazia com botão de cadastro.

Se houver itens, mostra a lista normalmente.

Quando o usuário chegar perto do fim, busca a próxima página e mostra loading apenas no rodapé.

Se a próxima página falhar, preserva os itens já carregados e mostra erro no rodapé.

Quando não houver mais itens, mostra a mensagem de fim da lista.

### Como validar

Para validar o carregamento inicial, abra a tela com o repositório respondendo lentamente. O loading deve aparecer no centro da tela antes dos dados.

Para validar lista vazia, faça o repositório retornar uma lista vazia na primeira página. A tela deve mostrar a mensagem de nenhum pet cadastrado.

Para validar carregamento incremental, use mais registros do que o limite da página. Ao rolar até perto do fim, a próxima página deve ser buscada automaticamente.

Para validar fim da lista, faça a última página retornar menos itens do que `_limit`. A mensagem “Todos os pets foram carregados” deve aparecer no rodapé.

Para validar erro incremental, simule uma falha apenas na segunda ou terceira página. A lista já carregada deve continuar visível, e o erro deve aparecer apenas no final.

### Possíveis erros na aplicação

Um erro comum é limpar a lista ao carregar uma página adicional. Isso faz a interface perder os itens já exibidos.

Outro erro comum é não verificar `_isLoading` antes de buscar mais itens. Isso pode gerar chamadas duplicadas se o usuário rolar rapidamente.

Também é comum tratar qualquer erro como erro inicial. Isso prejudica a experiência quando o usuário já estava vendo dados na tela.

## 19. Organização dos widgets em arquivos separados

Quando a tela cresce, é recomendável extrair widgets auxiliares para arquivos próprios.

Uma organização possível é:

```text
lib/
  features/
    pet/
      presentation/
        widgets/
          empty_pets_view.dart
          initial_error_view.dart
          pets_list_footer.dart
```

O arquivo `empty_pets_view.dart` pode conter o widget de lista vazia.

O arquivo `initial_error_view.dart` pode conter o widget de erro inicial.

O arquivo `pets_list_footer.dart` pode conter o rodapé da lista, responsável por loading incremental, erro incremental e fim da lista.

Essa separação ajuda a manter a página principal focada na composição geral da interface. Também facilita testes, manutenção e reutilização dos widgets em outras telas.

## 20. Erros comuns e dúvidas frequentes

### Mostrar loading de tela inteira ao carregar mais itens

Esse erro acontece quando a interface trata todo carregamento da mesma forma. Em paginação infinita, o loading de tela inteira deve ser usado apenas quando ainda não há itens. Se a lista já possui dados, o loading deve aparecer no rodapé.

### Apagar os dados quando a próxima página falha

Esse problema ocorre quando a tela ou a controller limpam a lista durante um carregamento incremental. A lista só deve ser limpa ao carregar a primeira página. Em erro incremental, os itens já carregados devem ser preservados.

### Chamar `loadNextPage` várias vezes ao mesmo tempo

Isso acontece quando o listener de rolagem dispara muitas vezes perto do final da lista e a controller não bloqueia chamadas simultâneas. O getter `canLoadMore` e a verificação `_isLoading` resolvem esse problema.

### Confundir lista vazia com erro

Lista vazia significa que a busca funcionou, mas não encontrou registros. Erro significa que a busca falhou. A interface deve tratar esses casos de forma diferente.

### Não identificar o fim da lista

Se a controller não alterar `_hasMoreItems` para `false`, a tela continuará tentando carregar páginas mesmo quando não houver mais dados. A regra `newPets.length < _limit` ajuda a identificar o fim.

### Esquecer de chamar `notifyListeners`

Quando a controller altera estados internos, a interface precisa ser notificada. Sem `notifyListeners`, a tela pode não atualizar loading, erro, lista vazia ou novos itens.

## 21. Checklist explicado de implementação

### Verifique se a controller diferencia carregamento inicial e carregamento incremental

O que verificar: confirme se existem getters como `isInitialLoading` e `isLoadingMore`.

Por que importa: a interface precisa mostrar loading de tela inteira apenas no início e loading de rodapé ao buscar mais itens.

Como validar: abra a tela sem dados carregados e observe o loading central. Depois, role a lista até buscar a próxima página e confirme que o loading aparece apenas no final.

O que acontece se faltar: a lista pode desaparecer ou piscar toda vez que uma nova página for carregada.

### Verifique se a lista vazia não aparece durante o carregamento

O que verificar: o getter `isEmpty` deve considerar que a lista só está vazia quando não há carregamento e não há erro.

Por que importa: durante o carregamento inicial, a ausência temporária de itens não significa que a lista está vazia.

Como validar: simule uma busca lenta. Enquanto os dados não chegam, a tela deve mostrar loading, não mensagem de lista vazia.

O que acontece se faltar: o usuário pode ver uma mensagem incorreta de lista vazia antes de os dados serem carregados.

### Verifique se o erro inicial ocupa a tela inteira

O que verificar: quando `hasError` for verdadeiro e `pets.isEmpty` também, a tela deve exibir um widget de erro centralizado.

Por que importa: se não há dados, o usuário precisa entender o problema e ter uma ação clara para tentar novamente.

Como validar: simule erro na primeira busca. A tela deve mostrar mensagem e botão de retry.

O que acontece se faltar: o usuário pode ficar em uma tela vazia sem saber se houve falha, carregamento ou ausência de dados.

### Verifique se o erro incremental aparece no rodapé

O que verificar: quando a lista já possui itens e ocorre erro ao carregar mais, o erro deve ser mostrado no final da lista.

Por que importa: a falha ao buscar mais dados não deve apagar o conteúdo já disponível.

Como validar: carregue a primeira página com sucesso e simule erro na próxima. A lista deve permanecer visível.

O que acontece se faltar: a aplicação pode parecer instável, porque dados já carregados desaparecem sem necessidade.

### Verifique se `canLoadMore` bloqueia chamadas duplicadas

O que verificar: o listener de rolagem deve consultar `_controller.canLoadMore` antes de chamar `loadNextPage`.

Por que importa: a rolagem pode disparar várias vezes em sequência. Sem bloqueio, o repositório pode receber chamadas duplicadas.

Como validar: role rapidamente até o fim e observe se apenas uma busca é feita por vez.

O que acontece se faltar: podem aparecer itens duplicados, consumo desnecessário de recursos ou inconsistência na paginação.

### Verifique se o fim da lista é detectado corretamente

O que verificar: quando a quantidade de itens retornados for menor que `_limit`, `_hasMoreItems` deve virar `false`.

Por que importa: essa regra informa que não há mais páginas a carregar.

Como validar: use uma base com quantidade de registros que não complete a última página. Ao chegar ao fim, a mensagem de fim da lista deve aparecer.

O que acontece se faltar: a tela pode tentar carregar infinitamente mesmo sem novos dados.

### Verifique se os recursos são descartados no `dispose`

O que verificar: o `ScrollController` deve remover o listener e ser descartado. A controller também deve ser descartada quando não for mais usada.

Por que importa: controllers mantêm referências internas. Se não forem descartados, podem causar vazamentos de memória ou chamadas indevidas.

Como validar: revise o método `dispose` e confirme a presença de `removeListener`, `dispose` do scroll e `dispose` da controller.

O que acontece se faltar: a aplicação pode manter objetos vivos desnecessariamente e executar callbacks em telas que já foram removidas.

## 22. Síntese final

Uma listagem paginada com rolagem infinita precisa representar estados diferentes de forma clara. O carregamento inicial deve ocupar a tela inteira, porque ainda não há conteúdo. O carregamento incremental deve aparecer no rodapé, porque os itens existentes devem continuar visíveis.

A controller deve centralizar regras importantes, como `isInitialLoading`, `isLoadingMore`, `isEmpty`, `hasError` e `canLoadMore`. Esses getters tornam a interface mais legível e reduzem duplicação de lógica.

Erros também precisam ser diferenciados. O erro inicial impede a tela de mostrar dados e pode ocupar toda a área principal. O erro incremental acontece depois que alguns itens já foram carregados e deve aparecer apenas no rodapé.

O fim da lista deve ser controlado por `hasMoreItems`. Quando a última busca retorna menos itens que o limite, a aplicação entende que não há mais páginas.

---

## Conclusão

O controle correto dos estados de paginação melhora a experiência do usuário e torna o código mais fácil de manter. Uma tela bem estruturada não apenas carrega dados, mas também comunica claramente o que está acontecendo: carregando, vazia, com dados, carregando mais, finalizada ou em erro.

Ao separar as responsabilidades entre controller, tela principal e widgets auxiliares, a aplicação fica mais previsível, reutilizável e preparada para evoluir. Essa organização é especialmente importante em interfaces com rolagem infinita, porque pequenos erros de estado podem gerar chamadas duplicadas, telas confusas ou perda visual de dados já carregados.
